# Выполнить работу по готовому плану

Цель: реализовать задачу строго по `plan.md`.


## Исполнитель

Скил выполняет агент **developer** (`.claude/agents/developer.md`) в изолированном
контексте (`context: fork`): истории чата нет, вопросы пользователю задать нельзя.
Везде ниже, где сказано «спросить пользователя», — действовать по правилу из роли
developer: зафиксировать вопрос в файле задачи и вернуть его в разделе «Вопросы
владельцу» (NEEDS_INPUT). Основная сессия задаст вопросы и перезапустит скил с
ответами в аргументах после номера задачи (напр. `007 коммитить в main`).

## Аргументы
- `$ARGUMENTS` (опционально): номер задачи.

## Определение задачи

- Задачи: `second-brain/tasks/tasks/`. Формат: `{NNN}-{описание}`.
- Поиск: `ls second-brain/tasks/tasks/`.
- Если номер не передан — последняя задача по номеру.

## Границы задачи (жёстко)

**do реализует только то, что в плане.** Если по ходу выясняется, что нужна
самостоятельная доработка вне плана (другая подсистема, другая фича) — остановиться и
сообщить пользователю, что нужна отдельная задача. Не «дотягивать» лишнее ради
завершения.

## Что прочитать перед стартом

1. `plan.md` в папке задачи — основной источник инструкций. Нет файла — сообщить и
   предложить `/plan-implementation`. Учесть `plan-part2.md` и т.д., если есть.
2. `analyze.md` — для контекста и архитектуры.
3. `CLAUDE.md` — стек, конвенции, **команды проверок**.
4. **`README.md` в затрагиваемых папках** (если есть) — прочитать перед правками рядом.

## Порядок работы

### 1. Разбор плана
- Прочитать `plan.md` полностью.
- **Минимальный объём:** реализовать ровно то, что в плане. Не добавлять фич, не
  рефакторить соседний код, не улучшать вне задачи.
- Неоднозначности — **спросить пользователя** до начала, а не выбирать молча.

### 2. Реализация
- Выполнять шаги **последовательно**, по примерам из плана.
- Придерживаться конвенций `CLAUDE.md` и паттернов кода.
- Использовать сводную таблицу файлов из плана как чеклист.
- Читать каждый файл перед изменением.
- **Документация рядом с кодом:** если правки меняют то, что описано в `README.md`
  папки или в `second-brain/architecture/` — актуализировать в рамках той же задачи.

### 3. Проверки после реализации
Из корня проекта:
- `npm run format` — отформатировать.
- `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` — без ошибок.
- Визуальные изменения тестами не проверить — в отчёте **явно перечислить, что
  пользователю посмотреть в браузере** (`npm run dev`, пункт «Ручная проверка» из плана).
- Проверить: ничего лишнего не добавлено.

### 4. Перенос задачи в архив
Если все проверки прошли:
- `mv "second-brain/tasks/tasks/{NNN}-{описание}" second-brain/tasks/tasks-done/`
- Сообщить пользователю, что задача перенесена в `tasks-done`.

Если проверки не прошли — папку не переносить, доложить о проблемах.

## Большой план
Если план не помещается в один прогон — сделать законченную часть, в итоге явно
перечислить, что сделано и что осталось.

## Заметки
- do — третья стадия конвейера (analyze → plan → do → fix-tests).
- Коммиты не делать автоматически — только по явной просьбе (`/commit`).
- Обнаружив ошибку/неточность в плане — сообщить пользователю, не отклоняться молча.
