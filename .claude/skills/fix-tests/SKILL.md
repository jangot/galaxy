# Починить упавшие тесты

Цель: найти и починить упавшие тесты (и ошибки typecheck/lint) после реализации задачи,
не ломая логику реализации.

## Аргументы
- `$ARGUMENTS` (опционально): номер задачи.

## Определение задачи

- Задачи: `second-brain/tasks/tasks/` или `second-brain/tasks/tasks-done/`.
- Формат: `{NNN}-{описание}`. Искать сперва в `tasks/`, затем в `tasks-done/`.
- Если номер не передан — последняя задача по номеру.

## Что прочитать перед стартом

1. `plan.md` в папке задачи — что было реализовано.
2. `analyze.md` — контекст и архитектура.
3. `CLAUDE.md` — конвенции и команды.

## Порядок работы

### 1. Запуск проверок
Из корня проекта: `npm test`, `npm run typecheck`, `npm run lint`. Записать список
упавших тестов/ошибок.

Всё зелёное — сообщить и выйти.

### 2. Анализ причин
Для каждого упавшего теста определить причину:
- **Тест устарел** — реализация изменилась (новые поля, другие константы, другой порядок).
- **Тест некорректен** — неверные ожидания/входные данные.
- **Тест недетерминирован** — зависит от `Math.random`/реального времени вместо `Rng`/`dt`.
- **Баг в реализации** — тест вскрыл реальную ошибку.

### 3. Устранение
- **Устарел / некорректен:** обновить тест под текущую реализацию, сохранив его смысл.
- **Недетерминирован:** перевести на сидируемый `Rng` / явный `dt`.
- **Баг в реализации:** сообщить пользователю о найденном баге, починить код, не
  «заглушать» тест. Если логика верна — чинить тест; если тест вскрыл баг — чинить баг.

### 4. Проверка
Перезапустить тесты. Убедиться, что упавшие теперь проходят и ранее проходившие не
сломались.

### 5. Архив
Если задача ещё в `tasks/` (do не перенёс её из-за падений), а теперь всё зелёное —
перенести в `tasks-done/`.

## Ограничения
- **Не удалять** тесты — только чинить/обновлять.
- **Не отключать** тесты через `.skip`/`.todo` без явного согласия пользователя.
- Не менять логику реализации ради прохождения теста, если это противоречит плану — сообщить.
- Причина падения неясна — **спросить пользователя** перед правками.

## Заметки
- fix-tests — стадия после do (analyze → plan → do → fix-tests).
- Коммиты не делать автоматически.
- Тест вскрыл реальный баг — это важная находка, явно сообщить пользователю.
