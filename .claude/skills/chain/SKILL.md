# Прогон полного конвейера analyze → plan → do → fix-tests

Цель: последовательно выполнить стадии конвейера для задачи. Каждый шаг (`analyze`,
`plan-implementation`, `do`, `fix-tests`) выполняет отдельный агент **developer** с
изолированным контекстом и возвращает итог.

Оркестратор (основная сессия) сам код не пишет — только вызывает шаги, проверяет
результат по файлам задачи и приносит владельцу вопросы. Обмен между шагами — через
файлы в папке задачи (`description.md`, `analyze.md`, `plan.md`) и код.

## Аргументы

- `$ARGUMENTS` — номер задачи (обязателен). Без номера — сообщить и остановиться.

## Подготовка

- Найти папку: `ls second-brain/tasks/tasks/ second-brain/tasks/tasks-done/ | grep '^{NNN}-'`.
  Не нашлась — сообщить и остановиться.
- Запомнить путь — для проверок и `error.md`.

## Как запускать шаг

Рабочие скилы объявлены с `context: fork`, но при вызове через `Skill` tool аргументы
до форкнутого агента **не доходят** — агент сам выбирает задачу (может взять не ту).
Поэтому каждый шаг запускать **через Agent tool** (`subagent_type: developer`) с явным
промптом:

```
Выполни скил `{skill}` проекта для задачи **{NNN}** (папка `{путь к папке задачи}`).
Инструкции — в `.claude/skills/{skill}/SKILL.md`; прочитай и следуй им, считая
аргументы скила равными `{NNN}{ ответы, если перезапуск}`.
{Для do: ручную проверку в браузере не выполняй — перечисли, что проверить владельцу.}
Не коммить.
{Ответы владельца на вопросы прошлого прогона (если перезапуск): ...}

Верни итог со статусом SUCCESS / NEEDS_INPUT (с разделом «Вопросы владельцу») /
FAILURE{, для do — результат проверок format:check, lint, typecheck, test, build}.
```

Если в первой строке итога агент указал другую задачу, чем `{NNN}`, — результат не
принимать: сообщить владельцу, что и где изменено, и остановиться (ничего не откатывать
самому).

Статусы итога:

- **SUCCESS** → следующий шаг;
- **NEEDS_INPUT** → задать владельцу вопросы из раздела «Вопросы владельцу» через
  `AskUserQuestion` (самодостаточно, варианты с рекомендуемым первым), затем
  перезапустить тот же шаг с ответами в промпте;
- **FAILURE** → см. правила шага ниже.

Если субагент сообщил, что задача требует работы вне её рамок, — остановить конвейер,
сообщить владельцу, предложить отдельную задачу.

## Шаги

1. **analyze**. После — проверить `analyze.md`. Нет файла и нет
   вопросов → **обработка ошибок**. Есть `analyze.md`, но в нём открытые вопросы,
   влияющие на реализацию, — показать их владельцу и спросить, продолжать ли.
2. **plan-implementation**. Нет `plan.md` → **обработка ошибок**.
3. **do**. Ошибки тестов/линта → шаг 4. Неустранимая ошибка сборки или выход за рамки
   задачи → **обработка ошибок**.
4. **fix-tests**. Тесты по-прежнему падают → **обработка ошибок**. Иначе — сводка
   владельцу по всем шагам, что проверить в браузере, предложить `/commit {NNN}`.

## Обработка ошибок

1. Создать `{путь к папке задачи}/error.md`:

```markdown
# Ошибка выполнения конвейера

**Шаг:** {analyze | plan | do | fix-tests}
**Дата:** {текущая дата}

## Описание ошибки

{Что пошло не так — из итога developer}

## Статус шагов

- {✅ | ❌ | ⏭} analyze
- {✅ | ❌ | ⏭} plan
- {✅ | ❌ | ⏭} do
- {✅ | ❌ | ⏭} fix-tests
```

2. Сообщить владельцу: какой шаг упал, причина, путь к `error.md`. Остановиться.

## Заметки

- Шаги строго последовательны; каждый — отдельный агент developer.
- `chain` сам задачу не реализует — только оркеструет.
