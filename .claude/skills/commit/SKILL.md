# Коммит результата задачи и pull request

Цель: закоммитить изменения по задаче так, чтобы CI **не упал** — форматирование, линт,
типы, тесты и сборка прогоняются локально **до** коммита.

Запускается обычно после `chain` / `do-chain`. Сам скилл код не меняет, кроме
автоформатирования и автофиксов линтера в файлах задачи.


## Исполнитель

Скил выполняет агент **developer** (`.claude/agents/developer.md`) в изолированном
контексте (`context: fork`): истории чата нет, вопросы пользователю задать нельзя.
Везде ниже, где сказано «спросить пользователя», — действовать по правилу из роли
developer: зафиксировать вопрос в файле задачи и вернуть его в разделе «Вопросы
владельцу» (NEEDS_INPUT). Основная сессия задаст вопросы и перезапустит скил с
ответами после номера задачи (напр. `007 коммитить в main`).

**Откуда брать аргументы.** Оркестраторы (`chain`, `do-chain`, `feature-chain`)
запускают developer через Agent tool, а не через `Skill`: при вызове форкнутого скила
через `Skill` аргументы до агента не доходят. Тогда номер задачи и ответы владельца —
в промпте запуска («считая аргументы скила равными `…`»); они имеют приоритет над
пустыми аргументами. В первой строке итога всегда указать, с какой задачей работал и
откуда взят номер (аргументы / промпт / выбран по умолчанию).

## Аргументы

- **номер задачи** (`007`) → режим «задача»
- **пусто** → режим «авто»
- после номера могут идти ответы владельца на вопросы прошлого прогона
  (напр. `007 коммитить в main, без PR`) — следовать им.

## Главное правило: при неоднозначности — спросить

Любая неясность → вопрос владельцу (NEEDS_INPUT, см. «Исполнитель»), а не догадка.
Ничего не коммитить, пока вопросы не сняты:

- непонятно, какую задачу коммитить, или кандидатов несколько;
- в рабочем дереве есть изменения, не относящиеся к задаче;
- непонятен тип/скоуп/текст коммит-сообщения;
- текущая ветка — `main` и неясно, коммитить ли в неё;
- проверки упали на том, что не похоже на изменения задачи.

## Шаг 1. Определить что коммитим

### Режим «задача»
1. Найти папку: `ls second-brain/tasks/tasks/ second-brain/tasks/tasks-done/ | grep '^{NNN}-'`.
   Не нашлась — сообщить и остановиться.
2. Прочитать `description.md` и `plan.md` (сводную таблицу файлов) — для сверки списка
   изменённых файлов и для коммит-сообщения.

### Режим «авто»
1. `git status --porcelain` — где реально есть изменения.
2. Сопоставить изменённые файлы со сводными таблицами `plan.md` последних задач
   (`ls -t second-brain/tasks/tasks-done/ second-brain/tasks/tasks/ | head`).
3. Ровно одна задача покрывает изменения — работать с ней. Иначе (несколько задач,
   изменения без задачи) — вопрос владельцу с кандидатами.

Инвариант: одна задача — один коммит.

## Шаг 2. Предварительные проверки

1. `git status`, `git branch --show-current`.
   - Ветка `main` → если remote ещё нет, коммит в `main` нормален; если есть —
     спросить: коммитить сюда или создать ветку (`feature/<kebab>` / `fix/<kebab>`).
   - Идёт merge/rebase, detached HEAD → сообщить и остановиться.
2. **Сверить изменённые файлы с задачей** (`git status --porcelain` против таблицы
   файлов в `plan.md`). Файлы задачи в `second-brain/` (папка задачи, обновлённые
   заметки) — часть задачи, коммитятся вместе с кодом. Лишние файлы → спросить.
   Не делать `git add -A` / `git add .` вслепую — стейджить явный список.
3. **Стоп-сигналы — не коммитить, сообщить:**
   - `package-lock.json` изменён, хотя зависимости по задаче не менялись → спросить;
   - секреты, `.env`, большие бинарники, `dist/`, логи.
4. Нет `node_modules` → `npm ci`.

## Шаг 3. Форматирование

1. Только файлы задачи: `npx prettier --write --ignore-unknown <изменённые файлы>`.
2. `npm run format:check`. Падает на файлах вне задачи — спросить, не чинить молча.

## Шаг 4. Все проверки локально — обязательно

Источник истины — `.github/workflows/*.yml` (если появится), иначе `CLAUDE.md`.
Сейчас: `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`,
`npm run build`.

- Ни одну проверку не пропускать.
- Ошибки линта в файлах задачи → один раз `npx eslint --fix <файлы>`, перепрогнать.
  Остались — **не коммитить**.
- Падение сборки / типов / тестов → **не коммитить**. Показать ошибку (файл, строка,
  текст), предложить `/fix-tests {NNN}`. Логику самому не переписывать.
- После автоформата/автофикса перепрогнать всё.

## Шаг 5. Коммит-сообщение

**Conventional Commits на английском**: `type(scope): summary`
(сверяться с `git log --oneline -15`).

- `type`: `feat` / `fix` / `refactor` / `chore` / `test` / `docs`.
- `scope`: модуль/подсистема (`engine`, `player`, `enemies`, `hud`, `menu`, `audio`…).
- `summary`: суть задачи одной строкой, ≤ 72 символов, повелительное наклонение, без точки.
- Тело (опционально): 1–4 пункта «что и зачем» из `description.md` / `plan.md`.
- В конце — строка атрибуции из системных указаний (`Co-Authored-By: ...`).

Тип/скоуп/суть неочевидны — вопрос владельцу с вариантами.

## Шаг 6. Коммит

```bash
git add <явный список файлов>
git diff --cached --stat     # сверить, что в индексе ровно нужное
git commit -F - <<'MSG'
type(scope): summary

- ...

Co-Authored-By: ...
MSG
```

Никаких `--no-verify`. Хук упал → разобраться, починить, сделать **новый** коммит
(не `--amend`).

## Шаг 7. Push и pull request

Только если коммит создан и все проверки прошли.

1. **Есть ли remote:** `git remote get-url origin`. Нет — пропустить шаг, в отчёте
   отметить «коммит локальный, remote не настроен». Создавать репозиторий на GitHub —
   только по явной просьбе пользователя.
2. **Ветка.** В `main` напрямую не пушить, если пользователь не сказал иначе: спросить —
   создать ветку от текущего коммита (`git switch -c <branch>`) или оставить локально.
3. **Push:** `git push -u origin HEAD`. Никаких `--force`. Отклонён — сообщить и спросить.
4. **Есть ли PR:** `gh pr list --head <branch> --state open --json number,url`.
   Открыт — новый не создавать (push обновил его). Нет — создать.
5. **Создание PR** (base — дефолтная ветка:
   `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`):
   ```bash
   gh pr create --base <base> --head <branch> --title "<заголовок коммита>" --body-file - <<'MSG'
   ## Summary
   - что и зачем (1–4 пункта)

   ## Checks
   - format:check, lint, typecheck, tests, build — passed locally

   🤖 Generated with [Claude Code](https://claude.com/claude-code)
   MSG
   ```
   На английском. Несколько коммитов на ветке — Summary по всей ветке. Не ставить
   reviewers/labels/auto-merge и не мёржить.

## Шаг 8. Отчёт

- ✅ / ❌ ветка, хеш и заголовок коммита;
- какие проверки прошли и что было автоисправлено;
- PR: ссылка, «создан» / «обновлён push'ем» / «remote не настроен»;
- если не закоммичено — почему и что сделать.

## Заметки

- Скилл вызывается явно — это и есть разрешение на коммит, push ветки и создание PR.
  Мёрж — никогда.
- Не трогать файлы вне задачи, кроме согласованных с пользователем.
