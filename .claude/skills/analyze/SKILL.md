# Анализ логики и архитектуры кода перед изменениями

Цель: изучить код и создать файл-описание для дальнейшей работы (стадии plan и do).

## Аргументы
- `$ARGUMENTS` (опционально): номер задачи. Может не передаваться.

## Расположение задач

- Активные: `second-brain/tasks/tasks/`
- Завершённые: `second-brain/tasks/tasks-done/`
- Формат папки: `{NNN}-{описание}` (напр. `004-player-ship`)

Поиск папки: `ls second-brain/tasks/tasks/ second-brain/tasks/tasks-done/`.
- Если номер передан — использовать его.
- Если не передан — взять задачу с максимальным номером.
- Если папка есть — прочитать `description.md` для контекста; если есть `analyze.md` —
  предупредить о перезаписи.
- Если папки нет — создать в `second-brain/tasks/tasks/`. Не искать в других местах.

## Границы задачи

Анализ ограничен тем, что описано в `description.md`. Если выясняется, что для задачи
нужно сначала сделать другую самостоятельную часть (напр. для врагов нужна система
коллизий, которой ещё нет) — не расширять задачу молча: отметить в `## Открытые
вопросы` и предложить вынести в отдельную задачу.

## Что изучать

Порядок источников — **сперва second-brain, потом код** (см. CLAUDE.md):

1. **Правила проекта:** `CLAUDE.md` — стек, команды, конвенции.
2. **Гейм-дизайн:** `second-brain/game-design.md` — решённые механики и открытые вопросы.
3. **База знаний:** `second-brain/architecture/`, `second-brain/decisions/` (ADR),
   связанная запись в `second-brain/features/`, если есть.
4. **Код:** относящиеся модули в `src/` — реальные паттерны, структура, существующее
   поведение. **Если в затрагиваемой папке есть `README.md` — обязательно прочитать
   его** до анализа кода.
5. **Существующие тесты** (`src/**/*.test.ts`) — для понимания ожидаемого поведения.

## Структура выходного файла

Результат: `second-brain/tasks/tasks/{NNN}-{описание}/analyze.md`

Анализ **на русском**, со следующими секциями:

```markdown
# Анализ: {название задачи}

## Общее описание функциональности
Что нужно реализовать, зачем, как это выглядит и ощущается в игре.

## Модели данных и состояние
Сущности, их поля и состояния (напр. враг: в строю / пикирует / возвращается),
константы (скорости, размеры, тайминги). Таблица — если применимо.

## Связанные модули и сущности
Таблица: модуль/сущность → назначение → файлы.

## Точки встраивания
Где новая логика подключается: сцена, цикл обновления, отрисовка, ввод, HUD.

## Файлы и места в коде
Таблица: файл → что содержит → что нужно изменить/создать.

## Тестируемость
Что из логики можно покрыть unit-тестами (детерминизм через `Rng`/`dt`), что
проверяется только визуально.

## Зависимости и ограничения
Ограничения (разрешение 256×240, фиксированный шаг, производительность), риски.

## Открытые вопросы
Нерешённые вопросы; сюда же — части, которые стоит вынести в отдельную задачу.

## Ссылки на документацию
- CLAUDE.md
- second-brain/game-design.md
- (другие релевантные файлы)
```

## Проверка слепых зон

Перед записью `analyze.md` — для любой категории, где ответ неясен (особенно игровые
числа и поведение: скорость, частота стрельбы, очки, что происходит при смерти),
**спросить пользователя**, а не выбирать умолчание молча. Нерешённое — в
`## Открытые вопросы`.

## Заметки
- analyze — первая стадия конвейера (analyze → plan → do).
- Анализ НЕ должен содержать план реализации или примеры кода — это задача `/plan-implementation`.
- Анализ должен давать достаточно контекста, чтобы построить план.
