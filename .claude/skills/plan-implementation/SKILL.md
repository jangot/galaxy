# План реализации по готовому анализу (без изменений в коде)

Цель: составить детальный план реализации на основе `analyze.md`. Код не писать,
файлы проекта не менять.


## Исполнитель

Скил выполняет агент **developer** (`.claude/agents/developer.md`) в изолированном
контексте (`context: fork`): истории чата нет, вопросы пользователю задать нельзя.
Везде ниже, где сказано «спросить пользователя», — действовать по правилу из роли
developer: зафиксировать вопрос в файле задачи и вернуть его в разделе «Вопросы
владельцу» (NEEDS_INPUT). Основная сессия задаст вопросы и перезапустит скил с
ответами после номера задачи (напр. `007 коммитить в main`).

**Откуда брать аргументы.** Оркестраторы (`chain`, `do-chain`, `feature-chain`)
запускают developer через Agent tool, а не через `Skill`: при вызове форкнутого скила
через `Skill` аргументы до агента не доходят. Тогда номер задачи и ответы владельца —
в промпте запуска («считая аргументы скила равными `…`»); они имеют приоритет над
пустыми аргументами. В первой строке итога всегда указать, с какой задачей работал и
откуда взят номер (аргументы / промпт / выбран по умолчанию).

## Аргументы
- `$ARGUMENTS` (опционально): номер задачи.

## Определение задачи

- Задачи: `second-brain/tasks/tasks/` или `second-brain/tasks/tasks-done/`.
- Формат: `{NNN}-{описание}`.
- Поиск: `ls second-brain/tasks/tasks/ second-brain/tasks/tasks-done/`.
- Если номер не передан — последняя задача по номеру.

## Границы задачи

План описывает только то, что входит в задачу по `description.md`/`analyze.md`.
Самостоятельные куски, которые всплыли по ходу, — не включать: отметить в
`## Открытые вопросы` и предложить отдельную задачу.

## Что прочитать перед планом

1. `analyze.md` в папке задачи — если файла нет, сообщить и предложить `/analyze`.
2. `description.md` в папке задачи — доп. контекст и критерии готовности.
3. `CLAUDE.md` — стек, команды, конвенции.
4. `design.md` фичи (если задача из нарезки `/design-feature`) — план следует
   согласованным интерфейсам и модулям; отступления — только с причиной.
5. `second-brain/architecture/` и код в `src/` для паттернов.
6. **`README.md` в затрагиваемых папках** (если есть) — первичный источник по модулю.

Если пользователь дал описание задачи в сообщении — оно приоритетно; иначе брать из
`description.md`.

## Структура выходного файла

Результат: `second-brain/tasks/tasks/{NNN}-{описание}/plan.md`

План **на русском**, по структуре:

```markdown
# План реализации: {название задачи}

{Краткое описание цели — 2-3 предложения}

## 1. {Название шага}

**Файл (создать/изменить):** `src/.../file.ts`

{Что нужно сделать}

```typescript
// Пример кода
```

## 2. {Следующий шаг}
...

## N. Тесты

**Файл (создать):** `src/.../file.test.ts` (Vitest, environment `node`)

Сценарии:
- Основное поведение: ...
- Граничные случаи: ...

## N+1. Ручная проверка
Что запустить (`npm run dev`) и что увидеть на экране — для того, что не покрыть тестами.

## N+2. Обновление документации
Если план меняет то, что описано в `second-brain/architecture/`, `game-design.md`
или `README.md` затрагиваемой папки — обязательный шаг с обновлением (README —
на английском, second-brain — на русском).

## Сводка по файлам

| Действие | Файл |
|----------|------|
| Создать  | `src/.../file.ts` |
| Изменить | `src/.../existing.ts` |

## Архитектура и паттерны
Ключевые принципы из CLAUDE.md и кода, применённые в задаче.

## Ссылки
- analyze.md текущей задачи
- CLAUDE.md
- (другие релевантные документы)
```

## Требования к плану

- Каждый шаг — **конкретные пути файлов** и **примеры кода**.
- Соответствие конвенциям из `CLAUDE.md`: движок (`src/engine/`) не знает об игре,
  логика отделена от рендера, случайность через `Rng`, время через `dt`.
- Шаг с **тестами** на игровую логику.
- **Сводная таблица файлов** в конце — как чеклист для стадии `/do`.

## Большие задачи

Если задача велика для одного плана — разбить: `plan.md`, `plan-part2.md`, … В конце
каждой части указать, что продолжение в следующем файле.

## Заметки
- Ничего не реализовывать — только план.
- Не менять `analyze.md`.
- plan-implementation — вторая стадия конвейера (analyze → plan-implementation → do).
- Открытые вопросы из `analyze.md` — перенести в `## Открытые вопросы` плана, не выбирать умолчание молча.
- Перед сохранением проверить: у каждого шага есть конкретный путь и он исполним.
