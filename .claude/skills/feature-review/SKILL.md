# Ревью фичи

Цель: свежим взглядом проверить фичу, по которой основные вопросы уже обсуждены, и
найти упущенное:

1. **Открытые вопросы** — что не решено, хотя кажется решённым, или о чём забыли спросить.
2. **Несостыковки логики** — противоречия между решениями, между файлами фичи и
   `game-design.md`, устаревшие места.
3. **Соответствие коду** — файлы/функции/поля существуют и работают так, как написано;
   что всплывёт при реализации.

Ревью — поиск проблем, а не пересказ. Закрытые решения не подтверждать без аргумента
по существу.

## Аргументы

- `$ARGUMENTS`: номер фичи (`3`, `003`) — обязателен; после него — опциональный фокус.
- Без номера — спросить, показав последние фичи из `second-brain/features/README.md`.

## Порядок работы

### 1. Загрузить фичу целиком
- Найти `second-brain/features/{NNN}-*` (файл или папка). Не нашлась — остановиться.
- Прочитать **все** `.md` фичи, предыдущие ревью (`review*.md`) — закрытые пункты не
  поднимать без нового аргумента, открытые — перепроверить.
- Связанные задачи (`second-brain/tasks/`), ADR, разделы `game-design.md`.

### 2. Разобрать логику записей (до кода)
Список утверждений, на которые опираются решения («враг возвращается в строй на своё
место», «скорость пули 4 px/тик»…). Искать:
- противоречия между файлами и с `game-design.md`;
- устаревшие формулировки;
- непокрытые сценарии: смерть игрока во время пикирования, конец волны, пауза/потеря
  фокуса, много объектов одновременно, граница экрана, переход между сценами;
- незаданные вопросы, от которых зависит реализация (числа, тайминги, баланс).

### 3. Сверить с кодом
- Зафиксировать ветку и коммит (`git rev-parse --abbrev-ref HEAD`, `git log -1 --format=%h`).
- Проверить каждое утверждение по `src/`.
- Что всплывёт: тесты, которые сломаются; нарушение детерминизма; связность движка и
  игры; производительность на 60 тиках.
- Объёмную проверку можно распараллелить через субагентов `Explore`; их выводы с
  `file:line` перепроверить выборочно.

### 4. Записать отчёт
Если фича — папка: `review.md` в ней (повторно — `review-YYYY-MM-DD.md`). Если фича —
одиночный файл: `{NNN}-{name}.review.md` рядом (повторно — с датой).

```
# Ревью фичи — NNN (YYYY-MM-DD)

Что ревьюилось, по какому коду (ветка/коммит). Фокус, если задан.

Разделы: A — меняют решения (решает владелец), B — противоречия и неточности в
записях, C — что всплывёт при реализации, D — что подтвердилось.

## A. Меняют решения
### A1. <суть в одну строку>
Сценарий/доказательство с `path:line`, почему решение не работает, варианты.

## B. Противоречия и неточности в записях
1. **<тема>.** Где, в чём расхождение.

## C. Что всплывёт при реализации
- ...

## D. Подтвердилось
- ...
```

Правила: пункты A и C — с доказательством (`path:line`, цитата) или пометкой «не
проверено, предположение»; нумерация продолжает предыдущие ревью; пустой раздел —
«нет»; на русском, коротко.

### 5. Итог в чате
3–8 строк: сколько пунктов в A/B/C, суть каждого A, путь к отчёту. Добавить ссылку на
отчёт в раздел ссылок записи фичи. Статус и решения **не править** — это делает владелец.

## Важно

- Пункт в A — только при конкретном сценарии или факте из кода.
- Код не менять, не коммитить. Записи — только отчёт и строка-ссылка.
- Задачи не заводить; предложить `/new-task` можно.
