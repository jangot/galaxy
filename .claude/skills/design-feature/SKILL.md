# Проектирование фичи: архитектор ↔ разработчик

Цель: до постановки задач согласовать архитектуру фичи. Два агента с изолированным
контекстом обсуждают её через файлы в папке фичи:

- **architect** (`.claude/agents/architect.md`) — пишет и правит `design.md`,
  отвечает на замечания;
- **developer** (`.claude/agents/developer.md`) — сверяет дизайн с текущим кодом,
  пишет `dev-review*.md` с блокерами, рекомендациями и нарезкой на задачи.

Оркестратор (текущий агент) дизайн сам не пишет и код не меняет — только готовит
папку фичи, запускает раунды, решает, нужен ли следующий раунд, и приносит вопросы
владельцу.

Место в процессе: `/design-feature` → `/new-task` (по нарезке) → `/chain` …

## Аргументы

- **номер фичи** (`3`, `003`) → существующая запись в `second-brain/features/`;
  продолжить проектирование (новый раунд с учётом уже лежащих файлов).
- **описание** → новая фича; суть и требования берутся из описания и контекста чата.
- **пусто** → взять фичу из контекста чата; неясно — спросить.

## Шаг 0. Подготовка папки фичи

1. Прочитать `second-brain/features/README.md`, `second-brain/game-design.md`.
2. Новая фича:
   - номер — максимальный `№` в реестре + 1 (три цифры), имя — kebab-case на английском;
   - создать `second-brain/features/{NNN}-{name}/README.md`:

     ```markdown
     # Фича {NNN}: {название}

     **Статус:** проектирование

     ## Суть
     {что и зачем — по описанию и обсуждению}

     ## Требования
     {что проговорено: механика, управление, визуал, числа}

     ## Вне рамок
     {что сознательно не делаем сейчас, если обсуждалось}

     ## Файлы
     - design.md — архитектура (architect)
     - dev-review*.md — отзывы разработчика
     - discussion.md — ответы архитектора по пунктам

     ## Задачи
     {заполняется после нарезки}
     ```
   - добавить строку в таблицу `second-brain/features/README.md`.
3. Если суть фичи из описания неясна настолько, что проектировать нечего —
   **спросить владельца до запуска агентов**. Фиксировать только проговорённое.

## Как запускать агентов

Agent tool с `subagent_type: architect` / `subagent_type: developer`. Агенты не видят
чат — промпт самодостаточный: путь к проекту, путь к папке фичи, номер раунда, какой
файл писать, ответы владельца (если были).

Если такие типы агентов недоступны (сессия запущена до их создания) — запустить
`general-purpose` и первой строкой промпта: «Прочитай `.claude/agents/{architect|developer}.md`
и действуй в этой роли».

Сам `design-feature` выполняется в основной сессии (он запускает агентов и задаёт
вопросы владельцу), поэтому не объявлен как `context: fork`.

### Шаблон: architect, раунд 1

```
Проект Galaxy: /Users/jangot/Projects/private/galaxy. Папка фичи:
second-brain/features/{NNN}-{name}/.

Раунд 1. Спроектируй архитектуру фичи по её README.md и запиши в design.md этой
папки по структуре ниже. {Ответы владельца, если есть.}

Структура design.md:
# Дизайн: {название}
**Статус:** черновик | на ревью | согласовано · **Раунд:** N
## Цель и сценарии — что видит игрок, ключевые сценарии и крайние случаи
## Модули и файлы — таблица: модуль/файл → ответственность → новый/изменяемый
## Сущности и состояния — данные, конечные автоматы, переходы
## Поток тика — что и в каком порядке обновляется и рисуется
## Интерфейсы — ключевые TS-сигнатуры (без реализации)
## Тестирование — что покрывается тестами, что проверяется глазами
## Альтернативы — что рассматривал и почему отверг
## Открытые вопросы к владельцу
## Нарезка на задачи — порядок, каждая задача законченная и проверяемая
## История — раунд N: что изменилось

В конце ответа — резюме: что сделал, сколько вопросов к владельцу.
```

### Шаблон: developer, раунд N

```
Проект Galaxy: /Users/jangot/Projects/private/galaxy. Папка фичи:
second-brain/features/{NNN}-{name}/.

Режим: ревью дизайна (design-feature).

Раунд {N}. Прочитай design.md (и discussion.md, прошлые dev-review*.md, если есть),
сверь с текущим кодом src/ и запиши отзыв в {dev-review.md | dev-review-N.md} по
формату из своей роли. На пункты, закрытые в discussion.md, не возвращайся без
нового аргумента.

В конце ответа — резюме: число блокеров / рекомендаций / вопросов.
```

### Шаблон: architect, раунд N > 1

```
Проект Galaxy: /Users/jangot/Projects/private/galaxy. Папка фичи:
second-brain/features/{NNN}-{name}/.

Раунд {N}. Прочитай свежий отзыв разработчика {dev-review-*.md}. {Ответы владельца,
если есть.}
1. В discussion.md добавь раздел «Раунд {N}»: по каждому пункту отзыва — принято
   (что изменил) / отклонено (почему) / к владельцу.
2. Обнови design.md: внеси принятое, обнови «Открытые вопросы», «Нарезку», «Историю»,
   поставь статус «на ревью».

В конце ответа — резюме: сколько принято / отклонено / к владельцу.
```

## Шаг 1. Раунды

1. **architect, раунд 1** → проверить, что `design.md` появился.
2. **developer, раунд 1** → `dev-review.md`.
3. Прочитать отзыв и решить:
   - **нет блокеров и вопросов к архитектору** → к шагу 2;
   - иначе → **architect, раунд N+1** (ответ + правка дизайна), затем
     **developer, раунд N+1** (`dev-review-N.md`), снова решить.
4. **Не больше 3 раундов.** Если после 3-го блокеры остались — значит, спор упёрся в
   решение, которое должен принять владелец: вынести его как вопрос (шаг 2).
5. Если архитектор отклонил блокер, а разработчик в следующем раунде настаивает с тем
   же аргументом — не крутить дальше, вынести владельцу обе позиции.

Агенты пишут только в папку фичи. Если агент изменил что-то в `src/` — сообщить
владельцу и остановиться.

## Шаг 2. Вопросы владельцу

Собрать из `design.md` («Открытые вопросы к владельцу») и последнего отзыва
(«Вопросы → К владельцу»), плюс неразрешённые споры. Задать через `AskUserQuestion`
(до 4 вопросов за раз, у каждого — варианты из дизайна, рекомендуемый первым; вопрос
самодостаточный — владелец не видит файлов в этот момент).

Ответы → **architect, следующий раунд** с ответами в промпте (он фиксирует их в
`design.md` и `discussion.md`). Если ответы меняют архитектуру существенно —
ещё один раунд developer. Решения по геймдизайну — предложить внести в
`second-brain/game-design.md` (с согласия владельца).

Нет вопросов — к шагу 3.

## Шаг 3. Завершение

1. Статус в `design.md` → «согласовано»; в README фичи и в реестре
   `features/README.md` → «спроектирована».
2. Если дизайн меняет общую архитектуру (новый слой, новый принцип) — предложить
   владельцу ADR в `second-brain/decisions/` и правку `second-brain/architecture/`.
3. Отчёт в чат (коротко):
   - суть архитектуры в 3–6 пунктах;
   - сколько было раундов, что ключевого поменялось после замечаний разработчика;
   - принятые решения владельца;
   - нарезка на задачи (из `design.md`);
   - путь к папке фичи.
4. Предложить завести задачи по нарезке через `/new-task` — не создавать самому.

## Заметки

- Код не меняется, коммиты не делаются.
- Повторный запуск с номером фичи — продолжение: новый раунд поверх существующих
  файлов, нумерация отзывов продолжается.
- Для мелких фич, где архитектуры почти нет, достаточно одного раунда — не гонять
  агентов ради формальности.
