# Прогон всех задач фичи

Цель: без участия владельца довести все задачи фичи до реализованного состояния.
Владелец не следит за процессом и заходит время от времени — поэтому вопросы
разработчика сначала идут архитектору, а владельцу приходят только решения по
геймдизайну/вкусу, которые архитектор закрыть не может.

Оркестратор (основная сессия) сам код не пишет и дизайн не правит — запускает
агентов, проверяет результат по файлам и прогоняет проверки. Скил выполняется в
основной сессии (не `context: fork`): он запускает агентов и задаёт вопросы владельцу.

## Аргументы

- `$ARGUMENTS` — номер фичи (`2`, `002`). Обязателен. Без номера — сообщить и
  остановиться.

## Подготовка

1. Найти запись фичи в `second-brain/features/README.md`, открыть её `README.md` и
   `design.md`. Нет `design.md` со статусом «согласовано» — предложить
   `/design-feature` и остановиться.
2. Список задач — раздел «Задачи» README фичи, **в указанном порядке**. Для каждой —
   найти папку в `second-brain/tasks/tasks/` или `tasks-done/`.
3. Пропустить задачи:
   - лежащие в `tasks-done/`;
   - с файлом `acceptance.md` в папке (код готов, ждёт приёмки владельцем — см. ниже).
4. Задач для прогона нет — сообщить и остановиться.
5. Ветка: если текущая — `main`, создать `feature/{NNN}-{name}` (имя папки фичи).
   Коммиты не делать — только по явной просьбе владельца (`/commit`).
6. Перевести статус фичи в «в работе» (README фичи и реестр).

## Запуск шагов developer

Рабочие скилы объявлены с `context: fork`, но при вызове через `Skill` tool аргументы
до форкнутого агента **не доходят** (агент сам выбирает задачу). Поэтому каждый шаг
запускать **через Agent tool** (`subagent_type: developer`) с явным промптом:

```
Выполни скил `{skill}` проекта для задачи **{NNN}** (папка `{путь к папке задачи}`).
Инструкции — в `.claude/skills/{skill}/SKILL.md`; прочитай и следуй им, считая
аргументы скила равными `{NNN}{ ответы, если перезапуск}`.
Контекст фичи: `second-brain/features/{NNN}-{name}/` (design.md, discussion.md).
{Для analyze: предыдущие задачи фичи реализованы в рабочем дереве (не закоммичены) —
опирайся на реальный код.}
{Для do: ручную проверку в браузере не выполняй — перечисли, что проверить владельцу.
Если закрытие задачи требует приёмки владельцем глазами — НЕ переноси её в tasks-done,
а создай в папке задачи `acceptance.md` (что именно утвердить и как проверить).}
Не коммить. Запись фичи в `second-brain/features/` не трогай.
{Ответы на вопросы (если перезапуск): ...}

Верни итог со статусом SUCCESS / NEEDS_INPUT (с разделом «Вопросы владельцу») /
FAILURE{, для do — результат проверок format:check, lint, typecheck, test, build}.
```

Шаги строго последовательны, следующая задача — только после завершения предыдущей.

## Конвейер одной задачи

1. **analyze** → проверить, что `analyze.md` появился. Открытые вопросы в нём,
   влияющие на реализацию, — как NEEDS_INPUT.
2. **plan-implementation** → проверить `plan.md`.
3. **do** → по итогу самому прогнать проверки:
   `npm run format:check && npm run lint && npm run typecheck && npm test && npm run build`.
4. **fix-tests** — только если проверки упали. После — проверки ещё раз.
5. Задача завершена, если проверки зелёные и задача в `tasks-done/` **или** в её папке
   есть `acceptance.md`. Перейти к следующей.

Статусы шагов:

- **SUCCESS** → следующий шаг;
- **NEEDS_INPUT**, открытые вопросы в `analyze.md`, выход за рамки задачи →
  **разбор вопросов** (ниже), затем перезапустить тот же шаг с ответами;
- **FAILURE** / проверки падают после fix-tests → **обработка ошибок**.

## Разбор вопросов: сначала архитектор

1. Собрать вопросы developer (раздел «Вопросы владельцу» итога, открытые вопросы
   `analyze.md`/`plan.md`, сообщение о выходе за рамки).
2. Запустить **architect** (Agent tool, `subagent_type: architect`):

   ```
   Проект Galaxy: /Users/jangot/Projects/private/galaxy. Фича:
   second-brain/features/{NNN}-{name}/ (design.md согласован). Идёт реализация задачи
   {NNN-task} (second-brain/tasks/tasks/{NNN-task}/), шаг {skill}. Разработчик
   остановился с вопросами:

   {вопросы дословно, с вариантами}

   Ответь на каждый в рамках дизайна и решений владельца (design.md, discussion.md,
   second-brain/game-design.md). Для каждого: **решено** (ответ и почему) или
   **к владельцу** — только если это решение по геймдизайну/вкусу, которое нельзя
   разумно принять архитектурно (с вариантами и рекомендацией первым).
   Запиши разбор в discussion.md фичи (раздел «Реализация: задача {NNN-task}»); если
   ответ меняет дизайн — обнови design.md (и «Историю»). Код в src/ не трогай.

   В конце — список: вопрос → решено (ответ кратко) / к владельцу.
   ```

3. Всё «решено» → перезапустить шаг developer с ответами архитектора в промпте.
4. Есть «к владельцу» → задать через `AskUserQuestion` (самодостаточно: владелец не
   видит файлов; до 4 вопросов за раз; варианты архитектора, рекомендуемый первым).
   Ответы владельца → architect фиксирует их в `discussion.md`/`design.md` (короткий
   запуск) → перезапуск шага developer с ответами.
5. Если developer после ответов архитектора снова упирается в тот же вопрос с новым
   аргументом — ещё один раунд с архитектором (обе позиции в промпте). Не больше
   **2 раундов** на вопрос; дальше — владельцу обе позиции.
6. Выход за рамки задачи, который архитектор подтвердил как нужный, — к владельцу:
   предложить отдельную задачу (через `/new-task`), не расширять текущую.

## Приёмка глазами не блокирует конвейер

Утверждение спрайтов/анимаций/ощущения владельцем — не вопрос для архитектора и не
повод останавливаться. Задача с `acceptance.md` считается реализованной, конвейер идёт
дальше. Все приёмки собрать в итоговый отчёт. Когда владелец утвердит — перенести
задачу в `tasks-done/`, убрать `acceptance.md` и пометку в «Открытых вопросах»
`description.md`. Не утвердил — правка отдельным прогоном `do` с замечаниями.

## Обработка ошибок

1. Создать `{папка задачи}/error.md` (формат как в скиле `chain`: шаг, дата, описание,
   статус шагов ✅/❌/⏭).
2. Остановить прогон фичи (следующие задачи зависят от текущей). Сообщить владельцу:
   задача, шаг, причина, путь к `error.md`, какие задачи уже готовы.

Повторный запуск `/feature-chain {NNN}` продолжит с первой незавершённой задачи.

## Завершение

1. Обновить README фичи: ссылки задач на `tasks-done/`, статус — «готова», если
   приёмок нет, иначе «в работе — ждёт приёмки»; то же в реестре
   `features/README.md`. Прогнать `npx prettier --write` по изменённым файлам.
2. Отчёт владельцу (коротко):
   - по каждой задаче — одна строка: что сделано, тестов всего;
   - какие вопросы возникали и как решены (архитектором / владельцем);
   - список приёмок глазами: задача → что утвердить → как проверить
     (`npm run dev`, при необходимости `?level=N` и т. п.);
   - предложить `/commit`.

## Важно

- Код пишет только developer, дизайн правит только architect.
- Коммиты — только по явной просьбе владельца.
- Если агент изменил то, что ему не положено (architect — `src/`, developer — запись
  фичи), сообщить владельцу и остановиться.
