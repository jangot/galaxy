# Анализ: Движение корабля

## Общее описание функциональности

Третья задача фичи 001 (пункт 3 нарезки `design.md`). После задач 001–002 игровая
сцена показывает звёзды и неподвижный корабль по центру внизу. В этой задаче корабль
начинает ездить влево-вправо:

- зажата «влево» (← / A) или «вправо» (→ / D) — корабль едет с постоянной скоростью
  120 px/с = ровно 2 px/тик (решение владельца В1);
- отпустил — встал в этом же тике, инерции нет;
- зажаты обе стороны — стоит;
- у края экрана упирается: позиция зажата в `[0, SCREEN_WIDTH - SHIP_WIDTH]` = `[0, 241]`;
  шаг, который вывел бы за край, обрезается ровно до края (у края нет дрожания);
- потеря фокуса окна — `Input` уже очищает зажатые клавиши на `blur`
  (`src/engine/input.ts:37`), корабль останавливается сам.

Управление идёт не из `Input` напрямую, а через намерение игрока `PlayerIntent`
(`{ move, fire }`), которое получается функцией `readIntent(input)`. Появляется агрегат
`Player` — пока содержит только корабль; выстрел добавит задача 004. Ощущение — ровное
движение без подёргивания: шаг целый (ADR 002), поэтому `Math.floor` при отрисовке
ничего не «перещёлкивает».

## Модели данных и состояние

**Ship** (`src/game/ship.ts`, уже есть с задачи 002):

| Поле / константа   | Значение                                                                      | Статус                |
| ------------------ | ----------------------------------------------------------------------------- | --------------------- |
| `x`                | `number`, старт `floor((256 − 15) / 2)` = 120                                 | есть, теперь меняется |
| `y`                | `readonly`, `SHIP_Y = 208`                                                    | есть                  |
| `SHIP_WIDTH`       | `= SHIP_SPRITE.width` = 15                                                    | есть                  |
| `SHIP_HEIGHT`      | `= SHIP_SPRITE.height` = 16                                                   | есть                  |
| `SHIP_SPEED`       | `120` px/с (2 px/тик)                                                         | **новая**             |
| `MoveDir`          | тип `-1 \| 0 \| 1`                                                            | **новый**             |
| `update(dt, move)` | `x += move * SHIP_SPEED * dt`, затем зажим в `[0, SCREEN_WIDTH - SHIP_WIDTH]` | **новый**             |

Автомата состояний у корабля нет (всегда «активен»); `state` появится в фиче смерти.

**PlayerIntent** (`src/game/player.ts`, новый): `{ move: MoveDir; fire: boolean }`.
`readIntent(input)`: `move = (isDown('right') ? 1 : 0) − (isDown('left') ? 1 : 0)`,
`fire = input.pressed('fire')` (edge — решение В5). В этой задаче `fire` вычисляется,
но `Player` его ещё не использует — это нормально, его подхватит 004 (в `analyze.md`
задачи 004 так и предполагается).

**Player** (`src/game/player.ts`, новый): `readonly ship: Ship`, `constructor(ship?)`
(по умолчанию `new Ship()`), `update(dt, intent)` — пока только
`ship.update(dt, intent.move)`. Поле `shot` и геттер — задача 004.

**Численные инварианты** (проверены в дизайне и dev-review-2):
`120 * (1/60) === 2` в double; старт 120 и края 0 / 241 целые → `x` всегда целое,
сравнения в тестах — `toBe`. От края до края ≈ 121 тик ≈ 2 с.
`new Ship(1)` + `move=-1` → `-1` → зажим `0`; `new Ship(240)` + `move=1` → `242` → `241`.

## Точки встраивания

- **Цикл обновления.** `PlayScene.update(dt, input)` (сейчас
  `src/game/scenes/play-scene.ts:22-24`, параметр `_input` не используется): после
  `starfield.update(dt)` — `player.update(dt, readIntent(input))`. Параметр
  переименовать `_input` → `input`. `main.ts` и `engine` не меняются: `dt` приходит
  как `TICK_SECONDS`, `endTick()` вызывается после `update`.
- **Ввод.** Новых действий не нужно: `left`/`right`/`fire` с раскладкой
  ←/A, →/D, Space/Z уже есть в `DEFAULT_BINDINGS` (`src/engine/input.ts:3-15`).
  Чтение `Input` — только в `readIntent`; `Player`/`Ship` про клавиатуру не знают.
  В `player.ts` `Input` — через `import type`.
- **Отрисовка.** `PlayScene.render` рисует `drawSprite(ctx, SHIP_SPRITE,
floor(ship.x), floor(ship.y))` (`play-scene.ts:30`) — меняется только источник:
  `this.player.ship` вместо `this.ship`. Порядок слоёв не меняется.
- **Публичное поле сцены.** Сейчас `PlayScene` открывает для тестов `readonly ship`
  (`play-scene.ts:13`); по дизайну («Интерфейсы») — `readonly player: Player`. Поле
  `ship` заменяется на `player`, тесты обращаются к `scene.player.ship`.
- **HUD** — не затрагивается.

Граф импортов после задачи: `play-scene → {starfield, player, art, sprite}`,
`player → ship` (+ `import type` `Input`), `ship → {config, art}`. Прямой импорт `ship`
из `play-scene` больше не нужен (позиция берётся через `player.ship`). Циклов нет.

## Тестируемость

Всё поведение задачи — чистая логика, покрывается Vitest без canvas:

- **`ship.test.ts`:** инвариант правила скоростей
  `Number.isInteger(SHIP_SPEED * TICK_SECONDS)` (ADR 002); один тик `move=1` — сдвиг
  ровно на `SHIP_SPEED * TICK_SECONDS`, `move=-1` — на столько же влево, `move=0` —
  стоит; зажим — прямой установкой: `new Ship(1)` + `move=-1` → `0`,
  `new Ship(SCREEN_WIDTH - SHIP_WIDTH - 1)` + `move=1` → `SCREEN_WIDTH - SHIP_WIDTH`;
  «упёрся и стоит»: от края ещё несколько тиков в ту же сторону — позиция не меняется;
  `y` не меняется при движении. Числа — через экспортируемые константы.
- **`player.test.ts`:** `readIntent` через реальный `Input` (`press`/`release`/`endTick`):
  только `left` → `-1`, только `right` → `1`, обе → `0`, ничего → `0`; `fire` — `true`
  в тике нажатия и `false` при удержании после `endTick()`. `Player.update` с
  интентом-литералом двигает `player.ship`; `fire: true` в 003 ни на что не влияет
  (явно не тестировать — поведение придёт в 004).
- **`play-scene.test.ts`** — только через `step()`: зажать «вправо» N тиков → сдвиг
  `N * SHIP_SPEED * TICK_SECONDS`; зажать обе → стоит; `release` → в следующем тике
  стоит; долгое удержание (например, 200 тиков) → ровно у правого края.
- **Только глазами (`npm run dev`):** плавность без подёргивания, корабль упирается в
  края без дрожания, остановка сразу при отпускании, остановка при уходе фокуса окна.

## Зависимости и ограничения

- **Зависимость от 002** выполнена: `Ship`, `SHIP_WIDTH` из спрайта, `PlayScene` с
  отрисовкой корабля, `step()` есть в рабочем дереве. Ожидающее утверждение вида
  корабля (В7) на 003 не влияет: движение зависит только от `SHIP_WIDTH`, который
  выводится из спрайта и закреплён тестом 15×16.
- **Если спрайт перерисуют с другой шириной** — правый край зажима сдвинется
  автоматически (через `SHIP_WIDTH`); тесты зажима, написанные через константы, не
  сломаются.
- **Фиксированный шаг:** `dt` всегда `TICK_SECONDS`; при долгой паузе вкладки
  `accumulate()` ограничивает число тиков, а зажим не даёт уйти за край.
- **Детерминизм:** `Rng` в движении не участвует; время — только через `dt`.
- **Конвенции:** `import type` для `Input` в `player.ts`; неиспользуемых параметров
  не остаётся (`_input` в `PlayScene.update` становится используемым).
- **Производительность:** одна сущность, несколько операций за тик — не фактор.
- **Риск:** если в `Ship.update` зажим сделать до прибавления шага или через
  «не двигаться, если выйдет за край», корабль остановится в 1 px от края при
  нечётном остатке; дизайн требует именно «обрезать шаг до края» — тесты на
  `x = 1` / `x = 240` это ловят. (При старте 120 и шаге 2 нечётных остатков не
  бывает, поэтому тесты прямой установкой обязательны.)
