# Анализ: Инерция striker

Задача 016 (номер — из промпта запуска). Рамка — согласованный `design.md` фичи 003
(раунд 2, пункт 3 нарезки). Анализ опирается на рабочее дерево с реализованными 014 и 015
(не закоммичены). Все числа ниже я проверил прогоном настоящего `Enemy`/`Battle`/`Wave` с
`turnTicks: 8` в копии дерева во временной папке; `src/` проекта не менялся.

## Общее описание функциональности

`striker` по-прежнему берёт цель (центр корабля) каждый тик, но боковая скорость `vx`
меняется с инерцией: на 1 px/тик за `STRIKER_TURN_TICKS = 8` тиков. Что видит игрок:

- после дуги вылета `striker` продолжает её боковое движение (дуга плавно переходит в пике),
  потом разворачивается к кораблю;
- на развороте корабля враг ещё 7 тиков летит прежним курсом (проскок), 8 тиков «стоит» по X,
  и только потом догоняет. Финт работает: корабль уходит на `5T − 3 = 37` px относительно
  врага;
- над стоящим кораблём враг «виляет» с размахом ≤ `T − 1 = 7` px, так что таран всё равно
  почти наверняка — стоя на месте не уйти;
- когда корабль сбит (`targetX = null`), боковой ход гаснет за ≤ `T` тиков, а не сразу.

Модель (`steering.ts`, `descend` в `enemy.ts`) уже реализована в 014. Задача 016 меняет одно
число в профиле `striker` и переписывает тесты, которые полагались на мгновенный разворот.

| --------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |

| `ENEMY_KINDS.striker.steer` | `{ retargetTicks: 1, turnTicks: 0, maxVx: 1 }` | `{ retargetTicks: 1, turnTicks: STRIKER_TURN_TICKS, maxVx: 1 }` |
| `drone`, `raider`           | `{30, 0, 1}`, `{null, 0, 1}`                   | без изменений                                                   |

Правила тика `descend` (`enemy.ts:225-247`) не меняются. Ниже то, что получается из них при
`T = 8` (проверено на настоящем `Enemy`, `newEnemyOf('striker')`, `side = +1`, после дуги
`x = 127`, цель 0):

- `d = 1`: `vx = +1` (продолжение дуги), `x = 128`;
- `d = 1…7`: `vx = +1` (проскок 7 px, до `x = 134`); `d = 8…15`: `vx = 0`; с `d = 16`:
  `vx = −1`. Это ровно раскладка `T − 1` / `T` / дальше, как в дизайне;
- стена (настоящий проскок, без искусственного заказа): цель 0 → `aimFor` зажимает её в
  центр 6 (`x = 0`); враг доходит до `x = 0` с `vx = −1` (`d = 149`); в следующем тике
  `desired = 0`, инерция ещё держит `vx = −1`, `x` уходит в −1 → зажим → `vx = 0`,
  `turnCounter = 0` (`d = 150`). Без правила стены `vx` держался бы на −1 ещё 6 тиков.
  Зеркально справа (цель 255, `side = −1`): `x = 243 = SCREEN_WIDTH − 13`, `vx = +1 → 0`
  (`d = 166/167`). При `diveSpeed 60` враг к этому моменту ещё в `diving`. Тест можно
  сократить: поставить `x` у стены, когда `vx` уже направлен туда;
- `targetX = null` (Battle, «no target while down»): в `d = 1` `vx = −1` (дуга, `side = −1`),
  после `hit()` `x` меняется ещё 6 тиков, потом стоит (≤ `T`);
- стоящий корабль (Battle aim, `S` в колонке 0 из 11): разница центров на `d = 150…164`
  лежит в [−6,75; 6,25] (дробная часть — от покачивания слота), на `d = 160` она 2,25;
  на `d ≈ 165` — таран, враг уходит в `exploding`.

## Тестируемость

Всё проверяется юнит-тестами без canvas: `Enemy.update(TICK_SECONDS, { diveSpeed, targetX })`
с `targetX` от теста, детерминированно (без `Rng`).

1. **Тесты инерции `striker` (`enemy.test.ts`)** — по критериям `description.md`:
   - продолжение дуги: `d = 1` → `vx = side · 1` при любой цели (и при `side = −1`);
   - раскладка разворота: `vx` по тикам `d = 1…7` = +1, `8…15` = 0, с `16` = −1 (цель с
     другой стороны); выражать через `STRIKER_TURN_TICKS`;
   - виляние у стоящей цели: после подхода `|центр − цель| ≤ T − 1` на всех следующих тиках
     и знак `vx` меняется (виляние есть);
   - затухание при `null`: `vx` → 0 не позже чем за `T` тиков и дальше держится 0;
   - стена: настоящий проскок (см. «Модели данных»), без несогласованного заказа.
2. **Механические тесты «Enemy aim»** (дизайн: перенос на `drone` / `steering.test.ts`, без
   подгонки под инерцию). Пробный перенос на `drone` показал:
   - «Y step at 60/120» — проходит на `drone` как есть (`x − 1` каждый тик);
   - «does not jitter», «stays on screen at the edge» — на `drone` работают, но меняются
     **геометрические** литералы: `drone` 11 px (центр `x + 5`, после дуги `x = 128`),
     `striker` 13 px (центр `x + 6`, `x = 127`). Окна теста (71 и 10 тиков) пересекают
     переприцеливания `d = 31, 61`, но цели в этих тиках те же — поведение не меняется.
     Это пересчёт геометрии, а не подгонка под инерцию;
   - «measures the gap from the center of its own sprite» сравнивает два вида разной
     ширины. Без `striker` вторым видом подходит `raider` (13 px, цель в 1-м тике,
     `turnTicks = 0`): на 5 тиках он ведёт себя как старый `striker` с теми же ожиданиями;
   - «track follows the target of every tick» на `drone` невозможен (цель держится 30 тиков).
     По дизайну «каждый тик» — в `steering.test.ts`: мини-симуляция (`isRetargetTick` →
     `desiredVx` → `turn` → `x += vx`) с профилем `{1, 0, 1}`, тот же сценарий целей.
     Этот же хелпер нужен для контроля уходимости (п. 5).
3. **«Enemy vx» из 014** (в перечне дизайна их нет — см. «Открытые вопросы», п. 2): они
   проверяют геттер `vx`, а не руление.
   - «is 0 after leaving past the bottom», «is 0 after kill()» — перевести на `drone`
     (`aimAt(0)` → `vx = −1` в `d = 1`, ожидания те же);
   - «in descend equals the actual x shift» — проверять свойство «`x − x_prev === vx`»
     на `striker` по последовательности целей 0/250/null без жёстких значений `vx`
     (или на `drone` с переприцеливаниями). Свойство на `striker` с инерцией ценнее;
   - «hitting the … edge zeroes vx» — заменить на настоящий проскок `striker` у обоих
     краёв (заметка из `plan.md` 014).
4. **Battle / Wave** — см. таблицу файлов; числа проверены (Battle aim: на `d = 160`
   разница 2,25, враг ещё `diving`; «down»: стабилен через 6 тиков).
5. **Сценарий уходимости.** Мой скрипт: `striker` после дуги (`side = +1`, `vx = +1` в
   `d = 1`), центр корабля на 27 px правее центра врага, корабль бежит вправо 2 px/тик
   с `d = 1`, разворачивается, когда `y` врага ≥ `turnY`; таран — `overlaps` с
   прямоугольником корабля (`SHIP_Y`, `SHIP_WIDTH`, `SHIP_HEIGHT`); «стоит» — корабль не
   двигается. Результаты:

   | `diveSpeed` | `turnY` | стоит, `T = 8` | финт, `T = 8`              | финт, `T = 0`     |
   | ----------- | ------- | -------------- | -------------------------- | ----------------- |
   | 180         | 110     | таран          | мин. 35 px                 | разошлись (14 px) |
   | 180         | 120     | таран          | **разошлись (24 px)**      | **таран**         |
   | 180         | 125     | таран          | разошлись (21 px)          | таран             |
   | 180         | 130     | таран          | разошлись (14 px, впритык) | таран             |
   | 120         | 120     | таран          | разошлись (39 px)          | разошлись (17 px) |
   | 120         | 130     | таран          | **разошлись (29 px)**      | **таран**         |
   | 120         | 135     | таран          | разошлись (23 px)          | таран             |
   | 120         | 140     | таран          | разошлись (19 px)          | таран             |
   | 120         | 150     | таран          | таран                      | таран             |

   «Окно» (финт с `T = 8` уходит, с `T = 0` — таран): `diveSpeed 180` → `turnY` 120–130,
   `diveSpeed 120` → 130–140. **Одна высота на обе скорости не годится с запасом:** при 120
   и `turnY = 120` контроль `T = 0` тоже уходит. Значит, высота разворота задаётся по
   скорости (рекомендую 120 для 180 и 135 для 120 — середины окон) или как `y` с запасом
   от `SHIP_Y` в тиках. Стоящий корабль — таран во всех случаях. Мин. расстояния — между
   центрами в тиках, когда враг на высоте корабля (для разведки, в тест не обязательно).

   Контроль `T = 0` — в `steering.test.ts` на мини-симуляции (подменить `T` в `Enemy`
   нельзя, профиль из константы); там нужно повторить зажим `x` и правило стены, а также
   стартовые `x`, `y`, `vx` врага (`vx` дуги в `d = 1`). Импорт `overlaps`, `SHIP_*` и
   `STRIKER_SPRITE` — только в тесте; `steering.ts` без импортов. На настоящем `Enemy` —
   «стоит → таран» и «финт → разошлись».

Только глазами: «опасен, но уходится финтом», плавность перехода дуги в пике, слабость
фланговых `striker` (уровни 2 и 5).

## Зависимости и ограничения

- Зависит от 014 (модель есть в рабочем дереве). С 015 независима, но правит те же места:
  тест профилей (`enemy.test.ts:448`), абзац «Пикирование» в `game-design.md:30-36`,
  строку профилей в `overview.md:117`, комментарий `battle.ts:64-65`. 015 тоже не закоммичена,
  так что правки идут поверх её текста; при раздельных коммитах — следить за порядком.
- Окна механических тестов на `drone` должны укладываться в `N = 30` тиков или давать ту же
  цель на переприцеливаниях (проверено для «does not jitter»).
- «Battle aim»: запас до тарана — ≈ 4 тика (`d = 160` проверка, таран ≈ `d = 165`). Таран
  зависит от вертикали (не от `T`), поэтому запас стабилен, но удлинять прогон дальше 160
  нельзя.
- Разрешение 256×240, 60 тиков/с; X в `descend` — целые px/тик без `dt` (ADR 002/003);
  производительность не затронута (два числа состояния на врага).
- Риск приёмки: фланговые `striker` ослаблены продолжением дуги (принято, В2); запасной
  вариант — старт `descend` с `vx = 0` (одна строка в `descend`, `d === 1`), тест
  продолжения дуги тогда меняется.

## Открытые вопросы

Вопросов к владельцу нет (числа и поведение утверждены: В2). Уточнения, где дизайн
расходится с кодом, — с рекомендацией (решаются в плане, при сомнении — архитектор):

1. **`wave.test.ts`: переход на `D` сам по себе не чинит тест.** Тест подаёт `0` в `d = 1`
   (`x − 1`), затем `null` в `d = 2` и ждёт, что `x` не изменится. `drone` во 2-м тике не
   переприцеливается, держит цель 0 и сдвигается ещё на 1 (проверено: `−1`, затем `−2`).
   Рекомендация: проверять `null` на тике прицеливания — например, две волны с одним
   сидом: одной в `d = 1` подать `0` (`x − 1`), другой `null` (`x` не меняется; `drone` без
   цели летит прямо вниз). Вариант: одна волна, `null` в `d = 1 + N`.
2. **Четыре теста «Enemy vx» из 014 в перечне дизайна не названы, но падают.** Это проверки
   геттера `vx`, не инерции. Рекомендация — как в «Тестируемости», п. 3: «bottom»/«kill»
   на `drone`, «x shift» — свойство на `striker`, стена — настоящий проскок.
3. **«track follows the target of every tick» нельзя перенести на `drone`.** Рекомендация:
   мини-симуляция в `steering.test.ts` с профилем `{1, 0, 1}` (дизайн это допускает:
   «проверки "каждый тик" — на `steering.test.ts`»).
4. **«measures the gap from the center of its own sprite»** — второй вид вместо `striker`:
   рекомендую `raider` (13 px, цель в 1-м тике).
5. **Высота разворота в сценарии уходимости** — по скорости (180 → `y` 120, 120 → `y` 135),
   а не одна на обе (см. таблицу).

Вынести в отдельную задачу — нечего.
