# Анализ: Спрайты и корабль на месте

## Общее описание функциональности

Вторая задача фичи 001 «Корабль игрока». После задачи 001 по Enter открывается
игровая сцена `PlayScene`, но на ней только звёзды. Эта задача даёт:

1. **Модуль спрайтов** (`src/game/sprite.ts`) — формат пиксель-арта «массив строк +
   палитра», чистый разбор `parseSprite()` и отрисовка `drawSprite()` попиксельно
   через `fillRect`. Это основа для всех будущих спрайтов (враги, иконки жизней).
2. **Данные арта** (`src/game/art.ts`) — `SHIP_SPRITE` 15×16: свой оригинальный
   силуэт, 2–3 цвета, 8-битный стиль.
3. **Неподвижный корабль** (`src/game/ship.ts`, `Ship`) — стоит по центру по X, верх
   на `y = 208`. Размеры выводятся из спрайта.
4. **Отрисовка корабля** в `PlayScene` поверх звёзд.

Как выглядит в игре: титул → Enter → звёздный фон, внизу по центру стоит корабль.
Пиксели чёткие (масштабирование экрана уже целочисленное, `src/engine/screen.ts`).
Корабль пока не двигается и не стреляет — это задачи 003 и 004. **Вид корабля
владелец утверждает глазами** (решение В7) — это критерий готовности задачи, а не
вопрос к анализу: вид выбирается разработчиком на стадии plan/do.

Рамка — согласованный `second-brain/features/001-player-ship/design.md` (раунд 2,
пункт 2 нарезки; разделы «Сущности и состояния» → Ship, «Поток тика» → render,
«Интерфейсы», «Тестирование»). Анализ уточняет его по коду и не перепроектирует.

## Модели данных и состояние

**Sprite** (`src/game/sprite.ts`, новый) — интерфейс из дизайна:

| Поле     | Тип                           | Примечание                                                 |
| -------- | ----------------------------- | ---------------------------------------------------------- |
| `width`  | `number`                      | длина строки                                               |
| `height` | `number`                      | число строк                                                |
| `pixels` | `readonly (string \| null)[]` | row-major: индекс `row * width + col`; `null` — прозрачный |

**Входной формат `parseSprite(rows, palette)`:**

- `rows` — строки одинаковой длины; символ `.` — прозрачный пиксель; любой другой
  символ — ключ палитры.
- `palette` — `Record<string, string>`: символ → CSS-цвет.
- Ошибки (бросает исключение): пустой массив строк; строки разной длины; символ, которого
  нет в палитре. Дополнительно стоит решить в plan (см. «Зависимости и ограничения»):
  нулевая ширина (`['']`) и ключ `.` в палитре.

**SHIP_SPRITE** (`src/game/art.ts`, новый):

| Параметр | Значение                        | Источник                                           |
| -------- | ------------------------------- | -------------------------------------------------- |
| Размер   | 15×16 (ширина × высота)         | В3                                                 |
| Цвета    | 2–3 непрозрачных + прозрачность | В7                                                 |
| Нос      | центральный столбец (col 7)     | нечётная ширина; нужен в 004 для `muzzleX = x + 7` |
| Силуэт   | свой, не копия референса        | CLAUDE.md, В7                                      |

`SHOT_COLOR` в `art.ts` в эту задачу **не входит** — он появляется в задаче 004
(пункт 4 нарезки).

**Ship** (`src/game/ship.ts`, новый) — в этой задаче без движения:

| Поле / константа  | Значение                    | Примечание                                                |
| ----------------- | --------------------------- | --------------------------------------------------------- |
| `SHIP_WIDTH`      | `= SHIP_SPRITE.width` (15)  | выводится из спрайта, не литерал                          |
| `SHIP_HEIGHT`     | `= SHIP_SPRITE.height` (16) | выводится из спрайта                                      |
| `SHIP_Y`          | `208`                       | В6; низ корабля на 224, под ним 16 px под HUD жизней      |
| `x`               | `number`, мутабельное поле  | старт `Math.floor((SCREEN_WIDTH - SHIP_WIDTH) / 2)` = 120 |
| `y`               | `readonly`, `= SHIP_Y`      |                                                           |
| `constructor(x?)` | по умолчанию — центр        | параметр нужен тестам задач 003/004                       |

Не входят в задачу (по нарезке дизайна): `SHIP_SPEED`, `MoveDir`, `Ship.update` —
задача 003; `spawnShot()` — задача 004. Автомата состояний у корабля нет.

Позиция — левый верхний угол (система координат дизайна). Координаты в этой фиче
целые (ADR 002), при отрисовке всё равно `Math.floor` — как в `Starfield.render`.

## Точки встраивания

- **Сцена:** `PlayScene` создаёт `Ship` в конструкторе (без аргументов — центр).
  `Ship` в этой задаче живёт прямо в сцене; в задаче 003 его заменит `Player`
  (`readonly player: Player`, корабль — `player.ship`). Чтобы сцену можно было проверить
  в тестах и чтобы 003 переделывал минимум, поле корабля в сцене — публичное
  `readonly` (как `player` в дизайне, «exposed for tests»).
- **Цикл обновления:** не меняется. `PlayScene.update` по-прежнему обновляет только
  звёзды; корабль неподвижен, `input` не читается (`_input` остаётся).
- **Отрисовка:** `PlayScene.render` — после чёрной заливки и звёзд
  `drawSprite(ctx, SHIP_SPRITE, Math.floor(ship.x), Math.floor(ship.y))` (порядок слоёв
  дизайна: заливка → звёзды → [выстрел — задача 004] → корабль).
- **Ввод / HUD / `main.ts` / `TitleScene` / engine:** не меняются.
- **Документация:** `second-brain/architecture/overview.md` — дописать `sprite.ts`,
  `art.ts`, `ship.ts` и обновить граф импортов.

## Тестируемость

Покрывается unit-тестами (Vitest, environment `node`, без canvas):

- **`parseSprite`** (чистая функция): `width`/`height` по строкам; `.` → `null`;
  символ → цвет из палитры; порядок row-major (индекс `row * width + col`); исключения
  на пустом массиве, строках разной длины, символе вне палитры.
- **`drawSprite`** на фейковом ctx: объект с полем `fillStyle` и методом `fillRect`,
  который записывает `{ fillStyle, x, y, w, h }` на момент вызова; приведение
  `as unknown as CanvasRenderingContext2D`. Проверки: прозрачные пиксели не рисуются;
  число `fillRect` = числу непрозрачных пикселей; каждый `fillRect` — 1×1; смещение
  `x/y` применяется; на несимметричном спрайте 2×3 пиксель `(col, row)` рисуется в
  `(x + col, y + row)` своим цветом (защита от перепутанных строк/столбцов).
- **`ship.test.ts`**: `SHIP_WIDTH === SHIP_SPRITE.width`, `SHIP_HEIGHT ===
SHIP_SPRITE.height`; ширина нечётная (нос по центру); `15×16` (решение В3 —
  защита от случайной перерисовки другого размера); `new Ship()` — `x ===
Math.floor((SCREEN_WIDTH - SHIP_WIDTH) / 2)` (= 120), `y === SHIP_Y`; корабль
  целиком на экране (`SHIP_Y + SHIP_HEIGHT <= SCREEN_HEIGHT`, `x + SHIP_WIDTH <=
SCREEN_WIDTH`); `new Ship(x)` — `x` берётся из аргумента. Числа — через
  экспортируемые константы.
- **Валидность `SHIP_SPRITE`** проверяется косвенно: `art.ts` вызывает `parseSprite`
  при загрузке модуля, ошибка формата уронит импорт в `ship.test.ts`.
- **`PlayScene`** — по желанию: `new PlayScene(createRng(1)).ship` стоит на стартовой
  позиции и не сдвигается после `step()` с зажатыми клавишами. `play-scene.test.ts`
  по дизайну появляется в задаче 003; здесь не обязателен.

Только визуально (`npm run dev`): вид корабля (оригинальность, 8-битный стиль,
читаемость на звёздном фоне), положение по центру внизу, чёткость пикселей.
**Владелец утверждает вид** — без этого задача не закрыта.

## Зависимости и ограничения

- **Зависимость:** задача 001 реализована (в рабочем дереве, не закоммичена):
  `PlayScene`, переход с титула, `scene-test-utils.ts` на месте; `npm test` — 12
  тестов зелёные. Задача 002 строится поверх этого состояния.
- **Разрешение 256×240.** Корабль занимает `x ∈ [120, 135)`, `y ∈ [208, 224)`;
  нижние 16 px (224–239) оставлены под иконки жизней.
- **Производительность:** ≤ 240 `fillRect` на корабль за кадр — несущественно
  (дизайн, «Альтернативы»). Смену `fillStyle` можно делать только при смене цвета —
  мелкая оптимизация, на усмотрение plan.
- **TypeScript strict + `noUncheckedIndexedAccess`:** `rows[i]`, `palette[ch]`,
  `pixels[i]` дают `T | undefined` — в `parseSprite` это естественно совпадает с
  проверками ошибок (символ вне палитры), в `drawSprite` нужна проверка/пропуск
  `undefined`/`null`. `verbatimModuleSyntax` + линтер — `import type` для `Sprite` и
  типов из engine.
- **`drawSprite` не должен зависеть от DOM-типов в рантайме** — только `fillStyle` и
  `fillRect`, иначе тест на фейковом ctx не пройдёт в environment `node`.
- **Округление:** дизайн кладёт `Math.floor` в вызывающий код (`PlayScene.render`).
  Делать ли `floor` ещё и внутри `drawSprite` — решение plan; тест «смещение x/y
  применяется» должен быть согласован с выбранным вариантом.
- **Мелкие решения формата для plan** (не продуктовые, в рамке дизайна): что делать с
  `['']` (нулевая ширина — разумно считать ошибкой формата, как пустой массив) и с
  ключом `.` в палитре (`.` всегда прозрачный; ключ `.` в палитре — разумно считать
  ошибкой, чтобы не было неоднозначности).
- **Ошибка в `SHIP_SPRITE` роняет игру при старте** (исключение при импорте `art.ts`).
  Это приемлемо — ловится тестами раньше, чем в браузере.
- **Оригинальность арта:** в референсе (`second-brain/references/game-reference.png`)
  корабль — красный нос-«стрелка» над бело-голубыми раздвоенными крыльями. Наш силуэт и
  палитра должны заметно отличаться (CLAUDE.md: референс — ориентир по жанру, не макет).
  Палитру разумно согласовать с уже используемыми в игре цветами (`#ff5a3c`,
  `#5ab4ff`, `#ffd36b`, `#b884ff`, белый — `starfield.ts`, `title-scene.ts`), но
  комбинация — своя.
- **Риск переделки в 003:** поле корабля в `PlayScene` в задаче 003 заменится на
  `player`. Это ожидаемо по нарезке; правка механическая.

## Открытые вопросы

Блокирующих вопросов нет: все числа решены владельцем (В3 — 15×16, В6 — y=208), вид
корабля отдан разработчику (В7) с утверждением владельцем глазами по итогам задачи.
Расхождений дизайна с кодом не найдено: `PlayScene` имеет ровно ту форму, которую
предполагает дизайн (`constructor(rng, starfield?)`, `render` — заливка + звёзды).

Неблокирующее, решить в plan (в рамке дизайна):

- Имя публичного поля корабля в `PlayScene` на время до задачи 003 (предлагается
  `ship`).
- Нулевая ширина и ключ `.` в палитре в `parseSprite` — ошибки формата (предложение).
- `Math.floor` только в вызывающем коде или ещё и внутри `drawSprite`.

Выносить в отдельные задачи нечего.
