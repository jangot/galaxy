# Анализ: Статичный строй врагов

Код: ветка `feature/002-enemies-and-levels`, коммит `20da398` + незакоммиченная задача
005 в рабочем дереве (`battle.ts`, `battle-render.ts`, `canvas-test-utils.ts`). Перед
анализом: `npm test` — 80 тестов зелёные, `npm run typecheck` — чисто.

## Общее описание функциональности

Пункт 2 нарезки фичи 002. На игровом экране впервые появляются враги. Строй уровня 1
стоит наверху и пока не двигается: ряд `striker` (8 штук) и два ряда `drone` (по 10).
Покачивания, вылетов и попаданий ещё нет. Выстрел игрока пролетает сквозь врагов,
корабль работает как в 001.

Задача закладывает основу, на которую ложатся задачи 007–013:

- формат раскладки и таблица уровней (`levels.ts`);
- геометрия строя (`formation.ts`);
- сущность врага (`enemy.ts`) и волна (`wave.ts`);
- оригинальные спрайты двух видов (`enemy-art.ts`);
- отдельный `Rng` боя и внедряемая таблица уровней для тестов
  (`Battle(rng, { levels })`, `test-levels.ts`).

Глазами: титул → Enter → наверху, начиная с y = 32, три ряда врагов двух разных видов,
отцентрованные по ширине экрана. Корабль внизу двигается и стреляет как раньше. Задачу
закрывает только утверждение спрайтов `drone`/`striker` владельцем.

## Модели данных и состояние

Рамка — `design.md` («Интерфейсы», «Уточнения для реализации», таблица «Появление API
по задачам», строка 006). В задаче появляется только подмножество итогового API.

**`levels.ts`** (лист графа, импортирует только `config`):

| Элемент              | В задаче 006                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `EnemyKind`          | `'drone' \| 'striker'` (`'raider'` — в 013)                                                                               |
| `LayoutChar`         | `'D' \| 'S' \| '.'` (если вводится; `'R'` — в 013)                                                                        |
| `LevelConfig`        | `{ readonly layout: readonly string[] }`; остальные поля добавляют 007, 009, 012, 013                                     |
| `Slot`               | `{ row, col, kind }`, без `group` (появится в 013)                                                                        |
| `Layout`             | `{ rows, cols, slots }`                                                                                                   |
| `FORMATION_MAX_COLS` | `11` (по дизайну живёт в `levels.ts`: нужен парсеру; `formation.ts` может его импортировать)                              |
| `LEVELS`             | одна строка: `['.SSSSSSSS.', 'DDDDDDDDDD', 'DDDDDDDDDD']` (ширина 10, «Уточнения»)                                        |
| `levelConfig(n, l?)` | `l` по умолчанию `LEVELS`; бросает на `!Number.isInteger(n) \|\| n < 1` и на пустой таблице; за концом — последняя строка |
| `parseLayout(rows)`  | бросает: нет строк; строки разной длины; неизвестный символ (в т.ч. `R`); ширина > 11; ни одного врага                    |

Порядок `slots` — по строкам сверху вниз, внутри строки слева направо. От этого порядка
зависит порядок `wave.enemies`, а дизайн опирается на него в нескольких местах
(«при равенстве — меньший индекс», кандидаты директора, детерминизм). Порядок стоит
закрепить тестом уже здесь.

**`formation.ts`** — геометрия без покачивания (В9):

| Константа / поле | Значение                                                                              |
| ---------------- | ------------------------------------------------------------------------------------- |
| `CELL_WIDTH`     | 16                                                                                    |
| `CELL_HEIGHT`    | 12                                                                                    |
| `FORMATION_TOP`  | 32                                                                                    |
| `SWAY_RANGE`     | 16 — по таблице API нужен только в 007; в 006 не вводить или ввести без использования |
| `cols`, `rows`   | из `Layout`                                                                           |
| `baseX`          | `Math.floor((SCREEN_WIDTH - cols * CELL_WIDTH) / 2)`                                  |
| `slotX(col, w)`  | `baseX + col * CELL_WIDTH + Math.floor((CELL_WIDTH - w) / 2)` (`+ offset` — в 007)    |
| `slotY(row, h)`  | `FORMATION_TOP + row * CELL_HEIGHT + Math.floor((CELL_HEIGHT - h) / 2)`               |

Конструктор в 006 — `Formation(cols, rows)`; `swaySpeed` добавляет 007.

Расчёт для реальных раскладок:

- уровень 1: `cols = 10`, `baseX = 48`, строй по X — `[48, 208)`; ряды по Y — ячейки
  32, 44, 56 (низ строя — 68);
- `ONE_CORNER_ENEMY` (`['D..........']`): `cols = 11`, `baseX = 40`, враг у `x ≈ 40 +
floor((16 - w) / 2)`. Столбец выстрела игрока со старта — `x = 127`
  (`SHIP_START = 120`, `+7`), враг от него далеко.

**`enemy-art.ts`**: `DRONE_SPRITE`, `STRIKER_SPRITE` — через `parseSprite` (как
`art.ts`). Ограничения дизайна: оригинальные, 8-битные, **нечётная ширина**, не больше
**13 × 10**, хитбокс = размер спрайта, виды хорошо различимы. Палитры — свои: лучше не
повторять цвета корпуса корабля (`#ffd36b`, `#b884ff`, `#ff5a3c`) один в один, чтобы
враг читался отдельно от игрока. Цвета и форма — на усмотрение разработчика, владелец
утверждает глазами.

**`enemy.ts`**:

| Элемент         | В задаче 006                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------- |
| `EnemyKindSpec` | `{ readonly sprite: Sprite }` (`aim` — в 010)                                                                 |
| `ENEMY_KINDS`   | `Record<EnemyKind, EnemyKindSpec>`: `drone → DRONE_SPRITE`, `striker → STRIKER_SPRITE`                        |
| `EnemyState`    | только `'formation'`                                                                                          |
| `Enemy`         | `kind`, `slot`, `width`/`height` из спрайта вида, `x`/`y` = слот; `constructor(slot, formation)`; `get state` |

`isAlive`, `kill`, `stateTicks` появляются в 008, `startDive`/`isOut`/`sortieId` — в 009. Отрисовку дизайн выводит через `ENEMY_KINDS[enemy.kind].sprite`, поэтому поле
спрайта у `Enemy` не нужно.

**`wave.ts`**: `Wave(config, rng)`:

- `parseLayout(config.layout)` → `Formation(cols, rows)` → `Enemy` на каждый слот;
- поля `readonly config`, `readonly formation`, `readonly enemies`;
- `update(dt)`.

Директора, выстрелов и `isCleared` в 006 нет.

**`battle.ts`**:

- `BattleOptions { readonly levels?: readonly LevelConfig[] }` (`startLevel` — в 008);
- `Battle(rng, opts?)`: `wave = new Wave(levelConfig(1, opts.levels ?? LEVELS), rng)`;
- геттер `wave`: дизайн даёт `get wave()`, потому что с 008 волна меняется. В 006
  допустимо `readonly`.
- `update(dt, intent)`: `player.update` → `wave.update(dt)` (шаги 1–2 «Потока тика»;
  коллизий и фаз ещё нет).

**`test-levels.ts`** (только для тестов): `ONE_CORNER_ENEMY: readonly LevelConfig[] =
[{ layout: ['D..........'] }]`. Пассивные поля (`swaySpeed = 15` и т. д.) добавляют
следующие задачи вместе с полями. `TWO_LEVELS` — в 008.

## Точки встраивания

1. **`PlayScene` (конструктор).** Сейчас поле `readonly battle = new Battle()` — это
   инициализатор поля, он выполняется до тела конструктора и `rng` не видит. Нужно
   создавать `Battle` в конструкторе:
   `new Battle(createRng(Math.floor(rng() * 2 ** 32)))`. Третий аргумент `opts` у
   `PlayScene` — не здесь, а в 008.
   Порядок потребления `rng` («Открытые вопросы», п. 2): если `starfield` не передан,
   сцена тоже берёт из `rng` (`new Starfield(..., rng)`). Сначала звёзды, потом seed —
   так раскладка звёзд для данного seed не меняется относительно 001/005. Из `TitleScene`
   `starfield` приходит готовым, и `rng` тратится только на seed боя.
2. **`Battle.update`.** После `player.update` вызывается `wave.update(dt)` («Поток
   тика», шаги 1–2).
3. **`drawBattle`.** Слои по дизайну: вражеские выстрелы (с 012) → выстрел игрока →
   враги → корабль. В 006 враги рисуются между выстрелом игрока и кораблём:
   `drawSprite(ctx, ENEMY_KINDS[e.kind].sprite, Math.floor(e.x), Math.floor(e.y))` для
   каждого врага по порядку `wave.enemies`. Импорт `enemy` в `battle-render` есть в графе
   дизайна; `Wave`/`Enemy` нужны только как типы.
4. **`main.ts`, `TitleScene`, цикл, ввод** — не меняются.
5. **`overview.md`** — дописать новые модули и обновить строки про `Battle`
   («конструктор без аргументов» → `Battle(rng, opts?)`), `battle-render` (слой врагов),
   `PlayScene` (отдельный `Rng` боя), граф импортов.

## Тестируемость

Всё, кроме самих картинок, тестируется без canvas:

- **`levels.test.ts`**:
  - `parseLayout`: размеры (`rows`, `cols`); виды по символам; `.` пропускается; порядок
    слотов row-major;
  - ошибки `parseLayout`: `[]`, строки разной длины, чужой символ (`'X'` и `'R'` — `R`
    до 013 неизвестен), ширина 12, раскладка из одних `.`;
  - `levelConfig`: `1` → `LEVELS[0]`; `LEVELS.length + 5` → последняя строка;
    `0`, `1.5`, `NaN`, `-1` → бросает; пустая таблица `[]` → бросает; внедрённая
    таблица — то же правило «за концом — последний»;
  - для каждой строки `LEVELS` (`it.each`): раскладка разбирается, ширина 10 (решение
    «Уточнений»). Остальные инварианты строк добавляют следующие задачи.
- **`formation.test.ts`**:
  - `slotX`/`slotY` центрируют спрайт в ячейке: нечётная ширина `w` даёт
    `floor((16 - w) / 2)`;
  - `baseX` центрирует строй (`cols = 10` → 48, `cols = 11` → 40);
  - строй максимальной ширины (11) внутри экрана. Проверка «при `±SWAY_RANGE`» — в 007.
- **`enemy.test.ts`**:
  - позиция = `formation.slotX(col, width)`, `slotY(row, height)`;
  - `width`/`height` = размер спрайта вида;
  - `state === 'formation'`;
  - инвариант спрайтов из `ENEMY_KINDS`: нечётная ширина, `≤ 13 × 10`, вписываются в
    ячейку 16 × 12 (дизайн, «enemy.test.ts»).
- **`wave.test.ts`**:
  - число врагов = числу непустых ячеек;
  - виды и `slot` совпадают с раскладкой, позиции — слоты `formation`;
  - порядок `enemies` = порядок слотов;
  - `update` не меняет позиции (строй статичен) и не бросает.
  - Детерминизм по seed — в 009, когда `rng` начнёт использоваться.
- **`battle.test.ts`**:
  - с `{ levels: ONE_CORNER_ENEMY }` — в волне ровно один `drone` в слоте (0, 0);
  - без `opts` — волна из `LEVELS[0]` (28 врагов);
  - `update` двигает корабль, как в 001 (регрессия).
- **`battle-render.test.ts`**: на `recorder()`:
  - вызовы спрайта врага приходят после выстрела и до корабля;
  - координаты — `Math.floor(x/y)` врага (дробную позицию можно задать прямой
    установкой `enemy.x`, поле публичное).

**Только глазами** (`npm run dev`): вид спрайтов, читаемость двух видов, центровка
строя, отсутствие регрессии корабля. Спрайты утверждает владелец.

## Зависимости и ограничения

- Зависит от 005 (в рабочем дереве, не закоммичено; анализ опирается на реальный код).
- `tsconfig`: `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`.
  Неиспользуемые параметры проходят tsc и ESLint только с префиксом `_`
  (`argsIgnorePattern: '^_'`). Неиспользуемое `private`-поле tsc тоже ловит (TS6138).
  Это касается `rng` и `dt` в `Wave` («Открытые вопросы», п. 1).
- `noUncheckedIndexedAccess`: `levels[levels.length - 1]` и `rows[0]` имеют тип
  `T | undefined`. Нужна явная проверка, она же даёт ошибку «пустая таблица».
- Производительность: 28 врагов × до 130 пикселей ≈ 3 600 `fillRect` за кадр — в рамках
  оценки дизайна (до ~7 000), оптимизация не нужна.
- Логическое разрешение 256 × 240; строй уровня 1 занимает y 32–68, корабль — y 208.
  Пересечений нет.
- `LEVELS` разбирается при каждом `new Wave`. Ошибка формата строки таблицы ловится
  тестом «для каждой строки», а не падением при загрузке модуля (в отличие от
  спрайтов). Это нормально.
- `parseSprite` бросает при загрузке `enemy-art.ts` — ошибка в спрайте роняет импорт и
  ловится любым тестом, импортирующим `enemy`.

## Открытые вопросы

Вопросов к владельцу, блокирующих реализацию, нет. Приёмка спрайтов `drone`/`striker`
владельцем — после реализации (критерий готовности задачи).

Технические расхождения дизайна с кодом. Решаются на стадии plan без владельца, ниже —
рекомендации:

1. **`Wave(config, rng)` и `Wave.update(dt)` в 006 не используют `rng` и `dt`.**
   Таблица «Появление API» вводит их здесь, но строй статичен (`dt` нужен с 007,
   `Formation.update`), а директора нет (`rng` нужен с 009). При
   `noUnusedParameters` tsc не пропустит именованные параметры. Неиспользуемое
   `private readonly rng` тоже даст ошибку (TS6138). Убрать `rng` из `Wave` нельзя:
   тогда он не используется в `Battle(rng)`, а `Battle(rng)` с отдельным `Rng` боя —
   требование задачи.
   **Рекомендация:** параметры `_rng` и `_dt` в `Wave`. Их понимают и tsc, и ESLint
   (`argsIgnorePattern: '^_'`). В 007 `_dt` → `dt`, в 009 `_rng` → `rng` — правка в одну
   строку. Для `Battle` в 005 от `_rng` отказались, потому что там проще было не
   принимать `rng` вовсе. Здесь сигнатура `Wave(config, rng)` предписана и нужна, чтобы
   `rng` дошёл от `Battle`.
   Отдельно: нужен ли в 006 `Enemy.update`. Позиция в строю статична и задаётся в
   конструкторе. Варианты: (а) `Enemy.update()` без параметров пересчитывает позицию из
   слота, `Wave.update` вызывает её для всех врагов — это форма тика 007; (б)
   `Wave.update(_dt)` пустой, `Enemy.update` появляется в 007. Рекомендация — (а): в 007
   добавится только `formation.update(dt)`. Если пустой метод не пропустит линтер
   (`no-empty-function` в `recommended` сейчас не включено), (а) это тоже снимает.
2. **Порядок потребления `rng` сцены.** Дизайн не уточняет, что раньше: создание
   `Starfield` из `rng` (когда звёзды не переданы) или seed боя. Рекомендация — звёзды
   первыми: раскладка звёзд для данного seed не меняется. Ни один тест от этого не
   зависит.
3. **`battle-render.test.ts` сломается.** Тест «draws only the ship when there is no
   shot» и остальные сравнивают массив вызовов целиком. С волной `LEVELS` в массиве
   окажутся 28 спрайтов врагов. Перевести тесты на `ONE_CORNER_ENEMY`, ожидаемые вызовы
   строить из пикселей спрайта врага (как `shipCalls`). Это правка тестов, а не дизайна.
4. **`SWAY_RANGE` и `FORMATION_MAX_COLS`.** `FORMATION_MAX_COLS` нужен парсеру
   (`levels.ts`), а `formation.ts` может импортировать его оттуда для теста «строй
   максимальной ширины внутри экрана». `SWAY_RANGE` в 006 не используется (export без
   использования tsc пропускает). Рекомендация — вводить в 007.

Отдельная задача не требуется: всё нужное для 006 в коде есть.
