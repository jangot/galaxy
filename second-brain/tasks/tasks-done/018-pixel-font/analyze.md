# Анализ: Пиксельный шрифт

## Общее описание функциональности

Свой моноширинный пиксельный шрифт в стиле NES, чтобы текст в игре ложился ровно по
логическим пикселям 256×240 и при целочисленном масштабе оставался чётким. Сейчас
единственный текст в игре — заставка (`TitleScene.render`, `ctx.fillText` с
`monospace`, `src/game/scenes/title-scene.ts:36-42`): сглаженный системный шрифт,
размытый при масштабе и разный в разных ОС, тестами не проверяется.

Шрифт — инструмент для верхней панели (задача 019, фича 004-hud). В этой задаче он
только появляется как модуль с тестами: на экран ничего не выводится, `TitleScene` не
меняется (перевод заставки — вне фичи, `design.md:208`).

Рамка — согласованный `second-brain/features/004-hud/design.md` (разделы «Шрифт»,
«Интерфейсы», «Тестирование», пункт 1 нарезки) и принятые пункты 5, 6 и комментарий
про хвостовой зазор из `dev-review.md` / `discussion.md`. Анализ уточняет его по коду,
не перепроектирует.

## Модели данных и состояние

Состояния нет: шрифт — неизменяемые данные, собранные при загрузке модуля, и две
чистые функции поверх них.

| Сущность / константа | Значение / тип                                | Смысл                                                                 |
| -------------------- | --------------------------------------------- | --------------------------------------------------------------------- |
| `GLYPH_WIDTH`        | `7`                                           | Ширина глифа, px (В7)                                                 |
| `GLYPH_HEIGHT`       | `7`                                           | Высота глифа, px (В7)                                                 |
| `CHAR_ADVANCE`       | `8`                                           | Шаг символа — клетка 8×8, справа и снизу 1 px зазора                  |
| `Font`               | `ReadonlyMap<string, Sprite>`                 | Символ → глиф                                                         |
| `FONT_GLYPHS`        | `Readonly<Record<string, readonly string[]>>` | Сырые данные глифов (`font-art.ts`): 7 строк по 7 символов, `#` / `.` |
| `FONT`               | `Font`                                        | Шрифт игры = `parseFont(FONT_GLYPHS)` при загрузке модуля             |
| `FONT_INK`           | приватная строка-цвет в `font.ts`             | Заглушка для палитры `{ '#': FONT_INK }`; «mask only, never drawn»    |

Глиф хранится как обычный `Sprite` (`src/game/sprite.ts:2-6`): `pixels[row * width +
col]`, `null` — пусто. При отрисовке шрифта используется только маска
`pixels[i] !== null`, цвет из `pixels` не читается.

Набор символов — 37 глифов: `0–9` (10), `A–Z` (26), пробел (из одних `.`, ничего не
рисует). Других символов нет; строчные, знаки препинания и т. п. — ошибка.

Контракты функций (`design.md:227-243`):

- `textWidth(text)` = `text.length * CHAR_ADVANCE`; хвостовой зазор 1 px последней
  клетки оставлен намеренно (ширина моноширинной клетки) — это должно быть сказано в
  комментарии, чтобы его не «починили». Бросает на символе без глифа. `textWidth('') = 0`.
- `drawText(ctx, text, x, y, color)` — верхний левый угол первого символа в `(x, y)`;
  символ `i` — в `x + i * CHAR_ADVANCE`. `ctx.fillStyle = color` один раз на вызов, затем
  `fillRect(px, py, 1, 1)` на каждый пиксель маски. `x`/`y` ожидаются целыми,
  `Math.floor` внутри нет (как у `drawSprite`). Бросает на символе без глифа.
- `parseFont(glyphs)` — каждый глиф через `parseSprite` (её ошибки пробрасываются),
  затем проверка размера `GLYPH_WIDTH × GLYPH_HEIGHT`; другой размер — ошибка.

## Тестируемость

Всё в задаче покрывается unit-тестами без canvas (Vitest, environment `node`):
случайности и времени нет вообще.

- **Набор:** `FONT` содержит ровно/как минимум `0–9`, `A–Z`, пробел; каждый глиф
  `GLYPH_WIDTH × GLYPH_HEIGHT`.
- **Пробел пуст:** все `pixels` пробела — `null`; остальные глифы — хотя бы один пиксель
  (дешёвая защита от пустого глифа-заготовки; в дизайне явно не требуется, но
  естественно дополняет).
- **Различимость цифр:** маски всех 10 цифр попарно различны (защита от копипасты,
  `design.md:309`). Стоит распространить и на буквы — те же 3 строки теста.
- **`parseFont`:** бросает на глифе неверной ширины и неверной высоты; пробрасывает
  ошибку `parseSprite` (рваные строки, неизвестный символ, например `x`).
- **`textWidth`:** `''` → 0, `'AB'` → `2 * CHAR_ADVANCE`; бросает на строчной букве.
- **`drawText`** через `recorder()`:
  - один глиф в `(x, y)` — ровно `fillRect(x + c, y + r, 1, 1)` по пикселям маски, в
    порядке обхода, все с переданным цветом;
  - второй символ сдвинут на `CHAR_ADVANCE`;
  - пробел ничего не рисует (0 вызовов);
  - бросает на неизвестном символе.
- **«`fillStyle` ровно один раз»** — `recorder()` фиксирует `fillStyle` в момент
  каждого `fillRect`, но не считает присваивания. Проверка «все вызовы с переданным
  цветом» им делается; строгий счёт присваиваний — нет (см. «Открытые вопросы», п. 1).

Визуально проверять нечего: вид глифов смотрится в задаче 019 (`acceptance.md` там).

## Зависимости и ограничения

- **Зависимостей от других задач нет.** Всё нужное (`parseSprite`, `recorder`) уже есть.
- **Клетка 8×8, глиф 7×7:** правый столбец и нижняя строка клетки всегда пустые —
  межсимвольный и межстрочный зазор. В HUD строки подписей и значений разнесены на
  10 px (`HUD_LABEL_Y = 4`, `HUD_VALUE_Y = 14`), так что высота глифа 7 — жёсткая
  часть раскладки 019: менять размер глифа нельзя без пересчёта раскладки.
- **Производительность:** ≈ 400 `fillRect` 1×1 на кадр для всей панели (оценка
  `design.md:131`) — кэш/offscreen-canvas не нужен.
- **TypeScript strict + `noUncheckedIndexedAccess`:** `sprite.pixels[i]` типа
  `string | null | undefined`, `FONT.get(ch)` — `Sprite | undefined`; отсутствие глифа
  обрабатывается броском ошибки, а не `!`.
- **Итерация строки:** `text.length` считает UTF-16 единицы, перебор `for…of` — кодовые
  точки. Для разрешённого набора (ASCII) это одно и то же; любой не-ASCII символ и так
  бросает ошибку — расхождения на практике нет.
- **Ключи `FONT_GLYPHS`** — односимвольные строки; через `Map` нет риска с ключами вроде
  `constructor` (в отличие от поиска по объекту — ср. `Object.hasOwn` в `parseSprite`).
- **Конвенции:** код и комментарии на английском, `import type` для `Sprite`, шрифт в
  `src/game/` (не в движке, `design.md:92-93`).
- **Риск — читаемость глифов.** Форма букв — художественное решение разработчика в
  рамках 7×7 (стиль NES: толщина штриха на усмотрение, `0` отличим от `O`, `1` от `I`,
  `5` от `S`, `8` от `B`). Проверяется глазами только в 019; если не понравится —
  правятся только данные `font-art.ts`.

## Открытые вопросы

Вопросов к владельцу нет: все игровые/визуальные решения уже приняты (В7) и
зафиксированы в `design.md`. Технические уточнения, решаемые на стадии плана:

1. **Как проверить «`fillStyle` выставлен ровно один раз».** `recorder()`
   (`src/game/canvas-test-utils.ts:12-21`) хранит `fillStyle` как обычное поле и
   присваивания не считает. Варианты: (а) в `font.test.ts` локальный фейк-ctx с
   setter'ом `fillStyle`, считающим присваивания (общий util не трогается);
   (б) добавить счётчик присваиваний в `recorder()` — затрагивает общий тестовый util,
   его используют `sprite.test.ts` и `battle-render.test.ts`; (в) ограничиться
   проверкой «все `FillCall.fillStyle` равны переданному цвету». Рекомендация — (а):
   строго по дизайну и без правки общего кода. Описание задачи говорит «через
   `recorder()`» — основная проверка пикселей идёт через него, счёт присваиваний — поверх.
2. **`drawText('')` / только пробелы:** ставить ли `fillStyle` при отсутствии пикселей.
   Дизайн говорит «один раз на вызов» — проще и последовательнее ставить всегда;
   тестом не фиксировать (поведение несущественно).
3. **Проверка ключей в `parseFont`** (ключ ровно один символ) — в дизайне нет;
   многосимвольный ключ просто никогда не совпадёт. Можно добавить дешёвую проверку
   или не делать — решить в плане, по умолчанию не расширять задачу.

Выносить в отдельные задачи нечего.
