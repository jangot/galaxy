# Анализ: Специальные враги raider

## Общее описание функциональности

Последняя (9-я) задача фичи 002 «Враги и уровни». С 4-го уровня в верхнем ряду строя
стоят специальные враги `raider` — группами по 2–3 в соседних ячейках (`..RR..RR..` на
уровне 4, `.RRR..RRR.` на уровне 5). Группа вылетает **целиком, одним вылетом**: все её
члены в одном тике «отклеиваются» в одну сторону по одной дуге `peel`, затем пикируют
к кораблю, сохраняя взаимное расположение (каждый целится в X корабля со своим сдвигом
по слоту — `aimOffsetX`), и стреляют залпами (`raiderShots` уровня). Ушедшие за низ
возвращаются каждый в свой слот поодиночке — как обычные враги.

Для игрока: на уровнях 4–5 сверху летит «звено» из 2–3 одинаковых кораблей, держащее
строй, и даёт плотный залп — заметный рост сложности после уровней 1–3. Плюс два
новых уровня в `LEVELS` и обновление `second-brain/game-design.md` решениями владельца
по фиче 002.

Рамка — согласованный `design.md` фичи (раздел «Сущности и состояния» → `AttackDirector`,
«Интерфейсы», «Уточнения для реализации» → «Таблица LEVELS», «Точные правила»: `side`
группы, лидер и `aimOffsetX`; таблица «Появление API по задачам», строка 013). Анализ
не перепроектирует, а уточняет по коду.

## Модели данных и состояние

**Новое/меняющееся в данных:**

| Сущность / поле                  | Сейчас (после 012)                     | После 013                                                                                                                       |
| -------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `EnemyKind`                      | `'drone' \| 'striker'`                 | `+ 'raider'`                                                                                                                    |
| `LayoutChar`                     | `'D' \| 'S' \| '.'`                    | `+ 'R'`                                                                                                                         |
| `Slot`                           | `{ row, col, kind }`                   | `+ group: number \| null` — номер непрерывной серии `R` в строке, сквозной по раскладке (row-major); у `D`/`S` — `null`         |
| `LevelConfig`                    | `… diverShots`                         | `+ raiderShots` (обязательное; уровни 1–3 и тестовые таблицы — 0)                                                               |
| `DiveOrder`                      | `{ sortieId, side, shots }`            | `+ aimOffsetX` (одиночные — 0)                                                                                                  |
| `ENEMY_KINDS`                    | `drone` (fixed), `striker` (track)     | `+ raider: { sprite: RAIDER_SPRITE, aim: 'fixed' }`                                                                             |
| `Enemy` (приватно)               | `fixedAimX` = `env.targetX` в тике `D` | хранит `aimOffsetX` из приказа; цель `fixed` = `targetX + aimOffsetX` (если `targetX === null` — цели нет, весь `descend` вниз) |
| `RAIDER_SPRITE` (`enemy-art.ts`) | —                                      | новый спрайт                                                                                                                    |

`Record<EnemyKind, …>` в `ENEMY_KINDS` и `Record<…, EnemyKind>` в `KIND_BY_CHAR`
(`levels.ts`) — исчерпывающие: добавление `'raider'` без записей в них не пройдёт `tsc`.

**Правила (из «Точных правил» дизайна):**

- `side` группы: `firstCol + lastCol + 1 < cols ? -1 : 1` (центр группы левее середины —
  влево; ровно посередине — вправо).
- Лидер — самый внешний **живой** член группы в сторону `side` (для `side = -1` —
  наименьший `col`, для `+1` — наибольший). `aimOffsetX = (member.col - leader.col) *
CELL_WIDTH`. Все члены — один `sortieId`, один `side`, `shots = raiderShots`.
- Группа — кандидат, только если **все её живые** члены в `formation` (если хоть один
  живой в `diving`/`returning` — группы в кандидатах нет). Мёртвые/взрывающиеся члены не
  участвуют; группа из одного выжившего — вылет из одного с `aimOffsetX = 0`.
- Кандидаты-«крайние» (`edgeCandidates`) — только `drone`/`striker`: `raider` в них не
  входят (в уровнях 4–5 верхний ряд целиком из `R`, поэтому он даёт только групповых
  кандидатов).
- Группа — один кандидат в равновероятном выборе (`randomInt(rng, 0, n)`) и один вылет в
  лимите `maxSorties` (лимит уже считает различные `sortieId` — `activeSorties`).

**Почему группа держит строй (проверено по коду `enemy.ts`):** члены группы — один вид
(одинаковая ширина), стоят в соседних ячейках с шагом `CELL_WIDTH`, стартуют в одном
тике, идут по одной дуге `peel` (`side` общий), цель `fixed` берут в одном тике `D`, а
цель смещена ровно на разницу их позиций. Значит, `gap = aimX - centerX` у всех
одинаков, и `steerStep` даёт всем одинаковый шаг — строй сохраняется точно, пока не
вмешается зажим X по краю экрана (см. «Риски»).

**Уровни 4–5 (точные строки — «Уточнения для реализации»):**

| Уровень | `layout`                                                       | sway | dive | first | interval | maxSorties | diverShots | raiderShots |
| ------- | -------------------------------------------------------------- | ---- | ---- | ----- | -------- | ---------- | ---------- | ----------- |
| 4       | `'..RR..RR..'`, `'.SSSSSSSS.'`, `'DDDDDDDDDD'`, `'DDDDDDDDDD'` | 30   | 120  | 120   | 90       | 3          | 2          | 2           |
| 5       | `'.RRR..RRR.'`, `'.SSSSSSSS.'`, `'DDDDDDDDDD'`, `'DDDDDDDDDD'` | 30   | 180  | 90    | 60       | 3          | 2          | 3           |

Проверка по существующим инвариантам таблицы (`levels.test.ts`): `isAllowedSpeed(30)`,
`180/60 = 3` px/тик — целое; `30 < STEER_SPEED = 60`; `ENEMY_SHOT_SPEED 240 > 180`;
туннелирование: `4 + max(3, 1, 1) = 7 < SHOT_HEIGHT 4 + minEnemyHeight` — при текущем
минимуме 8 (drone) выполняется; `RAIDER_SPRITE` должен иметь высоту ≥ 4 (иначе станет
новым минимумом и сломает инвариант). Ширина 10 — как у уровней 1–3. Группы: на
уровне 4 — cols 2–3 (`side -1`) и 6–7 (`+1`); на уровне 5 — 1–3 (`-1`) и 6–8 (`+1`).

**Спрайт `RAIDER_SPRITE`:** оригинальный, ширина нечётная, ≤ 13 × 10 (тест
`ENEMY_KINDS sprites` проверяет это для всех видов автоматически), высота ≥ 4, заметно
отличается от `drone` (зелёный) и `striker` (синий/пурпурный), цвет не совпадает с
`ENEMY_SHOT_COLOR` (`#ff5fd2`). Вид — визуальное решение разработчика, утверждает
владелец глазами.

## Точки встраивания

- **Разбор раскладки:** `parseLayout` — символ `R` → `raider`, счётчик групп: новая
  серия `R` начинается на `R`, если предыдущая ячейка строки не `R` (или начало строки);
  нумерация сквозная по раскладке в row-major порядке. Ошибки формата прежние.
- **Выбор вылета:** `selectSortie` — к кандидатам «крайних» (уже без `raider`)
  добавляются групповые кандидаты; `Sortie` уже поддерживает несколько участников
  (`members[i]` ↔ `orders[i]`), а `AttackDirector.update` уже раздаёт `startDive` всем
  участникам — менять его не нужно.
- **Прицеливание:** `Enemy.startDive` сохраняет `aimOffsetX`; в первом тике `descend`
  `fixedAimX = targetX === null ? null : targetX + aimOffsetX`. `track` (`striker`) от
  `aimOffsetX` не зависит (у него всегда 0).
- **Стрельба:** без изменений — `raider` стреляет по общему расписанию `fires()`,
  `shots` из приказа = `raiderShots`.
- **Рендер, сцена, ввод, цикл, `Battle`:** без изменений. Отладочный вход — уже есть
  `?level=4` / `?level=5` (`parseStartLevel` в dev-сборке).

**`game-design.md` — что внести (решения владельца по фиче 002):**

- Строй: ячейка 16 × 12, до 11 столбцов (уровни — 10), верх на y = 32, покачивание ±16 px,
  появляется сразу без влёта (В3, В9); виды по рядам: `drone` внизу, `striker` в
  середине, `raider` в верхнем ряду.
- Пикирование: вылетают крайние враги любого ряда по дуге наружу; `drone` — в точку,
  где был корабль, `striker` — преследует 1 px/тик, `raider` — группой 2–3 в точку со
  своим сдвигом; уход за низ → возврат сверху в свой слот (В3, В4).
- Вражеские выстрелы: 1 × 4, свой цвет, 240 px/с, не больше 4 на экране, интервал 20 тиков,
  выстрелы за вылет — по таблице уровня (В2).
- Поражение игрока: выстрел или таран (при таране гибнут оба), 1 с без корабля, затем
  2 с мигания с неуязвимостью, уровень не перезапускается (В5, В6).
- Уровни: таблица `LEVELS` (5 уровней, рост сложности: скорость → стрельба → группы
  `raider`), после конца таблицы повторяется последний, пауза 1,5 с без надписи (В1, В7, В8).
- Остаются в плане (не решено фичей 002): очки, «командир с эскортом» и бонус за него,
  жизни/Game Over, HUD, меню — пункты «Механики (план)» про них не трогать; `raider`
  без командира — не то же, что «командир с эскортом».

## Тестируемость

Всё поведение задачи — чистая детерминированная логика, покрывается Vitest без canvas:

- `levels.test.ts`:
  - `parseLayout`: `R` → `raider`; две серии в строке — две группы (`'RR.RR'` → 0, 0, 1, 1);
    серии в разных строках — разные группы; у `D`/`S` — `group: null`; `R` вплотную к `D`
    в строке (`'DRRD'`) — одна группа; `X` по-прежнему ошибка.
  - Для каждой строки `LEVELS`: `raiderShots` — целое ≥ 0; если есть `R` — `raiderShots > 0`;
    `R` только в строке 0 раскладки; каждая группа — 2–3 слота. Правило таблицы, а не
    парсера (дизайн, «Альтернативы»).
  - «has the agreed rows» — 5 строк ровно как в «Уточнениях»; минимальная высота спрайта
    в инварианте туннелирования теперь учитывает `raider` автоматически
    (`Object.values(ENEMY_KINDS)`).
- `attack-director.test.ts` (`selectSortie` на волнах `passiveLevel`):
  - группа — один кандидат, все члены в `members`, общий `sortieId`, общий `side`,
    `shots = config.raiderShots`; `aimOffsetX` = `(col - leader.col) * 16` (для `side = -1`
    лидер слева: 0, 16, 32; для `+1` — справа: −32, −16, 0);
  - `side` группы по центру (слева / справа / ровно посередине — вправо);
  - член группы в полёте → группы нет в кандидатах; член убит → группа вылетает без него,
    лидер — самый внешний живой (сдвиги от него); все члены мертвы → группы нет;
  - `raider` не попадают в «крайние» своего ряда;
  - порядок кандидатов фиксирован (через `fixed(v)` rng, как в тесте «lists row edges»);
    одиночные приказы — `aimOffsetX: 0`;
  - `AttackDirector`: группа — один слот в `maxSorties` (при `maxSorties = 1` после вылета
    группы новый вылет не стартует, пока вся группа не вернулась/не убита).
- `enemy.test.ts`: `ENEMY_KINDS.raider.aim === 'fixed'`; `fixed` с `aimOffsetX` целится в
  `targetX + aimOffsetX`; с `targetX === null` в тике `D` — прямо вниз независимо от
  сдвига; спрайты трёх видов различаются попарно; размеры `RAIDER_SPRITE` — общим `it.each`.
- По желанию — `wave.test.ts`: группа `raider` после `P` тиков даёт выстрелы в одном
  тике; члены группы в `descend` сохраняют разницу X (строй держится) — проверка «держат
  строй» без глаз.

Только глазами (`?level=4`, `?level=5`): вид спрайта `raider` (**утверждает владелец**),
что группы вылетают вместе, держат строй, стреляют залпом; ощущение роста сложности
1 → 5.

## Зависимости и ограничения

- Зависит от 012 (выстрелы, `config` в `selectSortie`, `DiveOrder.shots`) — реализовано
  в рабочем дереве; базовая линия: `npm test` — 345 тестов зелёные, `typecheck` чистый.
- Детерминизм: выбор только через `randomInt(rng, …)`, порядок кандидатов фиксирован;
  `rng` не вызывается, если кандидатов нет (существующий тест).
- Граница engine/game не затрагивается. Новая связь импорта
  `attack-director → formation` (`CELL_WIDTH`) — без циклов (`formation` импортирует
  только `config`).
- Производительность: врагов ≤ 4 × 10, `selectSortie` — линейный проход раз в тик, когда
  таймер на нуле; группы — несколько штук. Проблем нет.
- **Риск: зажим X у края экрана сжимает группу.** Если корабль у края в сторону, где
  у группы отрицательные (или положительные) сдвиги (напр. группа `side = +1`, лидер
  справа, корабль у левого края: цели −9, −25 px), крайние члены упрутся в `x = 0` и
  наложатся. Это следствие принятого в дизайне зажима X во всех фазах `diving` —
  ничего не ломает (коллизии/возврат работают), но «строй» на краю визуально сжимается.
  Отмечено для приёмки глазами.
- **Риск: лимит выстрелов «съедает» залпы `raider`.** Члены группы стреляют в одних и
  тех же тиках (`D`, `D+20`, `D+40`). Уровень 5: 3 рейдера × 3 выстрела = 9 выстрелов за
  40 тиков, а выстрел живёт на экране ~45–50 тиков (≈200 px при 4 px/тик), при
  `MAX_ENEMY_SHOTS = 4` реально вылетят ≈4: первый залп из 3, во втором — 1, третий почти
  весь пропадёт; плюс выстрелы `drone`/`striker` других вылетов конкурируют за тот же
  лимит. Теряются выстрелы членов, идущих позже в `wave.enemies` (правые в группе). На
  уровне 4 (2 × 2) залпы помещаются, если других выстрелов нет. Это ожидаемое следствие
  В2 («выстрел пропал»), не дефект — но влияет на ощущение; отмечено для приёмки глазами.
- Существующие тесты, которые изменятся по смыслу: `levels.test.ts` — кейс
  «raider char before task 013» (сейчас ожидает ошибку на `R`), точное сравнение слотов
  (`toEqual` без `group`), «has the agreed rows» (3 строки без `raiderShots`);
  `attack-director.test.ts` — точные приказы без `aimOffsetX`.

## Открытые вопросы

Блокирующих вопросов к владельцу нет: числа и поведение (В1–В4) и точные строки
уровней 4–5 согласованы в дизайне. Технические уточнения — решаю в рамках дизайна,
фиксирую здесь для плана (расходятся с буквой дизайна только в неоговорённых местах):

1. **`firstCol`/`lastCol` в формуле `side` группы — по всей группе раскладки или по живым?**
   Дизайн не уточняет. Предлагаю — **по живым членам** (то же, что для одиночки ряда:
   `side` по текущему положению); лидер и так берётся среди живых. Для `LEVELS` оба
   варианта дают одинаковый `side` при любом наборе выживших (группы далеко от
   середины). Если архитектор считает иначе — правка в одну строку.
2. **Место групповых кандидатов в порядке списка.** Дизайн: «по рядам сверху вниз, слева
   направо». Предлагаю: внутри ряда кандидаты упорядочены по левому столбцу кандидата
   (левый крайний, группы по `firstCol`, правый крайний). Для `LEVELS` (`R` только в
   верхнем ряду, ряд целиком из групп) это просто «группы слева направо, затем ряды
   ниже»; существующий тест «lists row edges top to bottom, left before right» не
   меняется.
3. **`aimOffsetX` и `Slot.group` — обязательные поля (как в «Интерфейсах»).** Это ~39
   правок литералов `startDive({ … })` и 5 литералов `Slot` в тестах (механически, без
   смены поведения). Альтернатива — необязательные поля с умолчанием — расходится с
   итоговыми сигнатурами дизайна; не предлагаю. В плане стоит завести в тестах общий
   хелпер приказа, если правок слишком много.
4. **Для приёмки владельцем глазами (не блокирует):** спрайт `raider`; сжатие группы у
   края экрана; потеря части залпов `raider` на уровне 5 из-за `MAX_ENEMY_SHOTS = 4`
   (подстройка, если нужно, — `raiderShots`/`maxSorties` в `LEVELS` или `MAX_ENEMY_SHOTS`;
   это вопрос баланса, а не этой задачи).

Выносить в отдельные задачи нечего: всё, что нужно (`Sortie` с несколькими
участниками, лимит по различным `sortieId`, стрельба, `?level=N`), уже есть в коде.
