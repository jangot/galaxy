# Анализ: Модель астероида

Код: рабочее дерево поверх `b9f6535` (задача 024 реализована, не закоммичена). Рамка —
согласованный `second-brain/features/006-asteroid-bonuses/design.md` (раунд 3), пункт 2а
нарезки.

## Общее описание функциональности

Логика второй цели игрока — астероида — и агрегата «бонусное поле», пока **без
встраивания в бой**: ни `Battle`, ни сцена, ни рендер не меняются, игра выглядит и
играется как раньше. Проверка — только unit-тестами.

Что моделируется:

- **Астероид 12×12** появляется над верхним краем (`y = -12`) у одного из верхних углов и
  падает наискосок: 1 px/тик вниз (60 px/с, ADR 002) и ½ px/тик вбок (30 px/с, ADR 003).
  Направление сноса и сдвиг от своего края (0…118 px) — случайные. За боковые края он
  никогда не выходит, уходит только за низ (`y >= SCREEN_HEIGHT`). Полёт — 252 тика
  (≈ 4,2 с).
- **Разбивается с одного попадания** — переходит во взрыв на месте (длительность — как у
  врага, `EXPLOSION_TICKS` = 16), затем исчезает. Капсулы в этой задаче нет (задача 027).
- **Вид бонуса** (жизнь / быстрая пуля / две пули) выбирается при появлении равновероятно
  и хранится в астероиде — понадобится капсуле в 027.
- **Поле бонусов** считает тики фазы `playing` текущего уровня, на старте уровня
  вытягивает момент появления 300…900 тиков (5–15 с), выпускает один астероид за
  уровень; если уровень сменился раньше — астероид этого уровня пропадает; если к тику
  появления поле занято — появление ждёт опустения.
- **Очки за астероид** — 100 с надбавкой уровня по той же формуле, что у врагов
  (1-й уровень 100, 5-й — 140). Формула выделяется из `killPoints` в общий
  `levelPoints`; результат `killPoints` не меняется.

## Модели данных и состояние

### Asteroid (`asteroid.ts`, новый)

| Поле              | Тип                                 | Смысл                                                                  |
| ----------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| `x`, `y`          | `number`                            | левый верхний угол; `x` дробная (шаг ½), `y` целая                     |
| `dir`             | `-1 \| 1`                           | направление сноса по X (`1` — вправо, старт у левого края)             |
| `width`, `height` | `number`                            | = `ASTEROID_SIZE` (12) — хитбокс                                       |
| `bonus`           | `BonusKind`                         | вид бонуса, выбран при появлении                                       |
| `state`           | `'flying' \| 'exploding' \| 'gone'` | автомат                                                                |
| `stateTicks`      | `number`                            | тики в состоянии: 0 в тике входа, `++` в начале `update` (как `Enemy`) |

Автомат:

```
flying --hit()--> exploding --EXPLOSION_TICKS--> gone
flying --y >= SCREEN_HEIGHT--> gone
```

- Старт: `y = -height`; `dir = 1` → `x = offset`, `dir = -1` → `x = SCREEN_WIDTH - width - offset`.
- `flying`: `x += dir · ASTEROID_DRIFT_SPEED · dt`, `y += ASTEROID_FALL_SPEED · dt`, затем
  проверка ухода за низ. В тике создания не движется (создаётся после движения поля).
- `hit()`: только из `flying` → `exploding`, `true`; иначе `false`, без эффекта.
- `exploding` стоит на месте; `gone` — терминальное, поле убирает объект.

Константы:

| Константа                   | Значение                                      | Откуда                                 |
| --------------------------- | --------------------------------------------- | -------------------------------------- |
| `ASTEROID_SIZE`             | 12                                            | design; в 2б — тест «= размер спрайта» |
| `ASTEROID_FALL_SPEED`       | 60 px/с (1 px/тик)                            | В9 (а), ADR 002                        |
| `ASTEROID_DRIFT_SPEED`      | 30 px/с (½ px/тик)                            | В9 (а), ADR 003                        |
| `ASTEROID_DRIFT_TOTAL`      | `(SCREEN_HEIGHT + SIZE) · DRIFT / FALL` = 126 | выражение, не литерал                  |
| `ASTEROID_SPAWN_OFFSET_MAX` | `SCREEN_WIDTH - SIZE - DRIFT_TOTAL` = 118     | выражение, не литерал                  |

Проверка крайних значений по коду: при `dir = 1`, `offset = 118` после 252 шагов
`x = 118 + 126 = 244`, `x + 12 = 256 = SCREEN_WIDTH` — граница достигается ровно в тике
ухода; при `dir = -1`, `offset = 118` старт `x = 126`, конец `x = 0`. 126 точно
представимо (252 · ½), шаги ½ точны в double (ADR 003).

### BonusField (`bonus-field.ts`, новый)

| Поле                         | Смысл                                                                            |
| ---------------------------- | -------------------------------------------------------------------------------- |
| `asteroid: Asteroid \| null` | текущий астероид (в т.ч. взрывающийся)                                           |
| `spawnTick: number \| null`  | тик появления текущего уровня; `null` — уже вылетел или `startLevel` ещё не было |
| `levelTicks: number`         | тики `playing` текущего уровня                                                   |
| `rng`                        | собственный генератор поля (в бой подключается в 2б)                             |
| `capsule`                    | **не в этой задаче** (027)                                                       |

- `ASTEROID_SPAWN_MIN_TICKS = 300`, `ASTEROID_SPAWN_MAX_TICKS = 900` (включительно).
- Конструктор тик не вытягивает и `rng` не трогает — без `startLevel` астероида нет никогда.
- `startLevel()`: `levelTicks = 0`, `spawnTick = randomInt(rng, MIN, MAX + 1)` — ровно один
  вызов `rng`; невыпущенный астероид прошлого уровня теряется; летящий — не трогается.
- `update(dt, spawning)` (без умолчания): двигает астероид, убирает `gone`; затем только
  при `spawning`: `levelTicks++`, и если `spawnTick !== null && levelTicks >= spawnTick &&`
  поле пусто — создаёт астероид, `spawnTick = null`. Порядок вызовов `rng` при появлении:
  `dir` (`rng() < 0.5 ? -1 : 1`) → `offset` (`randomInt(rng, 0, OFFSET_MAX + 1)`) →
  `bonus` (`BONUS_KINDS[randomInt(rng, 0, BONUS_KINDS.length)]`).
- `hitAsteroid()`: попадание по `flying`-астероиду, `true` при разбитии; капсулы нет
  (027 добавит выпадение сюда же). Нет астероида / не `flying` — `false`.

### Очки (`score.ts`, изменяемый)

- `levelPoints(base, level)` — текущая формула `killPoints` вместе с проверкой уровня
  (`RangeError` на нецелом/< 1): `floor((base · (9 + level) + 50) / 100) · 10`.
- `killPoints(kill, level)` = `levelPoints(ENEMY_POINTS[kind].formation|flying, level)`.
- `ASTEROID_POINTS = 100`, `asteroidPoints(level) = levelPoints(ASTEROID_POINTS, level)`:
  1 → 100, 5 → 140 (14,5 → округление вверх).
- `BONUS_FALLBACK_POINTS = 500` по дизайну — тоже в `score.ts`, но нужен только в 027;
  в 2а не требуется (см. «Открытые вопросы», п. 3).

## Точки встраивания

В этой задаче — **никаких**: `Battle`, `PlayScene`, рендер, HUD, коллизии не меняются.
Будущие точки (2б, задача 026) — по `design.md`, «Поток тика»: `bonuses?.update(dt,
phase === 'playing')` после `wave.update`, `startLevel()` в конструкторе `Battle` и на
переходе `cleared → playing`, `resolveBonusCollisions` → `hitAsteroid()` →
`addScore(asteroidPoints(level))`. Интерфейсы 2а должны быть такими, чтобы 2б их только
вызывал.

Импорты новых модулей: `asteroid.ts` → `config`, `bonus` (type), `enemy`
(`EXPLOSION_TICKS`); `bonus-field.ts` → `engine/rng` (`Rng` — type, `randomInt`),
`asteroid`, `bonus`. Циклов нет: `enemy.ts` не импортирует ничего из новых файлов.

## Тестируемость

Вся логика задачи — чистая, без canvas, детерминирована `dt = TICK_SECONDS` и `Rng`.

`asteroid.test.ts`:

- старт `y = -ASTEROID_SIZE`, `x` по `dir`/`offset` для обоих краёв; в конструкторе
  `state = 'flying'`, `stateTicks = 0`;
- шаг ½ px/тик по X (знак по `dir`) и 1 px/тик по Y; `isAllowedSpeed` для обеих скоростей;
  `ASTEROID_DRIFT_TOTAL` и `ASTEROID_SPAWN_OFFSET_MAX` — целые, 126 и 118 (и равны
  выражениям от констант);
- **инвариант «весь полёт на экране»**: `offset ∈ {0, OFFSET_MAX}` × `dir ∈ {-1, 1}` —
  каждый тик до `gone` `0 <= x` и `x + width <= SCREEN_WIDTH`;
- `gone` ровно на тике, где `y >= SCREEN_HEIGHT` (252-й `update`), не раньше;
- `hit()` в `flying` → `true`, `exploding`, позиция стоит; через `EXPLOSION_TICKS` →
  `gone`; `hit()` в `exploding`/`gone` → `false`, без эффекта; `update` в `gone` ничего
  не делает;
- **инвариант пробоя**: `FAST_SHOT_SPEED·TICK + ASTEROID_FALL_SPEED·TICK < SHOT_HEIGHT +
ASTEROID_SIZE` (7 < 16) — от констант.

`bonus-field.test.ts` (заглушка `rng` со счётчиком/очередью значений, как `counting` в
`attack-director.test.ts`):

- без `startLevel` — ни одного астероида за > 900 тиков; конструктор не вызывает `rng`;
- `spawnTick` в 300…900: края — `rng() = 0` → 300, `rng()` → 1⁻ → 900;
- астероид появляется в `update`, где `levelTicks === spawnTick`, не раньше; в тике
  появления не сдвинут (`y = -12`); после — `spawnTick === null`, второго на уровне нет;
- `spawning = false` — `levelTicks` стоит, астероид летит;
- `startLevel` до появления — тик вытягивается заново, `levelTicks = 0`; летящий
  астероид переживает `startLevel`;
- уровень «зачищен раньше» — `startLevel` до `spawnTick` → на прошлом уровне астероида
  не было, на новом — по новому тику;
- **отложенное появление** при занятом поле — см. «Открытые вопросы», п. 1;
- порядок вызовов `rng`: `startLevel` — 1 вызов; появление — 3 вызова, значения идут в
  `dir` → `offset` → `bonus` (проверка по заглушке с очередью);
- `hitAsteroid` → `true`, астероид `exploding`; повторно и без астероида — `false`;
  взорвавшийся убирается после `EXPLOSION_TICKS`;
- **детерминизм**: два поля с `createRng(seed)` при одинаковой последовательности
  вызовов дают одинаковые `spawnTick`, `dir`, `x`, `bonus`.

`score.test.ts`: `levelPoints` даёт прежние контрольные значения таблицы `killPoints`;
`RangeError` переехал в `levelPoints` (и `killPoints`/`asteroidPoints` его пробрасывают);
`asteroidPoints(1) = 100`, `asteroidPoints(5) = 140`, кратность 10; тесты `killPoints`
и `battle.test.ts` (5000 очков на уровне) — не меняются.

Глазами в этой задаче проверять нечего — в игру не встроено.

## Зависимости и ограничения

- Зависит от 024 (`bonus.ts`) — есть в рабочем дереве.
- Фиксированный шаг (ADR 003): шаг ½ px/тик точен только при `dt = TICK_SECONDS`.
- `stateTicks` и таймер взрыва — в тиках, как у `Enemy`; `dt` влияет только на движение.
- Новые вызовы `rng` — только у собственного `rng` поля; `rng` боя не трогается (в 2а поле
  вообще не создаётся боем) — существующие тесты с фиксированным seed не сдвигаются.
- Производительность — не вопрос: один объект на поле.
- `ASTEROID_SIZE` по дизайну = размер спрайта, но `ASTEROID_SPRITE` (`bonus-art.ts`)
  появляется только в 2б: в 2а `width/height = ASTEROID_SIZE`, тест равенства со
  спрайтом — в 026 (это не расхождение, а порядок нарезки; в `design.md` тест указан в
  общем списке `asteroid.test.ts`).
- Риск регрессии — только в `score.ts`: перенос формулы обязан сохранить значения и
  сообщение `RangeError` (тест `battle.test.ts` строки 462–465 опирается на точные очки).

## Открытые вопросы

> **Все вопросы закрыты архитектором** — `second-brain/features/006-asteroid-bonuses/discussion.md`,
> «Реализация: задача 025-asteroid-model»: п. 1 — вариант (а), `SpawnWindow` вторым
> параметром конструктора (умолчание `ASTEROID_SPAWN_WINDOW`, неверное окно →
> `RangeError`); п. 2 — подтверждено (тест спрайта в 026); п. 3 — `BONUS_FALLBACK_POINTS`
> в 027; строка `score.ts` в `architecture/overview.md` — правится в 025. К владельцу —
> ничего.

1. **Отложенное появление «поле занято» при реальных константах не воспроизводится в
   тесте.** Критерий готовности требует тест «отложенное появление», `design.md` —
   «при занятом поле появление откладывается до опустения». Но при константах В9
   астероид живёт ≤ 252 тика полёта (или ≤ 252 + `EXPLOSION_TICKS`, если сбит), а после
   `startLevel` до появления проходит ≥ 300 тиков `update(..., true)` — к этому моменту
   поле всегда пусто (сам дизайн называет проверку «страховкой»). В 027 капсула (≤ 240
   тиков) ничего не меняет. Через публичный интерфейс `constructor(rng)` занятое поле
   на тике появления получить нельзя. Варианты:
   - (а, рекомендую) необязательный второй параметр конструктора — окно появления
     `{ minTicks, maxTicks }` с умолчанием 300/900 (по образцу `BattleOptions.levels` для
     тестов); тест ставит окно 1…1, выпускает астероид, зовёт `startLevel` и проверяет,
     что новый появляется только после ухода старого. Расширение интерфейса дизайна, без
     влияния на игру.
   - (б) тест через `update(0, true)` — при `dt = 0` астероид стоит, а `levelTicks`
     растёт. Без изменения интерфейса, но тест опирается на нефизичный `dt`, который
     цикл никогда не передаёт.
   - (в) проверку «поле пусто» оставить в коде без прямого теста, а критерий закрыть
     тестом-инвариантом «к тику появления поле всегда пусто» (симуляция в 027).
     Вопрос к архитектору (технический; владельцу — только если архитектор не закроет).
2. **Тест `ASTEROID_SIZE` = размер спрайта** — переносится в 026 (спрайт там). Решение
   по нарезке, подтверждения не требует; зафиксировано, чтобы `/do` не создавал спрайт
   раньше времени.
3. **Мелочи вне рамок 2а (не блокируют):** `BONUS_FALLBACK_POINTS` по дизайну живёт в
   `score.ts`, но нужен только в 027 — добавлять там; строку `score.ts` в
   `architecture/overview.md` (`killPoints` → `levelPoints`/`asteroidPoints`) по нарезке
   обновляет 027 — рекомендую поправить уже в этой задаче, раз меняется сама формула
   (одна строка, без новых модулей).
