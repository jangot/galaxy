# Анализ: Покачивание строя и ADR 003

## Общее описание функциональности

Строй врагов, неподвижный после задачи 006, начинает плавно покачиваться
влево-вправо: от центра вправо до `+16` px, разворот, влево до `-16` px, разворот и так
далее. Все враги в строю двигаются вместе (позиция каждого — слот строя). На уровне 1
скорость — 15 px/с, то есть 1/4 px за тик: спрайт сдвигается ровно на 1 px каждые
4 тика, полный размах (32 px) — за 128 тиков (~2,1 с), полный цикл туда-обратно —
256 тиков (~4,3 с).

Такая скорость меньше 1 px/тик и нарушает ADR 002 («целые px/тик»), поэтому вводится
**ADR 003**: для медленных движений разрешены двоичные дроби `1/2`, `1/4`, `1/8` px/тик
(30, 15, 7,5 px/с), а таймеры считаются в целых тиках. Правило закрепляется функцией
`isAllowedSpeed` и тестом каждой строки `LEVELS`.

Рамка — согласованный `design.md` фичи 002 (разделы «Сущности и состояния» →
«Правило скоростей и таймеров», «Formation», «Поток тика», «Интерфейсы»,
«Тестирование», «Уточнения для реализации» → «Появление API по задачам», строка 007).
Анализ уточняет его по коду, не перепроектирует.

## Модели данных и состояние

**`LevelConfig`** (`src/game/levels.ts`) — добавляется обязательное поле:

| Поле        | Тип      | Смысл                                                    | Значение                                  |
| ----------- | -------- | -------------------------------------------------------- | ----------------------------------------- |
| `swaySpeed` | `number` | скорость покачивания, px/с; px/тик ∈ {1/8, 1/4, 1/2} ∪ ℕ | уровень 1 — `15`; тестовые таблицы — `15` |

**`Formation`** (`src/game/formation.ts`) — к геометрии 006 добавляется состояние:

| Поле / член       | Смысл                                                                                                                                  | Старт        |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `swaySpeed`       | из конструктора, px/с                                                                                                                  | —            |
| `offset` (getter) | текущее смещение строя по X, px (дробное)                                                                                              | `0`          |
| `dir` (private)   | направление `-1 \| 1`                                                                                                                  | `1` (вправо) |
| `update(dt)`      | `offset += dir * swaySpeed * dt`; при выходе за `±SWAY_RANGE` — обрезка ровно до границы и смена знака `dir` (как зажим корабля в 001) | —            |
| `slotX(col, w)`   | как в 006 **плюс `offset`**                                                                                                            | —            |
| `slotY(row, h)`   | без изменений (покачивание только по X)                                                                                                | —            |

Конструктор: `Formation(cols, rows, swaySpeed)` (в 006 — `Formation(cols, rows)`).

**Константы:**

| Константа        | Где            | Значение               | Откуда              |
| ---------------- | -------------- | ---------------------- | ------------------- |
| `SWAY_RANGE`     | `formation.ts` | `16` px                | В9                  |
| `swaySpeed` ур.1 | `LEVELS[0]`    | `15` px/с (1/4 px/тик) | В1, «точные строки» |

**`isAllowedSpeed(pxPerSecond)`** (`levels.ts`): `pxPerSecond * TICK_SECONDS` — целое
≥ 1 или ровно `1/2`, `1/4`, `1/8`. Проверено в double: `15 * (1/60) === 0.25`,
`30 * (1/60) === 0.5`, `7.5 * (1/60) === 0.125`; `90 * (1/60) === 1.5` — не целое,
`20` → `1/3` — не точная дробь, `45` → `0.75` — не из списка.

**Тайминги покачивания (15 px/с, проверено прогоном):** смещение кратно 1/4, сумма в
double точна; `offset === 16` ровно на 64-м тике, `-16` — на 192-м, `0` — на 256-м.

> **Заменено решением архитектора** (discussion.md, «Реализация: задача
> 007-formation-sway»; design.md «Точные правила → Разворот покачивания»): правило
> разворота — `step = swaySpeed * dt`, `minOffset = -SWAY_RANGE`, `maxOffset =
SWAY_RANGE + Math.max(0, 1 - step)`. Для 15 px/с: `+16` впервые на тике 64, `16.75` и
> разворот — 67, `-16` и разворот — 198, `0` с `dir = 1` — 262 (период 262); края `±16`
> по 7 тиков, середина по 4 за проход. Числа выше («`-16` на 192», «0 на 256», «65-й —
> 15.75» в таблице файлов) неверны — действуют новые (см. `plan.md`).

Состояния врага не меняются (`'formation'` — единственное). `Enemy.update()` уже
пересчитывает `x/y` из `formation.slotX/slotY` каждый тик — враг автоматически следует
за покачиванием; `x` становится дробным (рендер уже делает `Math.floor`).

## Точки встраивания

- **Цикл:** `main.ts` → `GameLoop(TICK_SECONDS)` вызывает `scene.update(dt)` с
  постоянным `dt = TICK_SECONDS` (`src/engine/loop.ts:61`) → `PlayScene.update` →
  `battle.update(dt, intent)` → `wave.update(dt)`. Цепочка уже передаёт `dt`, ничего
  в сцене, бое и цикле не меняется.
- **`Wave.update(_dt)` → `update(dt)`:** первым шагом `formation.update(dt)`, затем
  цикл `enemy.update()` (порядок по «Поток тика», п. 2.1 → 2.3). Враги берут слот уже
  сдвинутого в этом тике строя.
- **`Wave` конструктор:** `new Formation(layout.cols, layout.rows, config.swaySpeed)`.
- **Отрисовка:** без изменений — `battle-render.ts` уже рисует `Math.floor(e.x)`.
- **Ввод, HUD:** не затрагиваются.
- **Валидация таблицы:** `levels.test.ts`, блок `describe('LEVELS')` (`it.each` по
  строкам) — добавить `isAllowedSpeed(swaySpeed)`.

## Тестируемость

Покрывается unit-тестами без canvas (детерминизм: `dt = TICK_SECONDS`, `Rng` не
участвует):

- `isAllowedSpeed` — таблица значений (да/нет), включая граничные `0`, отрицательные
  (нет).
- Валидация `LEVELS` (`it.each`): `isAllowedSpeed(swaySpeed)`.
- `Formation`: шаг за один тик; точное попадание на `±SWAY_RANGE` через заданное число
  тиков (`toBe`, двоичные дроби точны); разворот (следующий тик — шаг назад); `slotX`
  включает `offset`, `slotY` нет; инвариант экрана при обоих крайних смещениях; для
  целой скорости, не кратной размаху (напр. 180 px/с = 3 px/тик) — обрезка ровно до
  границы.
- `Wave`/`Enemy`: враги в `formation` следуют за `offset`; `y` не меняется; порядок
  «строй, потом враги» — позиция врага в тике совпадает со слотом этого же тика.
- `Battle`: обновлённый тест одного тика.

Только визуально: «строй качается ровно, без подёргивания» — `npm run dev`, титул →
Enter; ожидается сдвиг на 1 px каждые 4 тика, разворот у краёв (см. риск в «Открытых
вопросах» про кадр на правом краю).

## Зависимости и ограничения

- Зависит от 006 (код в рабочем дереве, не закоммичен; ждёт только приёмки спрайтов —
  на 007 не влияет).
- Разрешение 256×240: строй максимальной ширины (11 столбцов) при `±16` остаётся в
  экране (24 … 232); уровень 1 (10 столбцов, `baseX = 48`) — 32 … 224.
- Фиксированный шаг 60 тиков/с: `dt` всегда `1/60`, поэтому точность двоичных дробей
  гарантирована. Если когда-нибудь появится переменный `dt`, правило ADR 003 перестанет
  работать — это и фиксирует ADR.
- `LevelConfig.swaySpeed` — обязательное поле: все литералы конфигов в тестах
  (`wave.test.ts`, `levels.test.ts`, `test-levels.ts`) должны его получить, иначе
  `typecheck` упадёт.
- `levels.ts` перестаёт быть «без импортов» (импорт `config`) — по графу дизайна
  допустимо, циклов нет (`config` — лист).
- Инвариант `swaySpeed < STEER_SPEED` — **не в этой задаче** (009), как сказано в
  `description.md`.
- Производительность: одно сложение за тик на строй, без изменений в рендере.

## Открытые вопросы

Вопросов к владельцу нет: числа (15 px/с, ±16 px, старт вправо) и правило разворота
заданы согласованным дизайном (В1, В9).

Технический риск для plan/приёмки (не меняет дизайн):

1. **Асимметрия краёв после `Math.floor`.** Прогон правила дизайна (15 px/с, обрезка до
   `±16`, разворот) даёт по видимым пикселям: в середине каждое смещение держится ровно
   4 тика, но на правом краю `+16` показывается **1 тик** (15 → 16 → 15), а на левом
   `-16` держится **7 тиков**. Причина — `floor` несимметричен для отрицательных
   значений (`floor(-15.25) = -16`). Это однокадровый сдвиг на 1 px при развороте
   вправо; вероятно, малозаметно, но критерий «без подёргивания» проверяется глазами.
   Предложение: реализовать по дизайну (тест `toBe` на ровных границах), владелец
   смотрит при приёмке; если кадр на правом краю заметен — отдельной правкой сменить
   правило разворота (напр. сдвинуть видимый размах до `[-16, +15]`), не меняя API.
   **Решено архитектором:** симметричный разворот с `maxOffset = SWAY_RANGE +
max(0, 1 - step)` (края по 7 тиков при 15 px/с), на приёмку не откладывается.
2. ADR 002 — добавлять ли в него ссылку «расширено ADR 003» (по умолчанию —
   добавить одну строку; решение в plan). **Решено архитектором:** добавить строку.

Частей, которые стоит вынести в отдельную задачу, нет.
