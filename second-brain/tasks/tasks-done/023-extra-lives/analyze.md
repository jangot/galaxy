# Анализ: Доп. жизни за очки

## Общее описание функциональности

Задача 4 нарезки фичи 005 (`second-brain/features/005-lives-score-game-over/design.md`,
согласован, раунд 3). Игрок получает дополнительную жизнь, когда счёт пересекает порог:
5000, затем каждые 10000 (15000, 25000, …) — решение владельца В4. Жизнь прибавляется
сразу, в тик попадания, принёсшего очки: в верхней панели в том же кадре появляется
новая иконка корабля. Запас — не больше `MAX_LIVES = 5`; если запас полон, доп. жизнь
пропадает, а порог считается пройденным (следующая — на следующем пороге).

Особый эффект: если последний корабль уже сбит (`lives === 0`, `down`), а выстрел,
выпущенный им до гибели, сбивает врага и пересекает порог, жизнь становится 1 и корабль
возрождается по обычному таймеру `DOWN_TICKS` — Game Over не наступает. Особого случая в
коде для этого нет: это следствие правила «возрождение, если `lives > 0`», которое
проверяется в тик таймера.

Для игрока это выглядит так: набрал 5000 — справа в панели появилась ещё одна иконка;
при пяти иконках новые не появляются.

## Модели данных и состояние

Новые константы и операции (имена — по `design.md`, раздел «Интерфейсы»):

| Что                       | Где         | Значение / поведение                                                                                                                |
| ------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `MAX_LIVES`               | `player.ts` | 5 — предел запаса жизней (В4)                                                                                                       |
| `Player.addLife()`        | `player.ts` | `lives = min(lives + 1, MAX_LIVES)` в любом состоянии; ни состояние, ни `stateTicks` не трогает                                     |
| Конструктор `Player`      | `player.ts` | `lives` — целое, `1 ≤ lives ≤ MAX_LIVES`, иначе `RangeError` (сейчас проверяется только `≥ 1`)                                      |
| `EXTRA_LIFE_FIRST`        | `score.ts`  | 5000 — первый порог                                                                                                                 |
| `EXTRA_LIFE_EVERY`        | `score.ts`  | 10000 — шаг следующих порогов                                                                                                       |
| `thresholdsReached(s)`    | `score.ts`  | `s < 5000 ? 0 : floor((s − 5000) / 10000) + 1`; внутренняя (экспорт — на усмотрение, если удобнее для теста)                        |
| `extraLivesEarned(b, a)`  | `score.ts`  | `thresholdsReached(a) − thresholdsReached(b)` — число порогов, пройденных за одно начисление; чистая функция, без предела по жизням |
| `Battle.addScore(points)` | `battle.ts` | сейчас `score += points`; станет: запомнить `before`, прибавить, затем `extraLivesEarned(before, score)` раз `player.addLife()`     |

Состояние не добавляется: пройденные пороги не хранятся отдельно — они выводятся из
счёта (`before`/`after`). Счёт только растёт (`addScore` с положительными `killPoints`),
поэтому `extraLivesEarned ≥ 0` на всех реальных вызовах.

Автомат корабля не меняется (`player.ts`): `down → invulnerable` уже требует
`livesLeft > 0 && ticksInState >= DOWN_TICKS` (`player.ts:120`). `addLife()` в `down`
при 0 жизнях делает условие истинным, и возрождение происходит в обычный тик
`DOWN_TICKS` от момента попадания (не от момента `addLife`).

Сопутствующее (уже есть, проверено по коду):

- `LIVES_ICON_SLOTS = 5` (`hud.ts`), `drawLives` рисует `min(lives, LIVES_ICON_SLOTS)`
  (`hud-render.ts:54-60`) — сделано в задаче 020. Нужна только проверка
  `LIVES_ICON_SLOTS >= MAX_LIVES` тестом.
- `isLost` = `lives === 0`; `Battle.updatePhase` переходит в `over` по
  `player.isLost && player.stateTicks >= GAME_OVER_DELAY_TICKS` — после `addLife` в
  `down` условие ложно, и `over` не наступает.

## Точки встраивания

- **Цикл боя** (`Battle.update`, `battle.ts`): после `resolveCollisions` для каждого
  `kill` вызывается `addScore(killPoints(kill, level))` — только в фазе `playing`. Хук доп.
  жизней — внутри `addScore`; комментарий в коде уже указывает это место («task 023 hooks
  extra lives in here»). Других мест изменения счёта нет.
- **Порядок «гибель → доп. жизнь» в одном тике.** `player.hit()` вызывается внутри
  `resolveCollisions` (правила 2 и 3, `collisions.ts:83`, `:96`), а `addScore` — после
  возврата списка убийств. Значит, при таране последним кораблём или одновременном
  попадании по кораблю и убийстве врага сначала списывается жизнь, потом начисляется
  доп. — при полном запасе (5) жизнь не теряется зря (5 → 4 → 5). Отдельной логики не
  нужно, но порядок стоит зафиксировать тестом или комментарием.
- **Фазы.** `updatePhase` идёт после начисления очков, проверка `over` — первой; после
  `addLife` в `down` `isLost` уже ложно. В `over` коллизий и начислений нет, поэтому
  доп. жизнь после Game Over невозможна.
- **Отрисовка/HUD.** Изменений нет: `hudView` читает `battle.player.lives` каждый кадр,
  иконка появится сама.
- **Ввод, сцены.** Не затрагиваются.

## Тестируемость

Всё поведение — чистая логика, покрывается unit-тестами без canvas:

- **`extraLivesEarned`** — чистая функция, таблица значений из `design.md` («Тестирование»).
- **`Player.addLife`** — напрямую: рост до 5 и не выше; в `down` при 0 — `isLost`
  становится ложным, возрождение в тик `DOWN_TICKS` от попадания (`run(player, DOWN_TICKS − 1)`
  → `down`, ещё 1 → `invulnerable`), `addLife` не перезапускает таймер; в `active`/
  `invulnerable` состояние не меняется.
- **Конструктор** — `RangeError` на `MAX_LIVES + 1`.
- **`Battle`** — главная трудность: `addScore` private, а набрать 5000 обычными
  убийствами в тесте долго (920 очков за весь строй 1-го уровня). Рабочий путь без
  изменения API — высокий `startLevel` на пассивной тестовой таблице: эскалация
  `levelConfig` сокращает таймеры относительно последней строки и оставляет
  `ONE_CORNER_ENEMY` пассивным (`escalate` — `min(last, …)`, у `PASSIVE` таймеры
  1 000 000, а шаг 6 тиков за уровень). Надбавка без потолка: `drone` в строю даёт ровно
  5000 на уровне 1656 (`floor((30·1665 + 50)/100)·10 = 5000`; на 1655 — 4990). Тогда:
  - «пересечение 5000»: `{ levels: ONE_CORNER_ENEMY, startLevel: 1656 }`,
    `shootCornerEnemy` → `score === 5000`, `lives === START_LIVES + 1`;
  - «предел»: то же с `lives: MAX_LIVES` → `lives === MAX_LIVES`;
  - «доп. жизнь в `down` отменяет Game Over»: `lives: 1`, выстрел выпущен, затем
    `player.hit()` до попадания (как в `player.test.ts` «lets the shot in flight fly
    on…»), выстрел сбивает врага → `lives === 1`, `isLost` ложно; через
    `GAME_OVER_DELAY_TICKS`/`DOWN_TICKS` — фаза не `over`, корабль `invulnerable`;
  - «несколько порогов за одно начисление» — в `Battle` достижимо так же (уровень,
    на котором одно убийство даёт ≥ 15000), но достаточно и таблицы в `score.test.ts`
    (0 → 25000: 3). Выбор — в плане.
    Конкретный уровень и способ (вычислить в тесте через `killPoints` или зашить
    константу с комментарием) — решение стадии plan; менять API `Battle` ради теста
    (`BattleOptions.score` и т.п.) дизайн не предусматривает.
- **HUD**: `LIVES_ICON_SLOTS >= MAX_LIVES` — тест-инвариант в `hud.test.ts`.

Только глазами (без отдельной приёмки, по `description.md`): `npm run dev` с `?level=N`
(напр. `?level=50`: целый строй ≈ 5000+ очков), набрать 5000 — появляется новая иконка.

## Зависимости и ограничения

- Зависит от 020 (жизни, `over`) и 022 (счёт, `addScore`) — обе реализованы в рабочем
  дереве (не закоммичены); 021 (экран Game Over) на результат не влияет, но тоже в
  рабочем дереве — задача ложится поверх всех трёх.
- Производительность не затронута: `extraLivesEarned` — несколько целочисленных операций
  на убийство (не больше двух убийств за тик).
- Целочисленность: счёт целый, пороги целые, `Math.floor` от неотрицательного — без
  float-ловушек.
- `addLife()` — публичный и работает «в любом состоянии». Из `Battle` в `over` он не
  вызывается (коллизий нет), но прямой вызов снаружи в `over` вернул бы корабль при
  терминальной фазе боя. Дизайн это допускает; вне `Battle` `addLife` никто не зовёт —
  можно отметить в JSDoc.
- Возрождение после доп. жизни в `down` идёт по таймеру от попадания; выстрел после
  гибели долетает до верха максимум за 51 тик (< `DOWN_TICKS` 60, подтверждено в
  дизайне), так что `addLife` всегда успевает до тика возрождения/`over`.

## Открытые вопросы

Нет. Все игровые числа решены владельцем (В4) и закреплены в `design.md`; поведение
крайних случаев (полный запас, несколько порогов, доп. жизнь после гибели последнего
корабля) описано там же. Расхождений дизайна с кодом не найдено: хук `addScore`,
ограничение `drawLives` и условие возрождения `lives > 0` уже на месте.

Решения для стадии plan (не к владельцу): экспортировать ли `thresholdsReached`; способ
набрать 5000 в `battle.test.ts` (высокий `startLevel`, см. «Тестируемость»).
