# Анализ: Плавный рост скорости по уровням

Код: `main`, `d68f8f5`. Базовый прогон: `npm test` — 19 файлов, 432 теста, зелёные.

## Общее описание функциональности

Сейчас `diveSpeed` по уровням идёт 60 → 120 → 120 → 120 → 180 px/с: удвоение уже на 2-м
уровне, потом плато, а за концом таблицы (`N > 5`) `levelConfig` отдаёт последнюю строку
как есть, и сложность больше не растёт. Задача:

1. Сделать скорость пике ровной: 60 / 90 / 120 / 150 / 180 px/с (1; 1,5; 2; 2,5; 3 px/тик).
   Половинный шаг разрешается **только для вертикали пике**, это фиксирует новый ADR 004
   (расширяет ADR 002). Вертикальный шаг при 90 и 150 px/с чередуется 1-2-1-2 / 2-3-2-3 px
   (после `Math.floor`). Владелец принимает это на приёмке глазами, запасной вариант есть
   (см. «Открытые вопросы» в `description.md`).
2. Продолжить рост после 5-го уровня через темп атак: `diveIntervalTicks` и
   `firstDiveDelayTicks` уменьшаются на 6 тиков за уровень до пола 30 / 60 (пол — на 10-м
   уровне). Остальные поля — как у 5-го уровня.

`swaySpeed` (15/15/30/30/30), раскладки, `maxSorties`, выстрелы не меняются.

**Главный риск проверен: окно уходимости `striker` есть при всех четырёх скоростях.**
Временный тест (удалён после замера, в `src/` ничего не осталось) прогнал `turnY` = 50..200
с шагом 1 тремя способами: мини-симуляция `steering.test.ts` с `T = 0` и с `T = 8`,
настоящий `Enemy` (`afterPeel('striker')` + `runEvasion`). Старт — `EVASION_START`.
Окно — это `turnY`, при которых финт с `T = 0` даёт таран, а с `T = 8` (и в симуляции, и
на настоящем `Enemy`) уходит:

| `diveSpeed` | px/тик | стоящий корабль (`T = 0`, `T = 8`, `Enemy`) | окно `turnY` (целые) | середина → `turnY` |
| ----------- | ------ | ------------------------------------------- | -------------------- | ------------------ |
| 60          | 1      | ram / ram / ram                             | 139–142              | (не в тестах)      |
| 90          | 1,5    | ram / ram / ram                             | 136–146 (11)         | **141**            |
| 120         | 2      | ram / ram / ram                             | 128–141 (14)         | 135 (как сейчас)   |
| 150         | 2,5    | ram / ram / ram                             | 120–137 (18)         | **128**            |
| 180         | 3      | ram / ram / ram                             | 111–131 (21)         | 125 (как сейчас)   |

Окна сплошные. Результат финта с `T = 8` в симуляции и на настоящем `Enemy` совпал для
всех `turnY` и скоростей. В задаче 016 окна мерили шагом 10 («120..130», «130..140»);
точный замер шире, текущие `turnY` 125 и 135 в него попадают. Одной общей высоты для всех
четырёх скоростей нет: 90, 120 и 150 пересекаются только на 136–137, а у 180 окно
заканчивается на 131. Так что `turnY` у каждой скорости свой, как и задумано.

Дробный `y` на точность не влияет: `90 · (1/60)` = 1,5 и `150 · (1/60)` = 2,5 в double
точно, сумма 200 шагов даёт ровно 300 / 500 (проверено в node). Половинки — двоичные дроби,
ошибка не копится (тот же довод, что в ADR 003).

## Модели данных и состояние

`LevelConfig` (`src/game/levels.ts`) — состав полей не меняется, меняются значения и
правило проверки:

| Уровень | `diveSpeed` было → станет | px/тик | `firstDiveDelayTicks` | `diveIntervalTicks` |
| ------- | ------------------------- | ------ | --------------------- | ------------------- |
| 1       | 60 → 60                   | 1      | 180                   | 180                 |
| 2       | 120 → **90**              | 1,5    | 150                   | 150                 |
| 3       | 120 → 120                 | 2      | 120                   | 120                 |
| 4       | 120 → **150**             | 2,5    | 120                   | 90                  |
| 5       | 180 → 180                 | 3      | 90                    | 60                  |
| 6 (k=1) | = 5                       | 3      | 84                    | 54                  |
| 7 (k=2) | = 5                       | 3      | 78                    | 48                  |
| 8 (k=3) | = 5                       | 3      | 72                    | 42                  |
| 9 (k=4) | = 5                       | 3      | 66                    | 36                  |
| 10+     | = 5                       | 3      | 60 (пол)              | 30 (пол)            |

Новые константы (имена по description — `ESCALATION_*`): шаг 6 тиков, пол интервала 30,
пол первой задержки 60. Все значения — целые тики (ADR 003).

Новая функция-правило `isAllowedDiveSpeed(pxPerSecond)`: `perTick = px/с · TICK_SECONDS`,
`perTick ≥ 1` и `perTick · 2` — целое. Допускает 60, 90, 120, 150, 180; отвергает 0, < 0,
45 (0,75), 75 (1,25), NaN, Infinity. `isAllowedSpeed` (для `swaySpeed`) не меняется — он
по-прежнему отвергает 90.

Инварианты, которые держат потолок 180 (код не меняется, проверяют тесты для уровней 1..20):

- `ENEMY_SHOT_SPEED = 240 > diveSpeed` (`src/game/enemy-shot.ts:10`);
- туннелирование: `SHOT_SPEED · dt + max(diveSpeed · dt, PEEL vy ≤ 3, RETURN 1) <
SHOT_HEIGHT + min высота врага`. Максимум по-прежнему 3 px/тик, запас не меняется;
- уходимость `striker` — таблица выше.

## Точки встраивания

- Сцены, цикл, ввод, HUD — не затрагиваются.
- Всё изменение — в данных уровня и в `levelConfig`: `Battle.createWave()` уже вызывает
  `levelConfig` на каждый новый уровень, так что эскалация попадёт в игру без правок
  `battle.ts` (только комментарий).
- `?level=N` (`parseStartLevel`) уже пропускает любое `N ≥ 1`, поэтому `?level=6`+ для
  приёмки работает сразу. JSDoc там («levelConfig repeats the last one») нужно поправить.

## Тестируемость

Unit-тестами покрывается всё, кроме ощущений:

- `isAllowedDiveSpeed`: допустимые 60/90/120/150/180, недопустимые 0, −60, 45, 75, NaN,
  Infinity.
- `levelConfig(N)` для N = 1..20: строки 1–5 — ровно `LEVELS[N−1]`; за концом таблицы
  `diveSpeed`, `swaySpeed`, `layout`, `maxSorties`, выстрелы — как у последней строки;
  тайминги по формуле: 6 → 84/54, 9 → 66/36, 10 и 20 → 60/30. Монотонность: `diveSpeed`
  не убывает, оба тайминга не растут. Чистота: два вызова с одним `N` дают равные значения.
- Правила скоростей, таймеров, туннелирования и `ENEMY_SHOT_SPEED > diveSpeed` — для
  `levelConfig(1..20)`, а не только для `LEVELS`.
- Уходимость: `EVASION_CASES` с 90/141 и 150/128 — в `enemy.test.ts` (настоящий `Enemy`) и
  `steering.test.ts` (контроль `T = 0`). Замер выше показывает, что оба проходят.
- Дробный `y`: `it.each([60, 90, 120])` в `enemy.test.ts`.
- Только глазами: заметна ли дрожь 1-2-1-2 на уровнях 2 и 4 (`?level=2`, `?level=4`),
  ровно ли растёт скорость 1→5, чаще ли атаки на `?level=6`+.

## Зависимости и ограничения

- Фиксированный шаг `dt = TICK_SECONDS` (ADR 003): правило половинного шага держится на нём.
- Интервал 30 тиков при `maxSorties = 3` — это ограничение «не больше 3 в полёте», а не
  поток в 2 вылета/с. Отдельной нагрузки нет: врагов столько же, сколько в 5-й волне.
- Выстрел врага стартует с дробного `y` (`wave.ts:90`: `enemy.y + enemy.height`): при 90 и
  150 это x,5. `EnemyShot` двигается на 4 px/тик, рендер и коллизии делают `floor` —
  ничего не ломается, просто выстрел может стоять на полпикселя ниже/выше, чем раньше
  (заметно только глазами, на тесты не влияет: тесты выстрелов работают на целых скоростях).
- Риск — визуальная дрожь половинного шага; запасной вариант описан в `description.md`.

## Открытые вопросы

1. **Эскалация для подставных таблиц (к архитектору, не блокирует).** Формула в
   description записана в абсолютных числах (`max(30, 60 − 6·k)`, `max(60, 90 − 6·k)`,
   `k = N − 5`). Но `levelConfig(level, levels)` принимает и тестовые таблицы, а у
   `passiveLevel` тайминги 1 000 000 тиков (`test-levels.ts:8-9`), чтобы враги не вылетали.
   Если применять абсолютную формулу к любой таблице, то `ONE_CORNER_ENEMY` и `TWO_LEVELS`
   за концом таблицы станут «активными» (первый вылет через 84 тика), и тесты сцены/боя,
   которые проходят уровни, начнут получать пикирующих врагов.
   Варианты:
   - (а, рекомендую) считать относительно последней строки переданной таблицы:
     `k = N − levels.length`, тайминг = `max(ПОЛ, последний − 6·k)`, но не больше
     последнего. Для `LEVELS` (60/90) это ровно формула владельца, а пассивные таблицы
     остаются пассивными.
   - (б) абсолютная формула только для `LEVELS`; для подставной таблицы — повтор
     последней строки как сейчас. Минус — два поведения в одной функции.
   - (в) абсолютная формула для любой таблицы, `k = N − levels.length`; переписать
     тесты боя/сцены, которые заходят за конец тестовой таблицы.
2. **`battle.test.ts` не упомянут в description.** Два теста (строки 76–80 и 117–126)
   сравнивают через `toBe` и упадут. Правка — в рамках задачи (это тесты того же
   поведения «за концом таблицы»): ожидать `toEqual` с последней строкой с поправкой на
   эскалацию или проверять `layout`/`diveSpeed`. Отдельная задача не нужна.
3. Запасной вариант при заметной дрожи (из description) — решается на приёмке, на анализ
   не влияет.
