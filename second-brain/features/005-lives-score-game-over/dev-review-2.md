## Рекомендации

1. **В тестах задачи 2 есть проверка `score === 0`, а `Battle.score` появляется только в
   задаче 3.** В «Тестирование», `title-scene.test.ts`, полный цикл заканчивается так:
   «новая `PlayScene` … `score === 0`, `player.lives === START_LIVES`». Это тест задачи 2
   (фабрика выхода, `TitleScene(rng, startLevel, starfield)`). Задача 2 по нарезке зависит
   только от задачи 1, поэтому `battle.score` в ней ещё не существует, и тест не
   скомпилируется (`tsc`). Предложение: в задаче 2 проверять тот же `starfield` и
   `player.lives === START_LIVES`, а `score === 0` добавить в этот тест в задаче 3 (одна
   строка; записать её в список тестов задачи 3).

2. **Prettier сломал смысл строки про предел тиков в тесте `title-scene`.** В
   `design.md` (раздел «Тестирование», пункт `title-scene.test.ts`) текст «≤ 3 × 180 + 60
   тиков» перенёсся так, что `+ 60` оказалось в начале строки. Markdown прочитал это как
   пункт списка, а Prettier заменил `+` на `-`. Теперь там «≤ 3 × 180» и вложенный пункт
   «- 60 тиков …», и весь хвост пункта (`→ start → TitleScene …`) уехал во вложенный
   список. Предложение: переписать без арифметики в начале строки, например «(предел в
   тесте — 600 тиков; на деле `over` наступает на ~420-м: 2 × (60 + 120) + 60)». Число
   тоже стоит поправить: при трёх жизнях циклов «down + invulnerable» два, а не три.
   Мелочь того же рода, смысл не страдает: переносы внутри `` `…` `` в строках 15–17,
   89–91, 572–573 сбивают отступ пункта.

3. **Тест надбавки не отличит целочисленную формулу от float, если в нём только
   нынешняя таблица.** Я пересчитал таблицу контрольных значений по формуле
   `floor((base × (9 + level) + 50) / 100) × 10`: все 36 значений совпадают с
   `design.md`. Но на уровнях 1–11 float-вариант
   `Math.round(base * (1 + 0.1 * (level - 1)) / 10) * 10` даёт **те же** числа. Значит,
   тест из дизайна пройдёт и при float-реализации, и защиты, ради которой выбрана
   целочисленная формула, не будет. Расхождения на уровнях 1–100 (базы 30…100) я нашёл
   перебором, их три, все у базы 50 (`raider` в строю):

   | уровень | целые | float |
   | ------- | ----- | ----- |
   | 14      | 120   | 110   |
   | 32      | 210   | 200   |
   | 78      | 440   | 430   |

   (`50 × 2.3 = 114.99999…`.) Предложение: добавить в `score.test.ts` случай
   «`raider` в строю, уровень 14 → 120 (float-ловушка)». Тогда выбор формулы закреплён
   тестом, а не только текстом дизайна. Уровень 14 достижим (`levelConfig` наращивает
   уровни дальше таблицы).

4. **Уточнить «`phaseTicks` = 0 в первом тике» для начала боя.** В разделе «Фазы
   `Battle`» стоит: «В начале боя (`playing` уровня `startLevel`) — 0 в первом тике».
   Вход в эту фазу происходит в конструкторе, а не в тике. По правилу «+1 каждый
   следующий тик» после первого `update` значение будет 1, как у
   `Player.stateTicks` (`player.ts:96`: `ticksInState++` в начале `update`). Предлагаю
   сформулировать так: «0 после конструктора; в тике, где произошёл переход в фазу, — 0
   после этого `update`; каждый следующий `update` +1». Реализация, которая это даёт и
   сохраняет текущее поведение `cleared` (`battle.ts:93-106`): `ticksInPhase++` в начале
   `updatePhase`, затем проверки (`over` первым), и каждый переход ставит 0. Тогда
   `playing → cleared` и `cleared → playing === LEVEL_PAUSE_TICKS` работают как сейчас,
   и тесты `battle.test.ts:96-107` не меняются. Условие `over` — через `>=`, как в
   дизайне. В `over` переход повторно не срабатывает, потому что фаза терминальная и
   проверка `over` идёт только из `playing | cleared`.

5. **Обоснование «гонка `over` против `cleared → playing` недостижима» можно сделать
   точнее (вывод верен).** В дизайне со ссылкой на меня написано «16 + 90 > 60». Но 16
   тиков от гибели до `cleared` — не нижняя граница. Последнего врага можно сбить
   раньше, а корабль погибнет от вражеского выстрела, который ещё летит, и тогда
   `cleared` наступит через 0–15 тиков после гибели. Общий довод: корабль гибнет только
   в `playing` (коллизии), значит гибель не позже входа в `cleared`, и
   `cleared → playing` наступает не раньше чем через 90 тиков после гибели, а 90 > 60.
   Это правка текста, не кода.

## Подтверждено

- **Таблица контрольных значений** (`drone`/`striker`/`raider`, уровни 1, 2, 3, 5, 6, 11)
  совпадает с формулой во всех 36 клетках. Пример владельца (`drone` 5 → 40 / 80,
  11 → 60 / 120) и «половина вверх» (`drone` 6 → 50) верны. Формула монотонна по уровню
  (`base × (9 + level)` растёт), на уровне 1 для баз, кратных 10, возвращает базу.
  Целочисленное деление в JS здесь точное: `base × (9 + level) + 50` — небольшое целое.
- **Довод против float подтверждён числами** (см. рек. 3): расхождение реально есть,
  например `raider` на уровне 14.
- **`Kill` без `cause`.** Убийства — только в `hitByPlayerShot` и `ram`
  (`collisions.ts:53-90`). В обоих `kind` и `isOut` читаются до `kill()`, и в `ram`
  `isOut` всегда `true` (`collisions.ts:83`). `inFlight` полностью покрывает В1. Порядок
  «правило 1 раньше правила 3» в одном тике достижим (выстрел сбивает одного, другой
  таранит), тест на порядок осмыслен.
- **Импорты без цикла.** `score.ts` берёт `import type { Kill }` из `collisions.ts` и
  `EnemyKind` из `levels.ts` (`enemy.ts:4` берёт его оттуда же). `collisions.ts` ничего
  не берёт из `score.ts`. `battle.ts` импортирует оба.
- **Уровень для надбавки** — `currentLevel` в момент `addScore`. Коллизии идут только в
  `playing` (`battle.ts:76`), а уровень меняется только в `cleared → playing`, так что
  очки всегда считаются по уровню, на котором враг сбит. Dev-старт `?level=N` попадает в
  `startLevel` (`main.ts:19-22` → `TitleScene` → `PlayScene` → `Battle`).
- **Удаление `levelClearBonus`** упрощает задачу 3: `playing → cleared` в
  `battle.ts:95-99` счёт не трогает, проверка «переход счёт не меняет» сводится к
  сравнению до/после.
- **Общий `phaseTicks`.** Схема из рек. 4 сохраняет текущий момент `cleared → playing`
  (тик `LEVEL_PAUSE_TICKS` после входа). Private-поле `phaseTicks` сейчас в тестах не
  используется (`grep`), так что переименование в `ticksInPhase` ничего не ломает.
- **`player` в конструкторе `Battle`.** `new Player(undefined, lives)` работает с
  параметром по умолчанию `ship: Ship = new Ship()` (`player.ts:41`). Остальные вызовы
  `new Player()` (`collisions.test.ts`, около 20) не меняются: `lives` по умолчанию
  `START_LIVES`.
- **`START_LIVES = 3` не ломает существующие тесты.** Каждый тест с `hit()`
  (`player.test.ts`, `battle-render.test.ts`, `battle.test.ts:218`,
  `collisions.test.ts`) бьёт корабль один раз. Длинных прогонов, где корабль погиб бы
  трижды и перестал бы возрождаться, нет: самый длинный — `battle.test.ts:185`
  (`1 + P + 160` тиков).
- **Перенос `addLife`/`MAX_LIVES` в задачу 4** согласован везде: модули, интерфейсы
  (`// --- task 4 ---`), тесты, нарезка. В задаче 3 `addScore` — просто `score += p`.
- **Подложка.** `recorder()` (`canvas-test-utils.ts`) пишет каждый `fillRect` вместе с
  `fillStyle` и в порядке вызовов. Этого хватает для проверок: подложка чёрная, лежит
  внутри расширенного на `GAME_OVER_BACKDROP_PAD` прямоугольника, рисуется до текста и
  остаётся при скрытом `PRESS ENTER`. `drawText` (`font.ts:52-69`) рисует только
  `fillRect` 1×1 внутри ячеек, так что тест «только внутри прямоугольников строк»
  выполним. Параметр `backdrop` с умолчанием `GAME_OVER_BACKDROP` позволяет проверить обе
  ветки, не трогая модульную константу.
- **Цвета и текст.** `HUD_LABEL_COLOR` / `HUD_VALUE_COLOR` есть в `art.ts:42-44`, глифы
  для `GAME OVER` / `PRESS ENTER` есть в шрифте.
- **`hud.test.ts:22-23, 44-56`** — места правки указаны верно. `PLACEHOLDER_LIVES`
  уходит в задаче 1, а `PLACEHOLDER_SCORE` в `hudView` и тесте остаётся до задачи 3.
