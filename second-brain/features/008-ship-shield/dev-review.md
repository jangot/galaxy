## Рекомендации

1. **Цикл импортов, если `art.ts` возьмёт `MAX_SHIELD` из `player.ts`.** Сейчас
   `ship.ts:2` импортирует `SHIP_SPRITE` из `art.ts`, а `player.ts:5` — `ship.ts`. Если
   `SHIELD_COLORS`/`SHIELD_SPRITES` строить через `MAX_SHIELD` (`Array.from({length: MAX_SHIELD + 1})`
   и т. п.), получится цикл `art → player → ship → art`: при загрузке через `art.ts` первым
   `ship.ts` вычислит `SHIP_WIDTH = SHIP_SPRITE.width` (`ship.ts:6`) до инициализации
   `SHIP_SPRITE` — `ReferenceError` (TDZ). Предложение: записать в дизайне явно — `art.ts`
   не импортирует логику (`player.ts`, `ship.ts`), массивы задаются литералами из 6
   элементов, а связь с `MAX_SHIELD` и `SHIP_WIDTH` проверяет `art.test.ts` (он может
   импортировать оба). `hud.ts` импортировать `MAX_SHIELD` из `player.ts` может — цикла нет.

2. **Задача 031 трогает больше тестов, чем перечислено, — перечислить явно, иначе она не
   будет зелёной.** Переименование `'life' → 'shield'` в `BonusKind` ломает `typecheck` в
   файлах, которых нет в таблице модулей: `asteroid.test.ts` (8 мест `new Asteroid(…, 'life')`),
   `capsule.test.ts` (4), `bonus.test.ts:6`, `collisions.test.ts:677–726`. Удаление
   возрождения ломает `battle-render.test.ts:258–333` («explosion ends before the respawn»,
   «blinks the invulnerable ship at SHIP_START_X», «draws the ship again once active» — все
   строят `invulnerable` через `hit()` + `run(DOWN_TICKS)`), хотя `battle-render.ts` в 031 не
   меняется. Плюс `play-scene.test.ts:34,206,311`, `title-scene.test.ts:5,104–130`,
   `dev-snapshot.test.ts:48,70–81`, `dev-params.test.ts` целиком, `hud.test.ts:31,50–66,169–186`,
   `hud-render.test.ts:33,87,106,117,138–154,188`. Предложение: в 031 добавить список
   «тесты, которые обязательно править» с этими файлами.

3. **Массовая замена `'down'` на `'invulnerable'` в тестах коллизий и боя.** Сейчас
   почти все кейсы в `collisions.test.ts` (≈20: строки 257–483, 574, 701) и
   `battle.test.ts:240–268,290–306` создают `new Player()` / `new Battle()` с умолчаниями и
   ждут `state === 'down'` после попадания; «неуязвимого» игрока строят через
   `update × DOWN_TICKS` (`collisions.test.ts:329,448,691`). С `START_SHIELD = 2` попадание
   даёт `invulnerable`, а через `DOWN_TICKS` из `down` больше не выйти. Правила коллизий от
   этого не меняются (`canBeHit` в обоих состояниях `false`), но кейсы надо осознанно
   разделить: «попадание засчитано» — проверять `shield − 1` / `invulnerable`; «гибель и
   прицеливание в `down`» (`battle.test.ts:254` «no target while down») — строить с
   `shield: 0`; «неуязвимый» — через `hit()` при `shield > 0`. Предложение: так и записать
   в 031, чтобы исполнитель не «чинил» тесты подстановкой ожиданий.

4. **`DOWN_TICKS` перестаёт быть константой `Player`.** После удаления возрождения
   `Player` её не использует (`player.ts:154` — единственное место); она нужна только как
   `GAME_OVER_DELAY_TICKS` (`battle.ts:21`) и в проверке «взрыв короче задержки»
   (`battle-render.test.ts:259`). Предложение: `GAME_OVER_DELAY_TICKS = 60` задать в
   `battle.ts` напрямую, `DOWN_TICKS` удалить, тесты (`collisions.test.ts:9`,
   `battle-render.test.ts:16`) перевести на `GAME_OVER_DELAY_TICKS`. Не обязательно — если
   оставить, хотя бы поправить комментарий (`player.ts:15`).

5. **В 032 сломаются точные списки вызовов в `battle-render.test.ts`.** Тесты сравнивают
   полный список `fillRect` (`shipCalls(x, y)`, напр. строки 316, 320, 333). С щитом по
   умолчанию `START_SHIELD = 2` каждый кадр корабля добавит пиксели дуги — упадут все такие

6. **Утверждение «баланс начала игры не меняется» верно только по числу ударов.** Сейчас

   приёмку («не слишком ли быстро снимается щит»); значение `INVULNERABLE_TICKS` пусть

7. **Временный HUD в 031 вводит в заблуждение.** «`shield` иконок кораблей» означает: старт

  ощущение передышки.

## Подтверждено

- `Player` хранит `livesLeft`, `hit()` действует только из `active` (`player.ts:139–143`) —
  замена на `shield` с ветвлением `shield > 0 ? invulnerable : down` тривиальна;
  `canBeHit`/`canBeTargeted` менять не нужно.
- Переход `down → invulnerable` и перенос в `SHIP_START_X` — одно место
  (`player.ts:154–156`); после удаления `down` без выхода — ровно текущее поведение при
  `lives === 0`.
- `Battle.updatePhase` уже переводит в `over` по `isLost && stateTicks >= GAME_OVER_DELAY_TICKS`
  (`battle.ts:181`) — с `isLost = state === 'down'` работает без изменений.
- Порядок «коллизии с врагами → `addScore` → бонусные коллизии → `applyBonus`»
  (`battle.ts:126–135`) даёт описанные в дизайне крайние случаи (таран + порог, удар + `L`
  в одном тике); `catchCapsule` не ловит в `down` (`collisions.ts:91`).
- Одно попадание за тик — `hitByEnemyShot`/`ram` проверяют `canBeHit` (`collisions.ts:128,141`);
  после `hit()` в `invulnerable` таранщик летит дальше — как в дизайне.
- Детерминизм: `Player` не использует `rng`; `BonusField` выбирает вид по индексу
  `BONUS_KINDS` — переименование значения при том же порядке розыгрыш не сдвигает. Оговорка:
  совпадение поведения с тем же seed — только до первого попадания (дальше корабль не
  исчезает, и прицел/позиция другие); тест `play-scene.test.ts:311` сравнивает с эталонным
  боем, а не с записанными числами — не сломается.
- `isLost`, `state`, `lives` вне тестов читают только `battle.ts`, `hud.ts:108`,
  `dev-snapshot.ts:93–100`, `battle-render.ts:66–71`, `collisions.ts:91` — перечень в
  дизайне полный (плюс `main.ts:20`, `title-scene.ts:10`, тоже указаны).
- Геометрия HUD: бывшая `LIVES_ZONE` 200…247 × 14…21 (48 px) вмещает 5 сегментов 8 px с шагом
  10; `HUD_ZONES` и тест непересечения переиспользуются.
- `parseIntIn` (`dev-params.ts:27`) принимает `0`, так что `?shield=0` (быстрый game over,
  замена `?lives=1`) работает тем же парсером.
- Дуга 15×4 при `SHIELD_OFFSET_Y = −5` (строки 203…206) не залезает в спрайт корабля
  (`SHIP_Y = 208`) и в HUD.
