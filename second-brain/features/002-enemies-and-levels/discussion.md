2. **Тесты `play-scene.test.ts` сломаются на попаданиях — принято, вариант (а).**

   их третьим аргументом; `levelConfig(level, levels = LEVELS)`. Новый тестовый модуль

## Реализация: задача 006-static-formation

Вопросы разработчика из `second-brain/tasks/tasks/006-static-formation/analyze.md`
(«Открытые вопросы», пп. 1–4). Все технические, решены в рамках дизайна; к владельцу —

1. **Неиспользуемые `rng`/`dt` в `Wave` — решено: `_rng`, `_dt`; `Enemy.update()` без

   (`_dt` → `dt`) и 009 (`_rng` → `rng`) — переименование в одну строку. Отвергнуто:
   публичное `readonly rng` в `Wave` — чтобы обойти TS6138, пришлось бы расширить API,
   которого в дизайне нет; `Battle` без `rng` до 009 — противоречит решению раунда 3
   (отдельный `Rng` боя — в задаче 006 вместе с первым потребителем) и сдвигает правку
   `PlayScene` в задачу с поведением.

   Возвращает `void`; `boolean` («хочу стрелять») — с 012, `dt`/`env` — в задаче, которая
   их первой использует (не позже 009, `EnemyEnv`). Вариант (б) с пустым

2. **Создание `Battle` в `PlayScene` — решено: в теле конструктора, сначала звёзды,
   потом seed.** Поле `readonly battle: Battle` объявляется без инициализатора.
   Порядок: `starfield ?? new Starfield(…, rng)`, затем
   `new Battle(createRng(Math.floor(rng() * 2 ** 32)))`. Причина — раскладка звёзд для

## Реализация: задача 007-formation-sway

Вопросы разработчика из `analyze.md` задачи 007 («Открытые вопросы»).

1. **Несимметричный разворот строя — решено: правая граница смещения сдвигается на
   `1 - step`, видимые края симметричны.** Прогон разработчика подтверждён (скрипт по
   правилу дизайна): при 15 px/с и границах `±16` пиксель `+16` виден 1 тик, `-16` —
   7 тиков. Причина не в `floor` для отрицательных как таковом, а в том, что пиксель
   `v` виден при `offset ∈ [v, v + 1)`: левая граница `-16` лежит у нижнего края своего
   пикселя и проходит через весь `[-16, -15)`, правая `+16` — тоже у нижнего края, но
   строй разворачивается, едва войдя в `[16, 17)`. Оставлять это на приёмку не нужно:
   дефект известен заранее, а исправление — одна формула внутри `Formation`, без
   изменения API.
   Новое правило: `maxOffset = SWAY_RANGE + Math.max(0, 1 - step)`, `minOffset =
-SWAY_RANGE`, `step = swaySpeed * dt`; обрезка и смена `dir` — как раньше. На сетке
   шага `floor(1 - step - x) = -floor(x)`, поэтому отображение симметрично; каждый
   край — последний пиксель перед выходом за `±16`.
   Числа (15 px/с, проверены прогоном): `+16` впервые — тик 64, `16.75` и разворот —
   тик 67, `-16` и разворот — тик 198, возврат в `0` с `dir = 1` — тик 262; период
   **262 тика** (было 256). Края `±16` — по **7 тиков**, промежуточные — по 4 за проход.
   1/8 px/тик — края 15, середина 8, период 526; 1/2 — края 3, середина 2, период 130;
   целые px/тик — без изменений (`maxOffset = 16`).
   Почему 7, а не 3 или 1 (тоже симметричные варианты `[-15.5, 16.25]` и `[-15.25,
16]`): при 7 край получает почти ту же долю экранного времени за период, что и любое
   промежуточное положение (7 против 8), при 1 край мелькает одним кадром, при 3 —
   заметно короче соседей. Кроме того, левая граница остаётся ровно `-SWAY_RANGE`
   (тесты 009 «крайний враг при `-SWAY_RANGE`» не меняются), формула одна для всех
   скоростей. Отвергнуто: квантование `offset` до целых — противоречит ADR 003 и точной
   привязке `returning` к дробному слоту; смена `floor` в рендере — задевает рендер и
   коллизии всех сущностей (`overlaps` по `floor`).
   Геймдизайн не затронут: видимый размах ровно ±16 px (В9), скорость 15 px/с (В1);
   период в `game-design.md` и ответах владельца не задан — к владельцу не выносится.
   Последствия для задачи: тесты `formation.test.ts` — `16.75` на тике 67 и разворот
   (тик 68 — `16.5`), `-16` на тике 198 (тик 199 — `-15.75`), гистограмма
   `Math.floor(offset)` за период — `±16` поровну (7/7 для 1/4; также для 1/8 и 1/2);
   инвариант экрана — при `maxOffset` (11 столбцов: 232,75 ≤ 256); тест целой скорости
   (3 px/тик) — обрезка ровно до 16, как было. В `design.md` — пункт «Разворот
   покачивания» в «Точных правилах», правки «Formation», «Интерфейсы» (комментарий к
   `SWAY_RANGE`), «Тестирование», «История».
2. **Строка «расширено ADR 003» в ADR 002 — решено: добавить.** ADR 002 формулирует
   правило как безусловное («целое число px/тик»); после 007 код ему формально
   противоречит, и читатель ADR 002 без ссылки этого не узнает. Достаточно одной строки
   в шапке/конце ADR 002 (`Расширено: ADR 003 — двоичные дроби для медленных движений`),
   статус ADR 002 остаётся «принято»: ADR 003 расширяет, а не отменяет его.

Итог: 2 вопроса — решено 2, к владельцу 0.

## Реализация: задача 008-enemy-hits-levels

Отступление разработчика от дизайна (`plan.md` задачи 008, раздел 10) — **принято**.

Дизайн помещал разбор `?level=N` прямо в `main.ts` («не целое ≥ 1 — уровень 1»). В
плане и коде разбор вынесен в чистую функцию `parseStartLevel(value: string | null):
number` в `src/game/levels.ts`: только десятичные цифры (`/^\d+$/`), безопасное целое
≥ 1, иначе 1, не бросает. `main.ts` лишь читает параметр URL под `import.meta.env.DEV`
и передаёт результат в `TitleScene`.

Почему принято:

- `main.ts` не покрыт тестами (DOM, `window.location`); правило разбора с краевыми
  случаями (`'1.5'`, `'1e3'`, `' 2'`, `'-2'`, переполнение) в нём осталось бы
  непроверенным. Чистая функция тестируется `it.each` без DOM — по принципу «логика
  отдельно от среды».
- Строгое «только цифры» точнее исходной формулировки: `Number(' 2')` и `Number('1e3')`
  дают целые, но это не то, что пишет человек в URL; поведение для разумного ввода то
  же.
- Место — `levels.ts`: функция про номер уровня, `levels` — лист графа, новых
  зависимостей и циклов нет; `main → levels` — одна новая связь из точки входа.
- Альтернатива — отдельный модуль `dev-params.ts`: лишний файл ради одной функции.
  Отвергнута.

В `design.md` отражено: «Модули и файлы» (`levels.ts`, `main.ts`), граф импортов,
«Интерфейсы» (сигнатура и контракт), «Тестирование» (`levels.test.ts`), «Появление API

## Реализация: задача 013-raiders

Вопросы разработчика из `analyze.md` задачи 013 (раздел «Риски» и «Открытые вопросы»).

### 1. Группа `raider` у края экрана сжимается — **решено** (дизайн изменён)

Проблема подтверждена по коду `enemy.ts`: цель члена — `targetX + aimOffsetX`, позиция
зажата в `[0, SCREEN_WIDTH - width]` по каждому врагу отдельно. Пример — уровень 5,
левая группа (`side = -1`, сдвиги 0/16/32), корабль у правого края (центр 248): цели
248/264/280, все три упираются в `x = 243` и рисуются одним спрайтом, а их выстрелы идут
одним столбцом. Игроки часто держатся у края, так что это частый видимый дефект и
нарушение В4 («группа держит строй»). Оставлять не стоит.

Где сжатие возникает: только в `descend` и только с «дальней» от лидера стороны (лидер —
самый внешний в сторону `side`, все сдвиги одного знака). В `peel` зажим при нынешних
числах не срабатывает: крайний столбец при `-SWAY_RANGE` стоит на `x ≥ 25`, дуга уводит
на 14 px, а все члены идут по ней одинаково.

Правило: **зажимать не позицию каждого, а общий якорь цели — по размаху группы.** Чисто
в текущем API это невозможно: член знает только свой `aimOffsetX`, а для сдвига группы
целиком нужен её размах. Проверены варианты без нового поля — каждый член зажимает якорь
по своему сдвигу: члены получают разные якоря и группа всё равно сжимается (для пары 0/16
у правого края оба встают в `x = max`). Поэтому `DiveOrder` получает два поля:

- `groupMinOffsetX` / `groupMaxOffsetX` — минимум и максимум `aimOffsetX` по живым
  членам вылета (одинаковы у всех членов; лидер даёт 0, поэтому `min ≤ 0 ≤ max`;
  одиночка — `0`/`0`). Считает `selectSortie` вместе с `aimOffsetX`.
- В первом тике `descend` (`fixed`, `targetX !== null`): `half = Math.floor(width / 2)`,
  `anchor = clamp(targetX, half - groupMinOffsetX, SCREEN_WIDTH - width + half -
groupMaxOffsetX)`, `fixedAimX = anchor + aimOffsetX`.

Почему строй держится точно: члены — один вид (одна ширина) с одинаковыми полями группы
→ якорь один → `gap` у всех одинаков → одинаковый шаг руления. Все цели внутри экрана,
старт внутри экрана, руление не перелетает цель — зажим позиции у группы в `descend` не
срабатывает вовсе (остаётся страховкой). В том же примере якорь = 217, цели 217/233/249:
над кораблём оказывается крайний член, угроза у края сохраняется, а выстрелы идут тремя
столбцами.

У одиночек поведение 010 не меняется: при `0`/`0` диапазон якоря `[floor(w/2), 256 -
ceil(w/2)]` шире диапазона центра корабля `[7, 248]` (спрайты врагов ≤ 13 < ширины
корабля 15). `track` поля группы не читает.

Отвергнуто:

- **Сдвигать всю группу на одинаковую величину во время полёта** (координация членов в
  `Wave`): нужна групповая логика во время полёта, у `Enemy` нет доступа к соседям.
  Сложнее без выгоды.
- **Не зажимать X у `raider`**: члены уходят за край экрана и стреляют невидимыми.
- **Одно поле размаха вместо двух** (знак по `side`): экономит поле ценой неочевидной
  кодировки; два явных поля проще читать и тестировать.

Цена: два обязательных поля в `DiveOrder` — те же литералы, что и для `aimOffsetX`
(см. п. 2в, общий хелпер). Тесты — в `enemy.test.ts` (якорь у правого края для 0/16/32,
у левого — для −32/−16/0; разница X членов сохраняется до ухода за низ) и в
`attack-director.test.ts` (поля группы по живым членам). В `design.md` — новый пункт
«Цель `fixed` группы» в «Точных правилах», правки «Enemy», «AttackDirector»,
«Интерфейсы», «Тестирование», «Появление API по задачам», «История».

### 2. Технические решения разработчика

(а) **`side` группы — по живым членам: подтверждаю, решено.** Совпадает с правилом
одиночки (`side` по текущему положению) и с выбором лидера среди живых; одна точка
правды — «живые члены вылета» — для `side`, лидера, `aimOffsetX` и размаха. Для `LEVELS`
результат одинаков. В «Точных правилах» уточнено.

(б) **Порядок кандидатов внутри ряда — по левому столбцу кандидата (у группы — левый
живой член): подтверждаю, решено.** Это и есть «слева направо» дизайна; кандидаты ряда
не пересекаются по столбцам, ничьих нет. Тест «lists row edges top to bottom, left
before right» не меняется. В «AttackDirector» уточнено.

(в) **`aimOffsetX` (и теперь `groupMinOffsetX`/`groupMaxOffsetX`) и `Slot.group` —
обязательные; в тестах — общий хелпер приказа: подтверждаю, решено.** Необязательные
поля с умолчанием спрятали бы забытый сдвиг в боевом коде (`selectSortie` обязан
заполнять их всегда). Хелпер — например `diveOrder(overrides?: Partial<DiveOrder>):
DiveOrder` с умолчаниями `{ sortieId: 1, side: 1, shots: 0, aimOffsetX: 0,
groupMinOffsetX: 0, groupMaxOffsetX: 0 }` в общем тестовом модуле (`test-levels.ts` —
уже общий модуль тестовых данных; имя и место — на усмотрение разработчика). Тесты,
сверяющие точные приказы `selectSortie`, пишут объекты полностью.

### 3. Лимит `MAX_ENEMY_SHOTS = 4` съедает залпы на уровне 5 — **подстройка после просмотра**
