# Дизайн: Повторный пролёт несбитого астероида

**Статус:** согласовано · **Раунд:** 3

Опирается на фичу 006 (`design.md`, `discussion.md` там же; код — `src/game/bonus-field.ts`,
`asteroid.ts`, `battle.ts`, `dev-snapshot.ts`). Вопросы В1–В4 закрыты владельцем (см.
«Решения владельца»), ответы по отзыву разработчика — в `discussion.md`.

## Цель и сценарии

Сейчас астероид появляется раз за уровень, и если игрок его не сбил — бонус пропал до
следующего уровня. Цель: дать ещё шанс, не меняя ничего в самом астероиде и капсуле.

**Что видит игрок:**

1. Астероид пролетел и ушёл за нижний край несбитым. Через **случайные 5–15 с** фазы
   `playing` (300…900 тиков, то же окно, что у первого появления, В1) сверху снова вылетает
   астероид — **с тем же бонусом** (В3), но с новой случайной стороной и смещением старта
   (траектория разная, чтобы повтор не выглядел «записью»).
2. Не сбил и его — ещё через случайные 5–15 с снова. Повторы **без ограничения числа** в
   пределах уровня (В2): пока не сбил или пока уровень не сменился.
3. Сбил (с первого раза или с повтора) — как в 006: 100 очков с надбавкой текущего уровня,
   капсула; больше повторов этого астероида нет. Капсула, которую не поймали, пропадает
   (вне рамок).
4. Уровень сменился, пока повтор ждал (`cleared` → `playing` следующего уровня): ожидающий
   повтор **отменяется**, новый уровень тянет свой астероид как обычно (В4). Бонус за
   несбитый астероид прошлого уровня потерян — новый уровень и так даёт новый шанс.

**Крайние случаи (решения архитектора, следуют из правил 006):**

- **Таймер повтора идёт только в `playing`**, как и окно появления: в `cleared` и `over`
  он стоит. Значит, повтор никогда не вылетает в паузе между уровнями и после конца игры.
- **Корабль сбит / мигает** — таймер идёт (фаза `playing`), как и появление в 006.
- **Правило одно: повтор назначается, только если ничего не ожидает вылета**
  (`pending === null`). На деле `pending === null` в момент ухода бывает **только у
  астероида текущего уровня**. После `startLevel` в ожидании стоит новый астероид уровня, а
  вылететь он не может, пока на поле летит старый (проверка пустого поля). Поэтому
  астероид прошлого уровня, улетевший уже на новом уровне, всегда застаёт ожидание занятым:
  повтор не назначается, `rng` не вызывается, свой астероид у нового уровня и так будет.
  Проверка `pending === null` остаётся в коде как защита. Отдельного теста на «ожидание
  пусто при уходе старого» нет: этот случай недостижим.
- **Ушёл в фазе `cleared`** (астероид вылетел в конце уровня): повтор назначается
  (задержка тянется из `rng`), но таймер стоит, а `startLevel` его отменяет (В4). Итог
  тот же, что в 006. В `over` аналогично: назначен, но не вылетит никогда.
- **«Не больше одного бонусного предмета»** не меняется: после ухода астероида поле пусто
  (капсула бывает только после попадания), повтор вылетает через ту же проверку пустого
  поля, что и обычный астероид.
- **Взорванный астероид** (`exploding` → `gone`) повтор не назначает — только ушедший за
  край из `flying`.

## Сущности и состояния

**Asteroid** — без изменений: `flying → exploding → gone`, `flying → gone` (ушёл за край).

**BonusField** — сейчас «ожидание» описано одним числом `tick: number | null` (тик уровня
появления). Заменяется на одну запись ожидания:

```ts
interface PendingAsteroid {
  /** Level tick ('playing' ticks) on which it may fly out (still waits for an empty field). */
  readonly tick: number;
  /** null - a new asteroid, the bonus is drawn at spawn; otherwise a retry with this bonus. */
  readonly bonus: BonusKind | null;
}
private pending: PendingAsteroid | null = null;
```

Состояние ожидания поля (неявный автомат), `d` — `randomInt(rng, minTicks, maxTicks + 1)`
из `spawnWindow`:

```
idle (pending = null)
  --startLevel--> waitingNew   (ticks = 0; pending = { tick: d, bonus: null })
waitingNew | waitingRetry
  --update(spawning), levelTicks >= tick, поле пусто--> idle, вылетает астероид
  --startLevel--> waitingNew   (повтор отменён, В4)
idle
  --астероид ушёл несбитым--> waitingRetry (pending = { tick: L + d, bonus: asteroid.bonus })
waitingNew
  --астероид ушёл несбитым--> waitingNew (без изменений, rng не трогается)
```

**Задержка повтора — то же окно `spawnWindow`.** Отдельной константы нет. Задержка
отсчитывается от ухода тем же окном, которым тик первого появления отсчитывается от начала
уровня. Тянется одним вспомогательным методом, общим со `startLevel`:

```ts
/** One rng call: a tick count in the spawn window, inclusive. */
private drawWindowTicks(): number {
  return randomInt(this.rng, this.spawnWindow.minTicks, this.spawnWindow.maxTicks + 1);
}
// startLevel: this.pending = { tick: this.drawWindowTicks(), bonus: null }
// retry:      this.pending = { tick: this.ticks + this.drawWindowTicks(), bonus }
```

Почему общее окно, а не отдельное `retryWindow`:

- владелец сказал «как первое появление», значит одно правило и один источник чисел;
- окно уже инжектируется в тестах. Короткое или вырожденное окно (`{d, d}`) сразу делает
  быстрыми и детерминированными и первый вылет, и повтор, а нового параметра конструктора
  не нужно;
- тестам, которым нужны разные окна для первого вылета и повтора, хватает `queued(...)`.
  Окно `{1, 900}` и значения `rng` дают любые задержки.

Если когда-нибудь окна разойдутся, это будет отдельный необязательный параметр. Сейчас не
делаем.

`minTicks >= 1` (проверка в конструкторе), поэтому `tick` повтора всегда больше текущего
`ticks`: повтор не может вылететь в тот же update, в котором ушёл астероид.

**Точный отсчёт задержки (контракт для теста).** Пусть астероид ушёл в update E, и после
прироста `ticks` в E (если E — `spawning`) `levelTicks = L`. Если E не `spawning`, `L` —
значение без прироста. Повтор назначается в E: `spawnTick = L + d`,
`d ∈ [minTicks, maxTicks]`, `d` из `rng`. Повтор вылетает в первом `spawning`-update, после
которого `levelTicks >= L + d` и поле пусто. При сплошном `playing` после E это update
`E + d`. Если E был не `spawning`, то это `d`-й `spawning`-update после E. С вырожденным
окном `{d, d}` всё фиксировано, на этом и строятся тесты. С игровым окном `d` лежит в
300…900, с `rng: () => 0` будет `d = 300`.

**rng.** Порядок вызовов (один `rng` поля, как в 006):

| Событие                                                   | Вызовы                                                 |
| --------------------------------------------------------- | ------------------------------------------------------ |
| `startLevel`                                              | 1 — тик появления                                      |
| вылет нового астероида                                    | `dir`, `offset`, `bonus`                               |
| уход несбитым при `pending === null` (назначение повтора) | **1 — задержка `d`** (в update ухода, после `ticks++`) |
| уход несбитым при занятом `pending`                       | 0                                                      |
| вылет повтора                                             | `dir`, `offset` (бонус не тянется, В3)                 |
| отмена повтора (`startLevel`)                             | только 1 вызов самого `startLevel`                     |

Все существующие сценарии без ухода несбитым дают ту же последовательность `rng`, что и в 006. Сценарии с уходом получают ровно один дополнительный вызов в update ухода.

## Поток тика

`Battle.update` не меняется: player → wave → `bonusField.update(dt, phase === 'playing')` →
столкновения с врагами → бонусные столкновения → фаза (`startLevel` при смене уровня).

Внутри `BonusField.update(dt, spawning)` порядок фиксирован:

1. Астероид: `wasFlying = state === 'flying'`; `update(dt)`; если стал `gone`, запомнить
   `escaped: BonusKind | null = wasFlying ? current.bonus : null` и только потом убрать
   (`this.current = null`). Если не ушёл, `escaped = null`.
2. Капсула — как сейчас.
3. `if (spawning) this.ticks++;` (поднят выше `return`. На движение `ticks` не влияет,
   поведение 006 не меняется.)
4. `if (escaped !== null && this.pending === null)` →
   `this.pending = { tick: this.ticks + this.drawWindowTicks(), bonus: escaped }`.
5. `if (!spawning) return;`
6. Если `pending` есть, `ticks >= pending.tick` и поле пусто — вылет: `spawn(pending.bonus)`,
   `pending = null`. Новый астероид в тик появления не двигается (как в 006).

Почему именно такой порядок:

- **3 до 4** (`ticks++` до назначения): так выполняется контракт отсчёта `L + d`, и повтор
  не вылетает в update ухода.
- **4 до 6** (назначение до проверки вылета): в update, где ушёл астероид прошлого уровня и
  вылетает новый, `pending` ещё занят новым, поэтому повтор не назначается. Если поставить
  назначение после вылета, `pending` к этому моменту уже `null`: лишний вызов `rng` и
  второй астероид за уровень. Это обоснование записывается и в doc-комментарий `update`.
  Тест-сторож: `delays the spawn while the field is busy with a flying asteroid`
  (`bonus-field.test.ts:204`), его концовка (`calls() === before + 3`, `spawnTick === null`)
  падает при неверном порядке.

Отрисовка не меняется: повтор — обычный `Asteroid`, рисуется тем же кодом.

## Интерфейсы

```ts

export class BonusField {
  constructor(rng: Rng, spawnWindow?: SpawnWindow); // без изменений; окно — и для повтора

  get asteroid(): Asteroid | null;      // без изменений
  get capsule(): Capsule | null;        // без изменений
  /**
   * Level tick of the next asteroid (new or retry); null when nothing waits.
   * Смысл расширен: раньше только новый астероид уровня.
   */
  get spawnTick(): number | null;       // = pending?.tick ?? null
  /** Bonus of the waiting retry; null when nothing waits or a new asteroid waits. For tests / QA. */
  get retryBonus(): BonusKind | null;   // = pending?.bonus ?? null
  get levelTicks(): number;             // без изменений

  /** Draws this level's spawn tick; a waiting retry (or unspawned asteroid) is dropped. */
  startLevel(): void;
  /** ... an unshot asteroid that left schedules its retry (1 rng call) if nothing waits. */
  update(dt: number, spawning: boolean): void;
  hitAsteroid(): boolean;               // без изменений
  takeCapsule(): BonusKind | null;      // без изменений

  /** rng: dir, offset, then bonus only when not given (bonus ?? BONUS_KINDS[randomInt(...)]). */
  private spawn(bonus: BonusKind | null): Asteroid;
  /** One rng call, minTicks..maxTicks inclusive. Used by startLevel and the retry. */
  private drawWindowTicks(): number;
}

// dev-snapshot.ts — bonuses

```

## Тестирование

**Unit (`bonus-field.test.ts`).** Окна: вырожденное `{d, d}` для точных моментов, короткое
для скорости.

- **Переписать** `spawns on the update where levelTicks reaches spawnTick, once per level`
  (`:101`). С повтором он бросает исключение на пятом вызове `rng` (задержка в update ухода
  552). Новое содержание: вылет ровно на `spawnTick`, затем `FLIGHT_TICKS` update'ов. До
  ухода на поле только этот астероид и `calls() === 4`. В update ухода `calls() === 5`,
  `spawnTick` не `null`. Добавить значение задержки в `queued(...)`, например `0` → 300.
  Название без «once per level». Повтор проверяют тесты ниже.
- **Тест `calls the rng in the order dir, offset, bonus on spawn` (`:126`) — без изменений**
  (регрессия порядка `spawn(null)`).
- **Назначение и вылет повтора, точный момент:** окно `{d, d}`. Ушёл в update E →
  `spawnTick === levelTicks + d`, `retryBonus === asteroid.bonus`. В `E + d - 1` астероида
  нет, в `E + d` есть, `spawnTick === null`, `retryBonus === null`.
- **Порядок `rng` повтора и сохранение бонуса** через `queued(...)`. Первый астероид с
  бонусом ≠ `BONUS_KINDS[0]` (например `0.5` → `fastShot`). В update ухода ровно +1 вызов
  (задержка). При вылете повтора ровно +2 (`dir`, `offset`), третий вызов бросает.
  Бонус повтора равен бонусу первого. `dir`/`offset` повтора отличаются от первого, чтобы
  проверить, что они взяты из новых значений.
- **Задержка из окна:** игровое окно, значение `rng` для задержки `ALMOST_ONE` →
  `spawnTick === L + 900`, `0` → `L + 300`.
- **Неограниченно:** повтор, ушедший несбитым, назначает следующий (минимум 2 повтора
  подряд, бонус тот же).
- **Сбитый не повторяется:** `hitAsteroid` → `exploding` → `gone` → `spawnTick === null`,
  `retryBonus === null`, лишних вызовов `rng` нет.
- **Таймер стоит при `spawning = false`:** N update'ов без `spawning` во время ожидания не
  сдвигают вылет.
- **Ушёл при `spawning = false`** (как в `cleared`). Окно `{d, d}`, астероид уходит в
  не-`spawning` update. `spawnTick === levelTicks + d` без прироста, задержка уже
  вытянута. Потом `d - 1` `spawning`-update'ов → нет. Ещё один → повтор на поле.
- **`startLevel` в ожидании повтора отменяет его:** `retryBonus === null`, `spawnTick` —
  новый из окна (1 вызов), вылет — новый астероид (бонус из `rng`).
- **Регрессия порядка шагов 4 → 6 — без изменений:** `delays the spawn while the field is
busy with a flying asteroid` (`:204`) и `:250`. Они же покрывают случай «астероид пережил
  `startLevel` и ушёл несбитым, пока ждёт новый астероид уровня» (повтор не назначен,
  лишнего `rng` нет). Отдельный тест на это не пишем.
- Инвариант «не больше одного бонусного предмета» — существующий тест остаётся зелёным.

**Unit (`battle.test.ts`)** — один интеграционный на `bonusBattle()` с `rng`, который
возвращает 0 и считает вызовы (как в `battle.test.ts:657-661`): астероид уходит несбитым →
через `ASTEROID_SPAWN_MIN_TICKS` (300: при `rng = 0` задержка равна нижней границе окна)
тиков `playing` на поле снова астероид, раньше — нет. При смене уровня в ожидании повтора:
повтора нет, `retryBonus === null`, `spawnTick === 300`, `levelTicks === 0`, и к этому
моменту вызовов `rng` ровно 6 (конструктор 1 + вылет 3 + задержка 1 + `startLevel` 1). Это
различает отмену и неотменённый повтор: подтверждает, что в реальном потоке `Battle`
задержка тянется один раз, в update ухода, а не повторно в `cleared`. Бонус здесь **не**
проверяем: при `rng = 0` он совпал бы и без сохранения (см. `discussion.md`, раунд 2, п. 5).
Остальные тесты боя, `dev-snapshot.test.ts`, `play-scene.test.ts`, `collisions.test.ts`
не меняются (до ухода несбитым не доходят или `rng` постоянный).

**dev-snapshot** — `retryBonus` попадает в снимок (`null` / вид бонуса).

**Глазами / `/qa`** (`acceptance.md` задачи): `?seed=…&paused=1`, дождаться астероида
(`bonuses.spawnTick`), не стрелять. После ухода `retryBonus` не `null`, `spawnTick` в
пределах `levelTicks + 300 … levelTicks + 900`. `step` до `spawnTick` → снова виден
астероид, `bonus` тот же, сторона и смещение — как выпал `rng`. Ощущение частоты повтора
(не слишком ли часто/редко) — вкусовое, владельцу.

## Правка game-design.md

Предлагаемая формулировка пункта «Астероиды и бонусы» (замена целиком; правит разработчик
в задаче, новое выделено здесь только для ревью — в файле без выделения):

> - **Астероиды и бонусы** (решено, фича 006, В1–В9; повтор — фича 007, В1–В4): раз за
>   уровень в случайный момент 5–15 с фазы `playing` сверху падает астероид 12×12
>   наискосок (60 px/с вниз, 30 px/с вбок); он безопасен и ни с чем, кроме выстрелов
>   игрока, не взаимодействует. **Несбитый астероид, ушедший за нижний край, прилетает
>   снова через случайные 5–15 с фазы `playing` — с тем же бонусом, но с новой случайной
>   стороной и смещением; повторы без ограничения, пока не сбит, в пределах уровня. При
>   смене уровня ожидающий повтор отменяется (астероид прошлого уровня, улетевший
>   несбитым уже на новом, тоже не возвращается — у нового уровня свой астероид).** Сбит
>   одним выстрелом — 100 очков с надбавкой уровня и капсула 8×8 с буквой `L` / `S` / `D`
>   (равновероятно), падает строго вниз 60 px/с, выстрелы пролетают сквозь неё. Капсулу
>   ловит корабль (и мигающий после возрождения, но не сбитый); не поймал — пропала.
>   `L` — доп. жизнь, `S` — быстрая пуля, `D` — две пули; улучшения — до конца игры,
>   переживают гибель и смену уровня, не складываются. Бесполезный бонус (`L` при 5
>   жизнях, уже полученное улучшение) — 500 очков. Астероид и капсула переживают смену
>   уровня; на поле не больше одного бонусного предмета (следующий астероид ждёт пустого
>   поля). Полученные улучшения видны в панели значками до конца игры.

## Альтернативы

- **Флаг `escaped` / состояние `escaped` в `Asteroid`.** Явнее, но меняет модель и её
  тесты ради одного места; в поле факт «был `flying`, стал `gone`» однозначен. Отвергнуто
  ради минимального диффа; если разработчик предпочтёт геттер в `Asteroid` — эквивалентно.
- **Не убирать астероид, а «развернуть» его наверх (тот же объект летит снова).** Сломает
  простой автомат `Asteroid` (`gone` перестанет быть конечным) и заставит держать объект на
  поле в паузе — нарушит «поле пусто → может вылететь следующий». Отвергнуто.
- **Отдельное поле `retry` рядом с `tick`.** Два независимых ожидания требуют правил, кто
  первый и что если оба созрели. Одна запись `pending` делает правило «в ожидании не
  больше одного» структурным. Выбрано `pending`.
- **Повтор переносится на следующий уровень** (В4 б). Отвергнут владельцем; потребовал бы
  очередь ожиданий вместо одной записи.
- **Тянуть задержку повтора в момент вылета, а не назначения.** Тогда `spawnTick` до вылета
  неизвестен, для QA и тестов нужен отдельный флаг «ждёт повтор». Отвергнуто: при
  назначении `spawnTick` сразу точный, как у первого появления.
- **Не назначать повтор (и не тянуть `rng`), если астероид ушёл при `spawning = false`.**
  Сэкономило бы вызов, который `startLevel` всё равно отменит. Но это второе правило
  поверх «назначать, только если ничего не ждёт», а `BonusField` не знает, что
  `spawning = false` означает именно `cleared`/`over`. Отвергнуто: одно правило проще, а
  потраченный вызов детерминирован.
- **Отдельное окно `retryWindow` в конструкторе.** Владелец задал «как первое появление».
  Второе окно — лишний параметр без нужды (см. «Сущности и состояния»). Отвергнуто.

## Решения владельца

- **В1 — через сколько несбитый астероид прилетает снова:** **случайно 5–15 с, как первое
  появление** (300…900 тиков `playing` от ухода, то же окно `spawnWindow`, задержка
  тянется из `rng` при назначении).
- **В2 — сколько раз:** **без ограничения в пределах уровня**, пока не сбит.
- **В3 — какой бонус:** **тот же, что был.**
- **В4 — уровень сменился, пока повтор ждал:** **повтор отменяется**, новый уровень тянет
  свой астероид как обычно.
